# 근거 기반 디버깅

`fs-review`에서 오류 증상이나 원인 조사 요청을 받으면 이 절차를 사용한다. 새 명령어나 실행 모드는 필요하지 않다. `get_work_context`의 review 모드와 기존 evidence 기록을 재사용한다. 검토 중 구체적인 결함 징후를 발견해도 요청된 수정 범위를 임의로 넓히지 않는다.

## 문제와 재현

기대 동작, 관찰한 동작, 발생 조건, 영향 범위를 구분한다. 기대값은 요구사항·승인된 결정에서 찾고 현재 구현을 그대로 정답으로 삼지 않는다. 코드에서 알 수 있는 사실은 직접 조사하고, 재현이나 판단에 필요한 누락 정보만 사용자에게 묻는다.

관련 호출자·소비자, 레이어 책임, 상태 소유권, 이벤트 순서, 비동기 경계와 실패 처리를 추적한다. 기존 증거와 지식을 증상으로 검색하되 같은 증상이 같은 원인을 뜻하지는 않는다. 가능한 가설과 각 가설을 확인하거나 배제할 관찰을 정한다. 많은 로그를 넣기보다 원인을 구분할 수 있는 최소 관찰을 선택한다.

리뷰 전용 요청은 코드·기록·브랜치를 변경하지 않는다. 디버깅과 수정 요청은 범위 안의 재현 코드, 임시 진단, 수정과 검증을 포함한다. 브랜치는 사용자가 요청했거나 진단 변경을 격리할 필요가 있을 때만 만든다. 먼저 현재 브랜치와 미커밋 변경을 확인하고, 사용자 변경을 reset·stash·덮어쓰지 않는다. 새 브랜치만으로 기존 변경이 격리되었다고 간주하지 않는다. 별도 checkout이 필요하면 환경과 변경 이관 범위를 확인한다. 자동 커밋·푸시는 하지 않는다.

## 원인 확인과 수정

관찰 사실, 가설, 확인된 원인, 미확인 사항을 구분한다. 재현하지 못한 경우에는 조사 결과와 다음 관찰을 보고한다. 코드에서 위험을 발견하거나 로그가 사라졌다는 사실만으로 해결을 선언하지 않는다.

원인이 확인되면 관련 호출 경로 전체에 적용되는 최소 수정을 한다. 증상을 숨기기 위한 예외 무시, 임의 지연, 무조건 재시도, 불필요한 전체 구조 변경을 피한다. 더 큰 마이그레이션이나 도메인 변경이 필요하면 근거와 비용을 제시하고 해당 작업 전에 논의한다.

가능하면 같은 재현 사례가 수정 전에는 실패하고 수정 후에는 통과함을 확인한다. 해당 수정으로 영향받는 기존 검증도 수행한다. 재현 환경이 없으면 코드 수정 완료와 해결 검증 미완료를 구분한다. 재현에 필요한 외부 경계만 대체하고 검증 대상 자체를 mock으로 바꾸지 않는다. 임시 진단 코드는 제거하되 사용자 로그와 필요한 운영 관찰 기능은 보존한다. 로그에 토큰·개인 데이터가 들어가지 않도록 한다.

## 기록과 지식 환류

허용된 디버깅·수정 작업 후 `save_project_record`에 kind=evidence, id=debug-<주제>로 결과를 저장한다. 기존 ID는 `get_project_record`로 읽고 expectedHash를 전달하며, 새 ID는 null을 사용한다. 읽기 전용 요청에서는 저장하지 않고 결과만 반환한다. MCP를 사용할 수 없다면 기록을 저장했다고 말하지 말고 결과와 저장 제약을 보고한다.

기록은 문제 규모에 맞춰 다음 내용을 담는다.

- 기대/실제 동작, 발생 조건과 요구사항 근거
- 조사한 코드·커밋 또는 소스 상태, 환경과 재현 방법
- 가설, 확인·배제한 증거, 원인 또는 미확인 상태
- 수정 내용, 대안과 선택 이유, 영향을 받는 경로
- 수정 전후 검증 결과와 check ID, 남은 위험·미실행 항목
- 관련 지식 ID와 재사용 가능한 지식 후보

실제 측정한 요청 수, 특정 상호작용의 렌더 횟수, 처리 시간, 의존 방향 위반 또는 회귀 테스트 결과를 필요한 경우 기록한다. 측정 조건과 표본 수를 함께 남긴다. 렌더 횟수 감소를 전체 성능 개선과 동일시하지 않는다. 측정하지 않은 유지보수 개선은 정성적 판단으로 설명하고 종합 점수를 만들지 않는다.

해결 경험은 우선 프로젝트 기록이다. 공통 지식으로 승격하도록 사용자가 요청하거나 승인한 경우에만 `fs-knowledge`로 민감 정보와 프로젝트 고유 정보를 제거한 원본을 등록한다. 확인된 결과와 추론, 적용 조건, 반례를 보존한다. 이어 `fs-knowledge sync`로 관련 개념·판단 참조를 보강한다. 프로젝트 기록 저장만으로 공통 reference가 갱신되었다고 보고하지 않는다. 미해결 가설도 보존할 수 있지만 검증된 해결책으로 승격하지 않는다.
