# React key·타입·위치와 상태 보존

검토일: 2026-09-21 · 분류: concept · 근거: 공개 문서와 검토한 원본 요약

## 참고 상황

목록 재정렬 뒤 다른 항목의 입력이 남거나 사용자 전환 후 폼이 의도와 다르게 유지될 때.

## 판단에 사용할 내용

부모 위치·컴포넌트 타입·key와 원하는 상태 수명을 비교해 보존 또는 초기화의 원인을 찾는다.

## 적용하지 않는 경우

모든 index key를 일괄 교체하거나 모든 폼을 key로 초기화하지 않는다. 초기화 시 입력·포커스 손실도 고려한다.

## 개념과 근거

React의 상태는 트리에서 컴포넌트가 차지하는 정체성에 연결된다. 같은 부모 아래에서 타입과 key/위치가 이 판단에 관여한다. 같은 key라고 다른 타입의 상태가 보존되는 것은 아니며 key는 전역 ID가 아니다. [Preserving and Resetting State](https://react.dev/learn/preserving-and-resetting-state).

재정렬 목록에서 위치를 key로 사용하면 항목의 데이터와 상태가 어긋날 수 있다. 반대로 정렬·삽입·삭제가 없고 위치 자체가 정체성인 고정 슬롯은 다른 조건이다. key={userId} 변경은 해당 하위 트리를 새 정체성으로 취급하는 방법이지만 입력·포커스도 초기화될 수 있다. key가 유지된 같은 사용자의 새 데이터까지 자동으로 초기화한다는 뜻은 아니다.

원인 분석에서는 데이터가 같은지뿐 아니라 부모 위치, 컴포넌트 타입, key가 유지되는지와 원하는 상태 수명을 함께 본다. 기존 정체성이 요구사항과 맞으면 변경할 이유가 없다. 모든 폼을 key로 리셋하거나 모든 index key를 일괄 수정하는 정책으로 사용하지 않는다.

원본의 key 설명과 비용을 보존했다. 문자열 key="{userId}"와 JSX 표현식 key={userId}는 다르다. Fiber 내부의 key 필드나 특정 reconciliation 알고리즘은 공개 상태 보존 모델과 구분한다. 이 개념은 React용이며 이번 sync에서 실제 제품의 리셋 동작을 실행한 결과는 아니다.
