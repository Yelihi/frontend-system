# 느린 상호작용과 동기 레이아웃 진단

검토일: 2026-09-21 · concept · public-contract

## 참고 상황

클릭·타이핑 반응이 늦거나 INP가 나쁘고 trace에 긴 작업·반복 Layout이 보일 때.

## 판단에 사용할 내용

입력 대기·이벤트 처리·다음 화면 표시 지연을 분리하고 재현한 작업에서 스타일 읽기·쓰기와 병목을 연결한다.

## 적용하지 않는 경우

고정 DOM 개수·16ms 예시를 공통 기준으로 강제하거나 변경 후 치수가 필요한 측정을 이전 값으로 바꾸지 않는다.

## 개념과 근거

실사용 자료로 느린 상호작용을 찾고 가능한 경우 동일 행동을 재현한다. INP 조사에서는 입력 대기, 콜백 실행, 화면 표시까지 걸린 시간을 나누어 어느 구간을 줄일지 판단한다. 계측 도구를 추가하는 것 자체가 해결은 아니다.

스타일을 바꾼 뒤 치수를 읽으면 최신 값을 제공하기 위한 동기 레이아웃이 발생할 수 있다. 반복 읽기·쓰기를 묶는 변경은 필요한 값의 시점이 같을 때 검토한다. 오래된 치수를 계속 쓰거나 모든 작업을 타이머로 미루면 정확성·후속 반응을 해칠 수 있다. 변경 전후를 같은 상호작용·환경에서 측정하며 이번 sync에서 성능 개선을 실측한 것은 아니다.

## 검토한 출처와 범위

- [web.dev — Optimize Interaction to Next Paint](https://web.dev/articles/optimize-inp) — 실사용 데이터·실험실 재현, 입력 지연·처리 시간·표시 지연의 구분, 긴 작업과 layout 조사. 삽입 미디어·관련 링크 전체는 제외.
- [web.dev — Avoid large, complex layouts and layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing) — 레이아웃 비용, 스타일 쓰기 뒤 측정, read/write 반복 예시, DevTools 관찰 방법.

적용 조건: 실제 사용자 상호작용이 있는 웹 UI. 대표 기기·실사용 데이터 또는 재현 trace를 확보한다.

읽은 범위의 개념 참조이며 제품 코드·예제 실행, 접근성·보안·성능 검증 완료를 뜻하지 않는다.
