# React 파생 값·이벤트 처리와 Effect의 구분

검토일: 2026-09-22 · concept · public-contract

## 참고 상황

props·state에서 계산 가능한 값을 Effect로 다시 저장하거나 클릭 결과를 Effect가 뒤늦게 처리할 때. 이전 검색 응답이 최신 결과를 덮어쓰거나 외부 저장소 구독을 직접 구현할 때.

## 판단에 사용할 내용

렌더 계산·특정 사용자 이벤트·외부 시스템 동기화를 구분하고 상태 소유권, 구독과 요청 cleanup을 확인한다.

## 적용하지 않는 경우

네트워크·외부 위젯 동기화까지 일괄 제거하거나 모든 계산에 useMemo를 추가하지 않는다.

## 개념과 근거

원본 값에서 계산할 수 있는 값을 별도 state로 저장하면 Effect가 실행될 때까지 오래된 값이 보이고 추가 업데이트가 생길 수 있다. 필터된 목록·합성 이름 같은 순수 파생 값은 렌더 계산으로 표현할 수 있는지 본다.

특정 클릭·제출 때문에 수행하는 로직은 그 이벤트의 맥락에서 판단한다. 외부 시스템과 현재 UI를 맞추는 Effect는 유지할 이유가 있다. 비싼 순수 계산의 캐시는 측정과 실제 컴파일 환경을 확인한 뒤 검토한다.

상태 초기화는 유지할 범위부터 정한다. key 변경은 해당 하위 트리의 상태를 초기화한다. 선택 ID에서 항목을 계산하는 방식은 목록이 바뀔 때 선택을 무조건 지우는 방식과 다르다. 렌더 중 갱신 예제는 같은 컴포넌트의 상태와 반복을 막는 조건에 한정된다. DOM 변경 등 부수 효과를 렌더에 옮기는 근거가 아니다.

현재 query·page에 맞춘 요청은 외부 동기화다. 이전 요청의 늦은 응답을 cleanup으로 무시하면 최신 결과의 덮어쓰기를 막을 수 있지만 요청 자체를 취소하지는 않는다. 오류·로딩·캐시·서버 데이터 로딩은 별도로 필요하며, 프로젝트에 있는 프레임워크·데이터 계층의 기능부터 확인한다.

외부 저장소의 변경을 React에 연결할 때 useSyncExternalStore의 구독·snapshot 계약을 검토한다. 서버 snapshot은 실제 초기 렌더 조건과 맞아야 한다. 부모 알림이 사용자 이벤트에서 비롯됐다면 같은 이벤트에서 알리거나 상태 소유권을 상위로 모을 수 있다. 앱 초기화용 모듈 변수를 서버의 사용자별 상태 공유에 적용하지 않는다.
