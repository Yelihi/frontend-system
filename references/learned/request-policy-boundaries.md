# 요청·인증·오류 처리의 경계

## 참고 상황

여러 UI에서 fetch/HTTP 클라이언트를 호출하거나 인증·오류 처리·재시도 정책을 변경한다. 직접 호출의 존재만으로 문제가 확정되지는 않는다. 간접 호출과 이미 있는 클라이언트도 추적한다.

## 판단에 사용할 내용

- 기존 클라이언트와 Hook의 계약, 호출자와 오류 소비자를 확인한다. 같은 인증·오류 분류는 공유할 수 있지만 화면별 메시지와 업무 거절까지 공통화할 필요는 없다.
- 대안은 현 구조 유지, 기존 조회 계층 재사용, 필요한 요청 경계 추가다. 파일/Hook 개수나 Axios 도입 자체로 평가하지 않는다.
- 사용자에게 확인할 것은 정책의 공유 범위, 인증 계약, 변경될 업무 요구다. 이미 받은 답과 코드로 확인 가능한 사실을 다시 묻지 않는다.
- 부작용 요청의 재시도는 서버의 중복 방지 계약을 확인한다. 일괄 자동 재시도는 기본 선택이 아니다.
- 입력 객체·헤더의 소유권을 결정한다. 보존 계약을 선택했다면 실패 경로까지 변경되지 않는지 검사한다. 불필요한 깊은 복사를 강제하지 않는다.

## 적용하지 않는 경우

단일하고 단순한 요청이며 공유할 정책이 없거나, 기존 공용 클라이언트가 필요한 계약을 충족하면 새 계층을 추가하지 않는다. 서로 다른 인증 대상·재시도 의미를 같은 설정으로 묶지 않는다. 불확실한 도메인 의도는 코드 형태만으로 확정하지 않는다.

## 예시와 검증

정책이 같은 두 화면은 기존 request 함수 재사용을 검토한다. 결제 POST와 조회 GET의 재시도 요구가 다르면 정책을 분리한다. 기존 클라이언트가 이미 입력 보존과 오류 계약을 충족하면 유지한다.

선택한 경계에 대해서만 import 경로, 전송 옵션, 객체 입력 보존, 인증 만료, 업무 오류 전달, 실제 전송 횟수를 검사한다. AST 후보는 결함이나 의미 검증 완료가 아니다. 라이브러리별 동작은 프로젝트의 설치 버전과 공식 문서로 확인한다.

## 근거와 한계

`fs-request-boundaries` — 사용자와 합의한 FS 검토 지침을 정리했다. 조건부 설계 판단이며 모든 프로젝트의 최적 구조를 입증한 자료가 아니다.
