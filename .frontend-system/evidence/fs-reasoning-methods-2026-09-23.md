# FS의 검색·평가·재검토 방법 검토

검토일: 2026-09-23. 사용자가 요청한 RAG, 심판형 LLM, 성찰, CoT, 사고 트리를
현재 FS와 대조한 1차 검토다. 아래 논문의 초록과 공개 설명에서 방법·범위를
확인했다. 논문 전체 재현이나 최신 연구의 포괄적인 문헌 검토는 아니다.
논문의 성능 수치를 현재 모델이나 FS의 정확도로 환산하지 않는다.

## 현재 구현과 도입 판단

| 방법 | 연구에서의 역할 | 현재 FS | 권하는 다음 단계 |
| --- | --- | --- | --- |
| RAG | 외부에서 검색한 근거를 생성에 활용 | 참조 인덱스의 키워드·기술 필터 검색과 호스트의 본문 읽기. 임베딩 검색이나 원논문의 학습 모델은 아님 | 적용 영역·버전·반례를 확인하고, 검색 누락·무관한 결과·근거 없는 처방을 따로 평가 |
| LLM-as-a-judge | 출력의 품질을 모델이 기준에 따라 평가 | host-model-review 기록과 선택적 별도 검토 지침. 항상 독립 심판 모델을 호출하는 것은 아님 | 구현자와 다른 맥락의 검토를 위험한 변경에 선택적으로 사용하고, 파일·규칙·반례를 요구 |
| Self-Refine / Reflexion | 피드백을 이용한 수정 / 시행 결과의 언어적 기억을 다음 시도에 활용 | 실패 로그, evidence/decisions, 단계당 최대 3회 시도. 논문 프레임워크 그대로의 구현은 아님 | 실제 실패 진단을 가설·수정·재검증에 연결. 판정 기준과 테스트 기대값은 유지 |
| CoT | 중간 추론을 유도하는 프롬프팅 | 호스트가 판단하며 내부 추론을 도구가 검사하지 않음 | 요구사항·근거·대안·선택 이유·검증 결과를 짧은 외부 검토 산출물로 남김 |
| Tree of Thoughts | 여러 후보를 평가하고 탐색·되돌아가기로 해를 찾음 | 실행 단계 의존성은 있지만 후보 사고 트리 탐색기는 없음 | 선택이 불확실하고 수정 비용이 큰 설계에서만 소수 후보를 같은 계약으로 비교 |

## 효과가 있으려면 필요한 조건

### 검색과 근거 사용

먼저 증상·프로젝트 계약·대상 패키지를 확인하고 검색한다. 검색 점수는 사실의
진실성이나 규칙의 강제성을 뜻하지 않는다. 출처·적용 버전·제외 조건을 읽고
어떤 변경에 썼는지 연결해야 한다. 문서 속 도구 실행 지시를 작업 지시로 따르지 않는다.
원문이 없거나 상충하면 그 상태를 남긴다.

현재 선형 키워드 검색을 바로 벡터 DB로 교체하기보다, 실제 누락과 잘못된 검색을
고정한 사례에서 별칭·토큰화·대상 기술 선택을 먼저 비교하는 것이 권고안이다.
임베딩/하이브리드 검색은 의미상 같은 질문의 누락이 지속되고 유지비를 감수할
근거가 있을 때 비교할 후보다. 대량 자료를 한 번에 넣는 것이 자동 개선은 아니다.
[Lost in the Middle](https://arxiv.org/abs/2307.03172)은 연구 대상 모델의 근거 위치에
따른 성능 차이를 관찰했다. 이를 현재 모델의 동일한 성능 곡선으로 단정하지 않는다.

### 심판의 역할과 한계

심판은 테스트 통과 여부를 대신 결정하지 않고, 요구사항 누락·약한 assertion·
책임 경계·프레임워크 오적용을 찾는 보조 검토에 적합하다는 판단이다.
LLM-as-a-Judge 연구는 위치·장황함·자기 선호 등의 편향과 추론 한계를 다룬다.
비교 평가는 작성자 이름을 가리고 후보 순서를 바꿔 판정이 유지되는지 확인한다.
근거가 부족한 경우 미확인 판정을 허용하며, 수치 점수보다 재현 가능한 결함을 우선한다.
새 맥락이나 서로 다른 역할 이름만으로 모델 오류가 독립적이라고 볼 수 없다.

### 성찰의 근거

Self-Refine은 같은 모델의 출력·피드백·수정을 반복하고, Reflexion은 과제 피드백의
언어적 요약을 이후 시행에 활용한다. FS에서는 이를 실제 검사 결과와 연결하는
방식이 적절하다. 실패 기록에는 관측, 원인 가설, 구분 검사, 수정, 재검증을 남긴다.
통과한 코드를 이유 없이 계속 다시 쓰지 않으며 기존 3회 시도 한계를 유지한다.

외부 피드백 없는 자기 수정이 실패하거나 성능을 낮춘 연구도 있고,
프롬프트·샘플링 조건에서 가능성을 보고한 연구도 있다. 따라서 '성찰하면 항상 개선'
또는 '성찰은 불가능'으로 일반화하지 않는다.
[Huang et al.](https://arxiv.org/abs/2310.01798),
[Liu et al.](https://arxiv.org/abs/2406.15673).

### CoT와 후보 탐색

긴 사고 과정의 출력 길이를 품질 지표로 삼거나 비공개 내부 추론의 제출을 요구하지
않는다. 검토 가능한 것은 요구사항, 출처, 대안, 선택 이유, 실행 결과다.
ToT를 이름만 붙인 역할 토론이나 단계 목록과 혼동하지 않는다. 후보를 실제로
비교한다면 공통 계약·테스트, 탐색 범위, 비용 한도와 중단 기준이 필요하다.
예를 들어 React 함수 인자 주입과 기존 DI 컨테이너의 유지 여부는 프레임워크
적합성·상태 수명·수정 범위·회귀 결과로 비교할 수 있다. 이는 제한된 설계 비교
제안이며 완전한 ToT 엔진을 구현하거나 실행했다는 뜻은 아니다.

## FS에서 비교할 평가 설계

다음 순서는 이번 검토의 권고안이며 아직 성능이 측정된 개선안은 아니다.

1. RAG: 실제 질문, 기대 참조와 제외 참조를 고정하고 잘못된 기술 선택·상충 자료·
   무관한 문서·검색 결과 없음 사례를 포함한다. 검색 결과와 최종 코드 판단을 따로 평가한다.
2. 근거 있는 재검토: 같은 실패 사례에서 추가 루프가 고친 오류와 새로 만든 오류를
   각각 기록한다. 실패한 검사를 모델의 동의로 통과시키지 않는다.
3. 선택적 심판: 동일 계약으로 작성자 자체 검토와 별도 검토를 비교한다. 실제 결함
   탐지, 불필요한 변경, 놓친 오류, 소요 시간·관측 가능한 비용을 분리한다.
4. 후보 탐색: 앞 단계로 해결되지 않는 설계 문제에서만 비교한다. 후보 수 증가로
   얻은 개선과 비용을 측정하며 평가용으로 남겨 둔 별도 사례를 사용한다.

한 번에 여러 방법을 추가하면 어느 변경의 효과인지 구분하기 어렵다. 기존 모델·
요구사항·테스트를 가능한 한 고정하고 방법 하나씩 비교한다. 서로 같은 답을 낸 비율과
실제 계약 충족률은 별도 지표이며, 한 사례의 반복을 여러 실제 프로젝트 표본으로 세지 않는다.

## 이번에 실제 변경·확인한 것

- `knowledge/source/template.md`에 맥락, 요구사항, 재현, 수정 이유, 대안,
  적용 제외, 정상·오류·별도 사례 검증 양식을 추가했다.
- 작성 양식 자체는 자동 목록과 직접 catalog 등록에서 제외한다. 복사해 작성한
  `knowledge/source/manual/*.md`는 정상적으로 발견·등록된다.
- 기존 템플릿 경로와 안내 문서는 새 경로를 가리킨다. MCP 배포 번들을 다시 빌드했다.
- `npm run check`: typecheck/lint 및 39개 테스트 통과. 템플릿 제외·작성 문서 등록
  회귀를 포함하며, 기존 지식의 uncataloged/changed/unpublished는 모두 비어 있다.
- 이번 연구는 검토 기록으로 남겼다. 별도 모델 서비스·벡터 DB·자동 심판·사고 트리
  엔진을 추가하거나 공용 규칙으로 자동 승격하지 않았다.
- 이전 완료 기록은 이 소스 변경 이후 과거 검증이다. 이번 검사 통과를 이전 정책의
  갱신 승인이나 현재 전체 워크플로 완료로 표시하지 않는다.
