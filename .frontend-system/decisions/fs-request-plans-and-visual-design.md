# 요청별 계획과 시각적 프론트엔드 설계

- 결정일: 2026-09-29
- 결정자: 사용자
- 범위: FS 제품 방향. 정확한 저장 경로와 런타임 구현은 미승인 제안.

사용자는 모든 구현 작업이 fs-plan의 계획에 기반하고, plan 안에서 최소 작업 이슈를 순서대로 실행하도록 요구했다. 전체 리팩터링뿐 아니라 기능·복수 화면·로직 설계도 요청별 계획으로 보관한다. 이미지에서 도메인/비기능 요구·상태·서버/클라이언트·파일/함수 책임·테스트 방향을 논의하며, 필수 규칙을 우선 적용해 판단을 필요한 선택에 집중한다. 레이어·상태·조회 영향을 이벤트별로 시각적으로 보고 싶다는 요구도 명시했다.

계획 ID·승인 버전·이슈 ID로 구현 근거를 고정하는 방향을 초안에 반영했다. 작은 작업은 작은 계획으로 처리하고 같은 승인 질문을 반복하지 않는다. 요청별 경로는 .frontend-system/plans/<plan-id>/plan.md를 제안했으며, 현재 단일 revision/execution에 연결하는 런타임 변경은 수행하지 않았다.

선택한 시연 방식은 설치된 Archify의 책임 관계도와 이벤트 순서도 HTML이다. Mermaid는 Markdown 기반 대안이고 React Flow는 직접 편집하는 전용 도구가 필요할 때의 후보다. 이 도구 선택은 시연 제작을 위한 것이며 공용 필수 규칙이나 소비 프로젝트 의존성으로 확정하지 않았다.

결과물: docs/fs-direction-draft.md v0.4, docs/previews/price-screen.plan.md 및 연결된 두 도식. 입력은 실제 프로젝트 코드가 아닌 사용자의 과거 관계도이므로 Next.js·캐시·필터 전제는 미승인 가정으로 표시했다. 도식 생성과 브라우저 검증은 수행했지만 앱 구현 검증·토큰 절감 측정·모델 판단 개선율 측정은 수행하지 않았다.

재검토 조건: 실제 여러 계획 간 충돌, 문서와 실행의 불일치, 그림의 가독성 저하, 중요 요구를 이미지에서 잘못 추론한 사례. 검색 맥락: plan 중심 실행, 요청별 계획, issue, 화면 이미지, 상태 소유권, Server Component, 이벤트 시각화.
