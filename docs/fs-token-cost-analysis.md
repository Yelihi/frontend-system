# FS v5 토큰 비용 분석과 최적화

분석 대상은 [2026-10-04T161324](../test/evals/fs-comparison/v5/results/2026-10-04T161324/analysis.md)이다. 주요 FS 절차와 보호 장치는 실행됐지만, 도구 오류 3회와 큰 기록 비용이 있었다. 같은 확정 계약의 구현은 일반 AI와 FS가 모두 14/14였고 제품 파일 7개가 동일했다. 따라서 이번 결과를 “FS가 품질과 효율 모두 잘 작동한다”로 표현하지 않는다.

## 확정할 수 있는 토큰 차이

| 누적 사용량 | 일반 AI | FS | 증가분 |
| --- | ---: | ---: | ---: |
| 캐시 입력 | 215,168 | 1,812,608 | 1,597,440 |
| 비캐시 입력 | 38,774 | 80,754 | 41,980 |
| 출력 | 6,431 | 17,441 | 11,010 |
| 총 처리 | 260,373 | 1,910,803 | 1,650,430 |

**추가 처리 토큰의 96.79%는 캐시 입력 증가분**이다. 이는 도구가 한 번에 190만 토큰을 반환했다는 뜻이 아니라, 큰 대화 문맥을 여러 모델 처리에 걸쳐 입력으로 다시 계산한 누적 사용량이다. 비캐시 입력도 2.08배이고 출력도 2.71배이므로 캐시만으로 비용 차이를 설명하거나 무시할 수 없다. 총 토큰 배수는 청구 금액 배수가 아니다.

준비는 일반 71,515 / FS 432,271토큰, 구현은 일반 188,858 / FS 1,478,532토큰이었다. FS 구현 단계가 전체 FS 처리량의 약 77.4%다. 준비 시 쌓인 문맥을 구현 단계에 이어받으므로 구현 단계의 추가 토큰 전부를 제품 코드 작성에 쓴 것으로 해석하지 않는다.

원자료에는 단계별 usage가 있고 개별 추론 호출의 세부 토큰 귀속은 없다. 따라서 도구 A가 정확히 몇 토큰 또는 몇 초를 추가했는지는 확정하지 못한다. 도구 호출 수·입출력 문자 수를 토큰으로 환산하거나 특정 오류를 제거하면 총 토큰이 몇 % 줄어든다고 추정하지 않는다.

## 실제 로그에서 보이는 비용 경로

| 도구 로그의 완료 이벤트 | 일반 AI | FS |
| --- | ---: | ---: |
| 셸 명령 | 21 | 30 |
| MCP 호출 | 0 | 35 |
| MCP 실패 | 0 | 3 |
| 명령·MCP 인자 문자 합계 | 1,997 | 53,572 |
| 명령·MCP 결과 문자 합계 | 27,892 | 183,259 |

문자 수는 기록된 명령·MCP JSON을 공백 없는 형태로 재집계한 값이다. 모델 메시지, 파일 변경 이벤트, 숨겨진 시스템 문맥/도구 스키마를 포함하지 않는다. 완료 이벤트 수는 추론 호출 수와 같지 않다. [재현 스크립트](../test/evals/fs-comparison/v5/token-audit.mjs)와 [세부 집계](../test/evals/fs-comparison/v5/validation/token-audit.json)에 집계 범위를 고정했다.

확인된 비용 경로는 다음과 같다.

1. **문서·소스의 중복 열람.** 준비에서 스킬 2개, 워크플로 문서, 여러 지식 본문을 읽었다. 제품 소스를 셸로 읽은 뒤 main 근거를 위해 read_project_source 11회로 다시 읽었다. 공식 근거는 필요하지만 같은 main 본문을 두 방식으로 연속 읽어야 할 이유는 없다.
2. **계획을 편집하기 위해 전체 기록을 다시 전달.** get_revision 3회 중 2회는 full이었다. 실제 필요는 Q1/Q2 결정의 갱신과 누락된 knowledgeIds 연결 보정인데, raw routing, 계획 본문, 정책, 작업 목록까지 돌아왔다. save_revision은 5회이며 변하지 않은 필드도 반복 작성했다.
3. **기계적인 기록 오류.** 검증 enum에 여러 유형을 이어 적은 오류, 현재 후보에 없는 이전 ID 5개의 혼입, apply한 지식의 결정 연결 누락이었다. 각각 실패 응답뿐 아니라 수정 요청과 누적 문맥 재처리가 뒤따랐다. 이 세 오류가 추가 비용의 전부라는 뜻은 아니다.
4. **검사와 상태 확인의 중복.** 셸 npm test/build 후 완료 증거를 위해 도구 delivery 검사를 다시 실행했고, 마지막 완료 확인에 get_work_context를 써 새 지식 라우팅까지 했다. 개발 중 표적 검사는 유지하되, 최종 검사부터 기록 도구로 실행하면 중복 실행을 피할 수 있다.
5. **추가 도구 정의의 문맥 가능성.** 수정 후 로컬 MCP는 43개 도구, 선언 JSON 55,015자를 노출하며 save_revision이 13,090자다. 이 숫자는 현재 도구 목록의 크기다. 당시 모델 제공자에게 어떤 스키마가 주입됐는지 기록이 없으므로 이를 실제 입력 토큰으로 귀속하지 않았다. 도구 수만 줄이면 비용 문제가 해결된다는 결론도 내리지 않는다.

## 반영한 최적화

| 변경 | 지키는 조건 |
| --- | --- |
| get_revision의 decisions 보기 | 결정·인용·판단은 그대로 반환하고 raw inspection·중복 계획/정책을 제외. 원문 조회는 계속 가능 |
| save_revision의 변경되지 않은 content/policy/issues 생략 | 정확한 expectedHash로 기존 필드 유지. 새 계획은 content 필수, 모든 저장은 승인 무효화 |
| 저장 영수증에 contractDiagnostics 추가 | 기존 승인 검사와 같은 계약 연결 함수를 사용. 선택·검사 연결 오류를 일찍 알리되 승인·최신성 확인을 대신하지 않음 |
| get_work_context에 candidateChanges 추가 | 이전 전체 경로와 현재 경로의 ID 차이를 표시. 다른 범위의 후보를 자동 삭제하거나 이전 판단을 자동 채택하지 않음 |
| verification enum의 조합 방법 명시 | tests + review는 behavior-test와 checks/reviews 연결로 표현. 새로운 임의 enum을 허용하지 않음 |
| 지시문에서 중복 절차 제거 | 선택된 planId 재사용, main 소스 직접 열람, 필요한 참조만 읽기, 최종 검사를 도구로 기록, 완료 확인에는 workflow 조회 |

계약 연결 검사는 부작용 없는 `design-contract.ts`로 분리해 저장 응답과 승인 경로가 같은 판단을 사용하도록 했다. 파일/지식/문서 freshness와 검사 자산 보호는 기존 승인 경로가 계속 검사한다. 새 도구를 늘리지 않았으며 기존 입력과 조회 형식도 유지한다.

## 검증 범위

과거 로그는 데이터로만 읽었다. 모델이 작성한 코드·명령은 호스트에서 실행하지 않았다. 원본 점수·사용량도 변경하지 않았다.

| 재구성 비교 | 이전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 결정 편집용 조회 1 | 14,793자 | 5,935자 | 59.9% |
| 결정 편집용 조회 2 | 14,673자 | 5,581자 | 62.0% |
| 같은 정책 생략 요청 1 | 8,792자 | 7,763자 | 11.7% |
| 같은 정책 생략 요청 2 | 7,481자 | 6,452자 | 13.8% |
| 같은 본문·정책·작업 생략 | 7,527자 | 4,379자 | 41.8% |

요청/응답의 역할이 맞는 경우에만 가능한 **조건부 문자 수 비교**다. 결정과 인용, 수정한 필드와 expectedHash가 보존되는지 검사했다. 새로운 진단 필드의 크기도 포함한다. 총 모델 토큰 감소율, 재시도 제거 횟수, CPU 절감률로 해석하지 않는다.

타입·린트·회귀 70개, 기존 실행기 v4 7개와 v5 3개, 독립 패키지 검사를 확인했다. 회귀 검사는 본문 생략 시 정책·작업·결정 보존, 새 계획의 본문 필수, 오래된 expectedHash 거절, 승인 무효화, 변경된 소스의 승인 차단을 다룬다. 실제 MCP를 통한 생략 저장과 decisions 조회도 검사한다. skill-creator의 Python 검사기는 기존 환경의 PyYAML 부재로 사용할 수 없어 변경하지 않은 frontmatter 형식과 문서 연결은 별도로 확인한다.

**당시에는 새 실제 모델 비교가 없었다.** 이후 실제 결과는 아래 반복 비교 절에 기록했다. 다음 비용 비교는 현재 v5의 같은 시작 코드·계약·600초 제한을 유지해야 한다. 프로젝트 규모를 동시에 바꾸면 이번 최적화의 효과와 과제 차이를 분리할 수 없다.

## pstack 참고가 도움 된 부분과 입증하지 못한 부분

대상과 파일별 근거는 [pstack 검토](pstack-review.md)에 고정돼 있다. pstack 코드·스크립트나 라우터를 복사한 것이 아니라 기존 FS의 구조와 지시문에 필요한 방식을 반영했다.

- architect의 **호출 예시에서 인터페이스·소유권을 정하는 방식**은 실제 FS 계획에 caller→client→repository→controller, 공개 계약과 소유자를 기록하는 데 반영됐다. 다만 같은 설계가 일반 AI에도 제공되어 제품 차이를 만들었다는 증거는 없다.
- **반복된 오류를 구조로 막는 방식**은 open/resolved 입력 구분과 반례 검증에 참고가 됐다. 이번에는 selected:null 누락 오류가 없었지만 다른 기록 오류는 남았다. 이번 후속 수정은 그 오류를 조기에 진단하는 데 집중했다.
- **증거와 추정 구분, 검증 범위 명시**는 지식 검토와 보고에 반영됐다. 같은 수준의 근거 보호 상당 부분은 기존 FS에도 있었으므로 pstack만의 새 성능 기여로 계산하지 않는다.
- 자연스러운 평가 프롬프트와 고정 교정 사례는 평가 절차에 반영됐다. FS가 더 좋은 코드를 만들거나 더 적은 토큰을 쓴다는 결과는 아니다. 다중 모델, 자동 승인, 별도 PR 오케스트레이터는 채택하지 않았다.

큰 프로젝트에서 분석·사용자 결정·검증 정책을 여러 작업에 재사용하는 가치는 측정할 여지가 있다. 반대로 현 구조의 재열람과 기록이 프로젝트 크기에 비례해 늘 수도 있다. 따라서 큰 프로젝트가 해결책이라고 가정하지 않고, 동일 프로젝트의 초기 분석 비용과 반복 변경의 누적 비용을 분리해서 봐야 한다.

## 수정 전 재검토: project.md 재사용 설계와 당시 구현의 차이

사용자가 의도한 것은 최초 분석을 저장하고 이후 요청에서 관련 사실·트리거·지식을 재사용하는 구조다. 이 방향 자체에 문제가 있는 것은 아니다. 아래는 후속 구현 전의 진단이며, 실제 반영 범위는 이 문서 마지막의 후속 구현 기록에 구분한다.

- `project.md`는 코드 인용·파일별 coverage와 연결된 설명서다. `validateProjectEvidence`가 파일 누락과 인용을 검사하지만, 프로젝트의 모든 의미와 관계를 완전히 해석했음을 보증하지 않는다.
- `task-context.ts`는 문서와 해시를 읽지만 `routeKnowledge`의 입력은 요청문, 지정 코드 파일, 요구 문서, 호스트 interpretations다. 저장된 프로젝트 진술을 검색해 관련 트리거의 첫 입력으로 삼는 영속 분석 인덱스는 구현돼 있지 않다. 문서를 읽은 모델이 observations/interpretations로 전달하는 경로는 가능하지만 자동 사실 검색과는 다르다.
- `analysis-receipts.ts`의 contextId는 프로세스 메모리의 최대 32개 영수증이며 서버 재시작 후 재발급한다. 저장된 계획의 근거 자체는 남지만, 영수증은 재사용 가능한 프로젝트 의미 모델이 아니다. knownContextId도 최신 라우팅을 계산한 뒤 같은 메타데이터의 재전송을 생략하는 기능이다.
- main 설명과 작업 브랜치는 서로 다른 버전이다. 작업 중인 파일을 전혀 다시 읽지 않으면 사용자의 변경이나 오래된 설명을 놓칠 수 있다. 필요한 버전 확인을 프로그램이 하는 것과, 같은 본문 전체를 모델에게 다시 전달하는 것은 구분해야 한다. 파일을 읽어 해시만 비교하는 일은 그 자체로 모델 입력 토큰이 아니다.

따라서 후속 구조 개선은 “처음 한 번 읽었으니 이후 코드는 읽지 않는다”가 아니라, **버전에 묶인 분석 사실을 저장하고 변경·요청 범위에 관련된 사실과 근거만 가져오는 것**이어야 한다. 설명서는 그 사실의 사람이 읽는 표현으로 유지할 수 있다. 변경 파일뿐 아니라 관련 설정·의존 관계·사용자 결정·지식 버전도 무효화 판단에 필요하다. 현재 반영한 조회/입력 축소를 이 영속 분석 인덱스까지 구현한 것으로 설명하지 않는다.

## pstack의 기술적 재사용: 확인한 구현과 적용 범위

동일한 pinned commit `e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a`의 `skills/poteto-mode/scripts/orch/store.ts`, `orch.ts`, `playbooks/orchestrate.md`를 다시 확인했다. 여기서 확인한 것은 장기 작업 조정용 상태 저장이며, 모든 pstack 작업에 쓰이는 프로젝트 AST/의미 캐시는 아니다.

| 실제 구현 | 기능 | FS에 참고할 부분 |
| --- | --- | --- |
| store.ts의 units.set | ID로 기존 행을 찾고 지정한 state/branch/PR/SHA만 변경, 나머지는 보존 | 모델이 전체 상태를 다시 작성하지 않아도 되게 할 것 |
| store.ts의 gates.resolve | ID와 answer를 받아 기존 question/options를 보존하며 결정 상태 전환 | 결정 변경을 작은 명령으로 표현. 사용자 승인·선택 검증은 FS 기준 유지 |
| store.ts의 status.render | units/ledger/frontier/gates로 status.md를 생성하고 이전 summary와 비교 | 원본 상태와 설명을 따로 수작업으로 유지하지 않을 것 |
| store.ts의 ledger.check | PR+SHA와 일치하는 검증 행이 없으면 NOT-VERIFIED | 확인 범위를 버전에 묶고 오래된 결과를 성공으로 재사용하지 않을 것 |

`orchestrate.md`도 overview 전체 재작성 금지, 작업 크기에 맞는 간단한 brief, 저장 상태에서 요약 생성 등을 지시한다. 반면 필요한 standing orders는 resume에 재전달하고 큰 범위의 작업에는 상당한 검증 절차를 둔다. pstack이 무조건 적게 읽거나 자동으로 의미적 영향 범위를 계산하는 것으로 해석해서는 안 된다. ledger 기록 역시 보고된 verdict/evidence를 저장하는 것이며 저장 자체가 실행 결과의 진실을 검증하지는 않는다.

전체 재검토가 필요한 경우는 유지해야 한다. 인증 정책처럼 여러 호출자에 영향을 주는 결정은 관련 경계를 넓게 확인해야 한다. 단순 연결 ID 보정에는 기존 승인 근거, 변경 내용, 관련 연결만으로 충분한지 판단할 수 있다. 둘을 구분하는 기준은 읽은 양이 아니라 변경 영향이다.

세 MCP 오류는 제품 실행 오류가 아니라 FS 관리 인터페이스에서 발생했다. 일반 AI 조건은 이 도구를 호출하지 않아 같은 종류의 오류를 낼 기회가 없다. 공통 제품 검사는 양쪽 모두 14/14였다. 보호 장치가 잘못된 기록을 거절한 점과, 호스트가 수작업으로 기록을 맞추느라 생긴 마찰을 동시에 개선 대상으로 본다.

### 도움말 버전 재현 결과와 검증 로그 보완

202328은 201059와 manifest 전체가 동일하지만 FS가 3,174,514토큰·620.662초를 사용했다. MCP 오류는 0건이고 도움말은 사용하지 않았다. 두 회차 평균 FS는 2,545,621토큰, 일반 AI는 328,855토큰으로 7.74배다. 과거 161324 대비 FS 평균 토큰은 33.2% 증가했다. 따라서 입력 오류 감소와 전체 비용 감소는 다른 문제다.

202328에서는 브라우저 OS 권한 실패 이후 대체 SSR 번들의 util 로드 오류가 발생했다. 실패 이벤트에는 data-URL 번들을 포함한 1,048,570문자 로그가 남았다. 실제 모델에 전체가 전달됐는지는 확정하지 않는다. 오류를 수정한 뒤 delivery 통과 후에도 UI 테스트를 보강하여 다시 검사했다. 제품 점수는 같아도 검증 코드 작성·환경 복구·출력 처리·재검증에서 비용 차이가 발생한다.

이에 검사 실패 요약을 끝부분만 2,000문자에서 앞·뒤 합계 최대 2,000문자로 바꿨다. 같은 오류 형태의 회귀에서 원인 메시지와 마지막 실패 표식이 남고, 실패 상태와 원본 로그가 유지되며 페이지 조회로 전체가 복원되는지 실제 MCP로 검사했다. 요약이 모든 오류를 찾는다고 보장하지 않으며, 부족하면 원본의 필요한 창을 읽는다. 스킬은 개발 검사에도 이 도구를 사용하고 테스트 개발·리뷰 후 최종 delivery를 실행하도록 연결했다. 일반 셸 전체를 가로채는 기능이나 테스트 생략은 아니다. 타입·린트·78개 테스트와 독립 패키지 검사를 통과했고 204033에서 같은 조건의 실측을 진행한다.

실패 횟수는 성격을 구분한다. 외부 수정 호출 0회는 모델이 내부에서 한 번도 고치지 않았다는 뜻이 아니다. MCP 입력 오류, 브라우저 권한 실패, 작성한 테스트 자체의 오류, 수정 전 기존 결함을 재현하는 의도된 테스트 실패는 서로 다르다. rg의 검색 결과 없음도 종료 코드 1이므로 셸 실패 이벤트 수를 그대로 코드 결함 수로 바꾸지 않는다. 204033의 일반 AI는 테스트를 먼저 작성해 기존 계약 위반을 재현한 뒤 구현을 수정했다. 이 의도된 실패를 일반 AI의 새 구현 오류로 집계하지 않는다.

204033 결과는 일반 AI 425,027토큰·205.710초, FS 2,666,706토큰·582.529초, 양쪽 최초 외부 14/14다. FS의 MCP 입력 오류는 0건이다. 개발 테스트 4회는 모두 MCP 경로를 사용했고 delivery는 1회였다. 브라우저 실패 원문 8,867문자가 2,000문자 요약으로 전달됐고 원본은 유지됐다. 이후 대체 UI 테스트의 null.type 오류를 수정했다. 재사용 등록 3개/발동 합계 6회, 새 답변 부분 수정 1/1도 성공했다.

그러나 전체 토큰은 일반 AI 대비 6.27배, 비캐시 입력 2.46배, 시간 2.83배다. 과거 FS 161324 대비 총 토큰 39.6% 증가, 시간 12.3% 감소다. 도움말 12회/31,182문자, FS 셸 명령 완료 이벤트 30개와 MCP 25개가 관측됐다. 일반 AI의 셸 명령은 20개다. FS 추가 토큰의 96.45%는 캐시 입력 증가분이며 비캐시 입력도 더 많다. 어떤 문서/도구가 정확히 얼마의 모델 토큰을 유발했는지는 공개 로그로 분해할 수 없다.

**8쌍의 직접 비교에서 기능 연결·오류 복구 경로는 보완했지만 비용 절감 목표는 달성하지 못했다.** 작은 같은 계약 구현에서 FS의 기록·규격 조회·검증 절차가 추가 문맥 처리를 유발한다. 현재 지표에서 그 비용을 상쇄하는 코드 품질·외부 수정 횟수 이득은 없다. 단순 지시문 추가나 우연히 좋은 회차 선택을 성과로 보고하지 않는다. 향후 구조 변경은 모델이 반복 작성하는 기록을 서버가 어디까지 파생할지, 필요한 검증의 실행 환경을 어떻게 준비할지 별도 가설로 검증해야 하며 이번 결과는 그대로 유지한다.
