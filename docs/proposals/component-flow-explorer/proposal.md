# 화면에서 읽는 FS 설계 — 논의용 시안

이 문서는 사용자가 제안한 화면·컴포넌트 이미지 위의 이벤트 흐름을 구체화하기 위한
제안이다. 실제 프로젝트의 분석 결과나 승인된 구현 계약이 아니다. 기존 FS의
스키마·MCP·배포 버전은 변경하지 않았다.

## 확인할 시안

`preview.html`을 브라우저에서 연다. 외부 CDN이나 네트워크 API 없이 동작한다.

- 검색 페이지: 입력, 자동완성, 반복 카드, 결과 wrapper, 페이지네이션, 컬렉션 미리보기.
- 컬렉션 페이지: 안정된 항목 ID, 표시 순서, 저장 상태, 공유 cache, 서버와 DB.
- 시나리오: 순서 변경 성공 / 실패 후 복구 / 검색의 늦은 응답 무시.
- hover는 임시 정보, 클릭은 선택 고정. 키보드로도 컴포넌트 영역을 선택한다.
- 이전·다음·단계 버튼과 자동 재생으로 화면/화살표/관련 상태 값을 함께 바꾼다.
- 같은 `ResourceCard` 정의의 `card-a`, `card-b`, `card-c`를 별도로 선택한다.
- `전체 영향 지도`에서 두 페이지와 공유 store/cache를 함께 본다. 빈 영역 드래그·휠로
  이동하고 Ctrl/⌘+휠이나 확대/축소 버튼으로 배율을 바꾼다. 키보드 방향키, +/−, Home도 지원한다.
- 오른쪽은 이미지 없이 interface, state, handler, lifecycle, props, framework/hooks를 보여준다.
- 전체 지도와 페이지 버튼은 하나만 선택된다. 전체 지도는 페이지를 브라우저 프레임으로
  감싸고 콘텐츠와 오른쪽 브라우저 기능 영역을 분리한다. 앱 상태·모듈은 페이지 아래의
  콘텐츠 영역에, 브라우저 API·저장소는 측면에, 백엔드·외부 서비스는 바깥 열에 배치한다.
  전체 자료를 유지하면서 현재 단계의 관계만 강조한다.

실제 프로젝트 적용 시험: [주문 예제 화면](observed/preview.html),
[fs-project 보고서](observed/project.md), [자료구조와 결과](observed/proposal.md).

이미지는 AI 생성물이 아니라 동일한 HTML 시안의 상태별 브라우저 캡처다. 페이지 이미지의
영역을 컴포넌트 선택에 사용한다. 실제 목록 drag/drop, 네트워크, DB 동작은 없으며
표시되는 변경 값은 작성된 시나리오다. 시안의 목적은 표현 방식과 정보 구조를 평가하는 것이다.

## 먼저 분리해야 하는 네 가지

| 데이터 | 답하는 질문 | 현재 FS와의 관계 |
|---|---|---|
| 의미 그래프 | 어떤 컴포넌트·함수·store·cache가 무엇을 소유하고 호출하는가? | 기존 `nodes`, `edges`, `contracts`, `evidence`를 유지 |
| 화면 인스턴스 트리 | 그 정의가 어느 페이지의 어느 항목으로 나타나는가? | `instances`로 정의 ID, 부모 인스턴스, entity key를 연결 |
| 화면 상태와 이미지 | 어떤 viewport·상태·테마의 어느 영역인가? | 기존 `design.screens`/`regions` 확장 후보 |
| 사건 시나리오 | 어떤 계기로 어디가 변하고 실패하면 어떻게 되는가? | 기존 `scenarios.steps`에 상태 변화와 화면 참조 연결 |

한 트리에 호출, 렌더링 포함 관계, cache 공유를 모두 담으면 순환 관계와 반복
인스턴스가 꼬인다. 포함 관계는 트리, 행동 관계는 그래프, 시간 순서는 시나리오로
두고 ID로 연결한다. 화면 좌표는 의미 그래프에 넣지 않는다.

비화면 노드의 `environment`는 `app`, `backend`, `external` 중 하나이며 코드 근거나
설계 의도로 지정한다. `browserApis`는 이름·소유 노드·사용 내용을 연결한다. 현재 시안은
AbortController, 실제 주문 예제는 fetch를 기록했다. IndexedDB·Storage·Events는 측면 영역의
분류이며 사용하지 않는 기능을 노드로 생성하지 않는다. 브라우저 프레임은 논리적 실행 경계다.
탭과 운영체제 프로세스가 일대일이라는 주장이나 브라우저 내부 구현 도식은 아니다.

`layout.mjs`가 페이지 수와 자원 수로 열과 높이를 계산한다. 좌표를 임의로 흩뿌리지 않고
페이지·내부 자원·외부 자원을 정렬한다. 같은 입력의 배치가 같으며 자원이 늘면 영역 높이를 늘린다.

## 많은 페이지를 위한 다음 설계 — 아직 미구현

현재 시안은 소수 페이지를 펼친다. 많은 페이지를 같은 크기의 이미지로 전부 펼치면
축소 시 읽기 어렵고 관계선도 겹친다. 다음 세 가지 보기를 같은 자료의 투영으로 제안한다.

| 보기 | 표시 내용 | 진입 방식 |
|---|---|---|
| 프로젝트 개요 | 도메인/라우트 그룹과 공유 자원의 작은 노드 | 프로젝트 열기, 도메인/라우트 검색 |
| 도메인 흐름 | 선택한 이벤트의 출발·변경·소비 페이지와 대표 상태 화면 | 이벤트 선택, 영향받는 페이지 펼치기 |
| 페이지 상세 | 컴포넌트, 인자, 상태 변화, 코드 근거 | 페이지 또는 컴포넌트 선택 |

`/users/[id]`와 같은 라우트는 한 정의와 대표 사례로 관리한다. 실제 엔티티 ID마다
페이지를 생성하지 않는다. 흐름 보기에서는 직접 연결된 화면을 먼저 펼치고 추가 소비자는
개수와 펼칠 수 있는 목록으로 남긴다. 화면 밖이라 생략된 관계와 아직 조사하지 못한
관계는 구별한다. 렌더 순서를 모르는 소비자에게 임의의 순번을 부여하지 않는다.

앱 상태·모듈과 브라우저 기능도 선택한 흐름과 관련된 자원을 먼저 보여주되 전체 자원 검색으로 확장한다.
처음에 개요 인덱스만 읽고 상세 그래프·캡처는 선택 시 불러온다. 안정된 ID와 고정된
flow hash를 유지하므로 화면 선택 때문에 AI가 프로젝트를 다시 해석할 필요는 없다.
실제 캡처는 대표 상태부터 수집하며 모든 페이지·상태 조합을 미리 생성하지 않는다.

다음 검증은 수십 개 라우트에서 알려진 교차 페이지 소비자를 놓치지 않는지,
접힌 영향 목록을 펼쳐 정확한 화면/상태로 갈 수 있는지, 초기 로딩 크기와 탐색 지연을
측정하는 것이다. 현재 8페이지 배치 계산 검사는 이 사용성·성능 검증을 대신하지 않는다.

라우트 탐색의 hover는 인접한 이동 경로와 조건을 잠깐 강조하고 클릭하면 선택을 고정하는
방향으로 제안한다. 키보드 focus도 같은 미리보기를 제공한다. 로그인 예에서는 인증됨,
미인증→로그인, 성공 후 복귀, 실패 후 잔류를 구별하되 실제 코드/계획에 있는 경로만 표현한다.
전체 연쇄를 hover만으로 자동 재생하거나 상세 화면을 매번 로딩하지 않는다. 깊은 분기는
클릭한 뒤 단계별로 탐색한다. 현재 시안에는 도메인별 라우트 노드, 인접 경로 hover/focus,
클릭 고정과 페이지 상세 흐름 진입을 구현했다. 대규모 인덱스 검색·지연 로딩은 아직 적용하지 않았다.

`spec.json`은 이 원리를 확인하는 작은 논의용 데이터이며 FS에 바로 저장되는 payload가
아니다. 실 스키마에서는 시나리오마다 from/to를 복제하기보다 기존 edge ID를 참조한다.

```ts
// 도입 검토용 구조. 아직 FS의 공개 타입이 아니다.
type ComponentInstance = {
  id: string;                  // card-c: 화면의 개별 항목
  nodeId: string;              // 기존 의미 그래프의 컴포넌트 노드
  parentInstanceId?: string;   // results-1: wrapper 내부
  entityKey?: string;          // c: 위치와 무관한 도메인 식별자
};

type ScreenState = {
  id: string;                  // collection.optimistic.desktop
  pageId: string;
  stateId: string;
  viewport: { width: number; height: number };
  asset: { path: string; hash: string };
  regions: Array<{
    instanceId: string;
    rect: [number, number, number, number]; // 0..1 이미지 좌표
  }>;
};

type ScenarioStep = {
  edgeId: string;              // FS의 기존 호출/쓰기/구독 edge
  fromInstanceId?: string;
  toInstanceId?: string;
  screenStateIds: string[];    // 여러 페이지가 영향받을 수 있음
  changes: Array<{
    ownerNodeId: string;
    field: string;
    before: unknown;
    after: unknown;
  }>;
  guard?: string;
};
```

여러 소비자가 같은 변경을 받는 단계는 `effects` 배열과 `ordering: 'unordered-consumers'`로
표현한다. 이번 순서 변경/복구 시나리오에서는 `collectionQueryCache`에서
`sortable-list-1`과 `preview-1`로 두 화살표가 갈라진다. 소비자 간 선후관계나 실제
렌더 완료 시각은 주장하지 않는다. 비동기 합류·취소·조건 분기까지 다룰 실 스키마에는
단계 간 의존 관계가 필요하지만, 이번 시안은 순차 단계 안의 다중 전파까지만 구현했다.

`framework`에는 실행 환경, hooks, 판단 근거를 둔다. 현재 값은 모두 설계 가정이다.
실 프로젝트의 Client/Server 경계는 화면의 부모 관계만 보고 정할 수 없다.
[`use client`는 모듈 의존 관계에 경계를 만든다](https://react.dev/reference/rsc/use-client).
따라서 directive와 import 경로를 확인하고, 불명확한 경우 미확인 상태를 보존해야 한다.

컴포넌트 정의가 여러 페이지에서 쓰이는 경우 화면별 역할 노드를 하나로 합치지 않는다.
실제 코드 symbol/path를 공통 정의 참조로 재사용하되 페이지별 인스턴스·props·소유권은
유지해야 한다. 가상화된 목록의 화면 밖 항목이나 portal도 실제 포함 관계와 DOM 위치를
혼동하면 안 된다. 첫 적용에서는 선택된 대표 인스턴스만 기록하고 나머지는 범위로 표시한다.

## 이미지와 구조가 서로 어긋나지 않게 만드는 방법

1. 기존 화면은 허용된 로컬 실행 환경에서 해당 상태를 캡처한다. 신규 설계는 HTML
   시안 또는 제공된 디자인에서 시작한다. 테마 기반 AI 이미지도 별도 입력으로 받을 수 있다.
2. 페이지 전체와 컴포넌트를 독립적으로 매번 생성하지 않는다. 같은 시안의 컴포넌트
   상태를 캡처하거나 전체 이미지의 영역을 사용한다. 필요한 경우에만 독립 변형을 만든다.
3. DOM의 측정 영역은 위치의 근거이고, AST/코드 인용은 책임과 호출의 근거다.
   DOM만으로 React/Vue/Svelte의 실제 컴포넌트 경계가 증명되지는 않는다.
4. AI 생성 이미지는 DOM이 없으므로 영역 매핑을 따로 확인한다. 매핑된 사각형이
   실제 코드 컴포넌트라는 주장은 코드/사용자 설계 근거가 있을 때만 한다.
5. 이미지·viewport·상태·매핑의 버전을 함께 고정한다. 이미지나 레이아웃이 바뀌면
   기존 영역을 자동으로 유효하다고 취급하지 않는다. 이 시안도 template/spec hash가
   바뀌면 이전 캡처를 거부한다.

Storybook과 비슷하게 컴포넌트 정의 + props/상태별 사례 + 페이지 조합을 분리하되,
이미 Storybook이 있는 프로젝트는 기존 사례를 재사용하는 방향이 적합하다.
Storybook 설치나 React 전용 해석을 필수로 만들지는 않는다.

## 드래그 예시에서 실제로 논의할 설계

“클라이언트가 순서를 처리한다”만으로는 충분하지 않다. 시안에서는 다음을 **가정**했다.

- `id`는 항목의 정체성이다. 순서를 바꿔도 a/b/c를 다시 발급하지 않는다.
- 클라이언트는 `[a,b,c] → [c,a,b]`를 계산하고 공유 cache에 낙관적으로 반영한다.
- 서버는 권한·ID 집합·expectedVersion을 확인하고 영속 순서를 원자적으로 확정한다.
- 저장 중 추가 이동은 잠근다. 실패 시 같은 mutation의 이전 순서로 복구한다.
- 두 페이지는 같은 cache를 구독한다. 화면별 복제 state를 따로 동기화하지 않는다.

이는 정답이 아니라 작은 시연을 위한 선택이다. 대량 목록, 부분 로딩, 동시 편집이 있으면
전체 ID 배열 전송 대신 위치 키, 이동 명령, 충돌 병합 등을 비교해야 한다.
전송 후 응답만 유실된 경우는 단순 rollback으로 해결되지 않는다. 서버 저장 전 실패와
구분해 재조회/중복 요청 처리 정책을 논의해야 하며 이번 시나리오는 이를 구현하지 않는다.

## 렌더러와 토큰 비용

이번 구현은 HTML 이미지 + 선택 영역 + SVG 연결선 + CSS transform 카메라다.
여러 페이지의 동시 비교·pan/zoom에 새 라이브러리를 추가하지 않았다. 확대·이동·단계
재생은 브라우저 코드로 실행하며 모델을 호출하지 않는다. 자유 드로잉·3D 회전은 구현하지 않았다.

같은 spec·렌더러·캡처 자산이면 같은 HTML을 생성한다. 이것이 AI의 코드 해석까지
결정적이거나 정확하다는 뜻은 아니다. 현재 캡처 무효화는 전체 template hash 기준이므로
지도 UI만 변경해도 재캡처가 필요하다. 실제 도입 시 화면 렌더링 입력만 따로 해시할 수 있다.

AI에는 기존 의미 그래프와 선택한 시나리오의 계약/변경만 전달한다. PNG/base64, 좌표,
전체 HTML은 기본 코드 해석 문맥에 넣지 않는다. 사람용 viewer가 그 데이터를 조합한다.
“토큰을 절감했다”는 주장은 아직 하지 않는다. 실 프로젝트에서 같은 설계 질문을 해결할 때
재조회·이미지 생성 횟수와 사용량을 측정해야 한다.

## fs-project에서 전체 프로젝트를 보여주려면

현재 fs-project도 포함된 관측 흐름마다 HTML을 자동 생성한다. 이번과 같은 페이지 이미지
통합 지도는 0.8.0부터 보조 렌더러와 skill 절차로 제공한다. 기본 MCP 출력에 자동 합성하는 것은 아니다. 기존 정적 분석은 제한된 구문·호출·콜백 관계를 추출하고,
AI가 근거를 연결한 흐름 기록을 작성한다. 전체 도메인을 완전히 추출하는 기능은 아니다.

| 단계 | 만드는 자료 | 비용과 한계 |
|---|---|---|
| 정적 수집 | 파일/import, 선언, hooks, 알려진 호출 위치 | 도구 처리. 동적 호출·지원하지 않는 구문은 미확인으로 남김 |
| 의미 해석 | 상태 소유권, 이벤트→함수→cache→소비자, 도메인 제약 | AI 분석이 필요. 근거·불확실성·검토 범위를 함께 저장 |
| 화면 대응 | 라우트/대표 상태 캡처, 컴포넌트 인스턴스 영역 | 실행·캡처 비용. 실행할 수 없으면 구조 카드와 미캡처 표시 |
| 렌더링 | 전체 인덱스와 페이지/도메인별 지도 | 같은 데이터 재사용. 탐색 때 모델 호출 불필요 |
| 갱신 | 변경 파일과 의존 관계에 영향받은 기록 재검토 | 모든 문서 재분석 대신 무효화된 범위 확인 |

전체 프로젝트의 **탐색 인덱스**는 생성하되 모든 페이지×상태×viewport를 한꺼번에
캡처하지 않는다. 첫 화면은 페이지/공유 의존성 개요, 선택하면 해당 도메인의 상세를
불러오는 방향이 적합하다. 현재 두 페이지 시안은 대규모 성능을 검증한 결과가 아니다.

Fiber를 공통 저장 형식으로 사용하기보다는 프레임워크별 추출기를 FS 중간 표현에 연결한다.
[React의 렌더 트리도 특정 렌더 패스를 표현한다](https://react.dev/learn/understanding-your-ui-as-a-tree).
그 트리 하나로 다른 상태의 화면·서버 흐름·도메인 의도를 모두 증명할 수는 없다.
관측 코드, 실행 캡처, 제안된 설계를 구별하고 동일한 ID로 서로 참조하는 것이 핵심이다.

기능 추가는 기준 자료에 대한 **계획 변경분**으로 연결한다. 기준은 commit과 flow hash로
고정하고 추가/변경/제거 대상 ID를 기록한다. 구현 전에는 기존 관측 자료를 덮어쓰지 않는다.
작업 후 영향을 받은 자료를 재검토하여 새 관측 버전을 저장한다. 기준 hash가 달라지면
변경분을 다시 확인한다. 이번 시험은 추가 전용 합성기를 구현했다. 기존 정의의 변경·제거·승격은 아직 지원하지 않는다.

## 기존 FS에 적용할 순서

1. 이 시안에서 화면 선택·정보 밀도·단계별 변화 표현을 사용자와 확정한다.
2. 실제 프로젝트의 한 도메인 흐름을 골라 현재 `flow`와 이미지 영역의 대응을 검증한다.
3. `flow-schema`에 선택적 인스턴스/화면 상태/단계 변화 필드를 추가한다. 기존 저장 기록은
   그대로 읽히도록 하고 `flow-design`에서 참조·소유권·영역·이미지 hash를 검사한다.
4. `flow-view`에 화면 중심 표현을 추가한다. 현재 논리 흐름도도 유지한다. 계획/시각화
   지침과 예제·브라우저 검사를 함께 수정한다.
5. 이미지 교체 후 좌표 무효화, 중복 컴포넌트 구분, 성공/실패/정리 흐름, 여러 페이지
   구독, 키보드 선택을 실제 프로젝트에서 확인한 뒤 배포한다.

현재 `design`은 proposed flow만 허용한다. 실제 페이지 캡처를 관측 근거로 사용하려면
이를 무조건 proposed로 바꾸지 말고 관측 화면 표현을 별도로 설계해야 한다. 기존 이미지
확인과 상세 설계 승인 조건 역시 단순 시각화를 위해 우회해서는 안 된다.

## 재생성과 검증

저장소 루트에서 `node docs/proposals/component-flow-explorer/build.mjs`를 실행하면
`dist/component-flow-explorer/index.html`이 생성된다. 캡처 데이터가 없으면 같은 HTML
시안을 배경으로 사용하므로 구조와 탐색 기능은 확인할 수 있다.

이미지 생성 시에는 생성 HTML의 `?capture=search&scene=ready`와
`?capture=collection&scene=optimistic` 같은 상태 URL을 열고 760×570 화면을 캡처한다.
`[data-instance]`의 실제 DOM 사각형을 `.mock` 크기로 정규화하여 이미지와 함께
`dist/component-flow-explorer/assets.json`에 저장한다. `capture-input.json`의
specHash/templateHash도 포함한 뒤 build를 다시 실행한다. 이미지가 포함된 최종 HTML을
`preview.html`로 복사한 것이 이번 전달물이다. 최종 HTML은 단독으로 열 수 있다.

빌드 검사는 노드·인스턴스의 참조, 부모 순환, 페이지 소유권, 상태 참조, 이미지 영역과
캡처 버전을 확인한다. 이는 코드 해석의 정확성이나 실제 도메인 동작을 증명하지 않는다.
브라우저 확인 결과는 `verification.json`에 별도로 기록한다.

## 페이지별 이벤트·라이프사이클과 새 기능 추가

페이지 버튼을 선택하면 상단 시나리오 목록이 해당 페이지에 연결된 흐름으로 좁혀진다.
관측/계획과 라이프사이클/이벤트를 구분하고, 전체 영향 지도로 돌아가면 모든 흐름을 보여준다.
페이지는 선택한 상태로 유지하며 교차 페이지 흐름의 전체 단계와 공유 자원 연결도 남긴다.
관련 페이지는 단계의 page, 출발·도착 노드의 부모 페이지, 다중 소비자 effects에서 계산한다.
기록이 없는 페이지는 ‘기록된 흐름 없음’으로 표시한다. 모든 라이프사이클을 자동 발견했다는 뜻은 아니다.

검색 시안에는 CollectionPreview 구독과 unmount 정리(타이머 취소, 요청 취소, 구독 해제)를
설계 흐름으로 추가했다. 실제 주문 예제는 저장된 초기 렌더링을 포함한 6개 흐름과
실제 함수의 실패→재시도 흐름을 함께 표시한다. 없는 unmount 동작은 만들지 않았다.

[관측 기준 + 새 기능 계획 예제](observed/preview-with-plan.html)의 ‘주문 완료 메시지 닫기’를
선택하면 기존 화면 위에 제안된 상태 변경을 확인할 수 있다. 버튼이나 미래 화면을 구현한
결과는 아니므로 이미지에는 ‘기준 화면’이라고 표시한다.

`compose.mjs`는 원본 모델을 복사한 뒤 별도 추가분을 합성한다.

- `baseHash`: 원본 JSON 객체의 `JSON.stringify`를 SHA-256으로 해시한 값. 기준이 달라지면 합성을 거부한다.
- `id`, `title`: 추가 계획 식별자와 이름.
- `scenarios`: 새 흐름. `category`는 `event` 또는 `lifecycle`이며 기존 노드 ID도 참조할 수 있다.
- `nodes`, `pages`, `instances`: 필요한 새 정의만 추가한다. 기존 ID를 덮어쓸 수 없다.
- 추가 노드·흐름은 입력의 basis에 관계없이 `proposed`로 표시한다. 합성은 사용자 승인이 아니다.

생성기는 합성 후 참조·부모 관계·화면 상태·상태 소유자를 다시 검사한다. 기준 hash를
자동으로 갱신하지 않는다. 기존 기준과 추가분을 재검토한 뒤 명시적으로 다시 고정해야 한다.
신규 페이지의 화면 캡처·컴포넌트 영역 매핑은 별도 입력이며 자동으로 만들어지지 않는다.
작업이 끝나도 관측 기준으로 자동 승격하지 않고 실제 구현을 재분석한다.

```sh
node docs/proposals/component-flow-explorer/observed/project-view.mjs
node docs/proposals/component-flow-explorer/observed/project-view.mjs docs/proposals/component-flow-explorer/observed/planned-addition.json
node docs/proposals/component-flow-explorer/check.mjs
```

0.8.0은 이 viewer를 패키지에 포함하며 fs-plan-visualize에서 사용하도록 안내한다.
호스트가 근거를 가진 입력을 작성해야 하며, FS 저장 스키마에서 자동 추출·변환하는 기능은 아니다.

## 라우트 개요 탐색

HTML을 열면 도메인별 작은 라우트 노드가 먼저 나타난다. 노드 hover나 키보드 focus는
인접한 이동 경로·발생 계기·조건을 미리 보여주고, 클릭(또는 Enter)은 선택을 고정한다.
하단 실행 흐름 목록에서 항목을 선택하면 해당 페이지 상세로 진입한다. 상세 화면에서도 ‘라우트 개요’로 돌아갈 수 있다.
라우트 개요·전체 영향 지도·개별 페이지는 한 번에 하나만 선택된다.

페이지의 `domain`은 명시한 도메인 그룹이다. 없으면 route의 첫 경로 구간을 탐색 그룹으로
사용하며 그것을 코드에서 해석한 도메인 지식으로 취급하지 않는다. 이동 경로는 별도 `navigation`에
저장한다. 이벤트의 공유 cache 소비자나 시나리오 순서를 라우트 이동으로 추론하지 않는다.

```json
{
  "id": "open-collection",
  "from": "search",
  "to": "collection",
  "label": "컬렉션 전체 열기",
  "condition": "Reading collection의 전체 열기 선택",
  "basis": "proposed"
}
```

`from`/`to`는 page ID다. 관측 이동은 `evidence`가 있어야 하며, 잘못된 page 참조·중복 ID·
빠진 조건은 거부한다. 로그인 성공/실패·복귀 등도 실제 기록이 있을 때 각각 별도 관계로 넣는다.
현재 Folio의 이동은 설계 가정이며, 실제 주문 fixture에는 라우트 이동 기록이 없다.
계획 추가분의 `navigation`도 기존 ID를 대체하지 않고 proposed로 합성된다.

흐름 선택창은 네이티브 select의 키보드 동작을 유지하면서 appearance를 제거하고,
오른쪽 14px에 16px 화살표와 텍스트용 44px 우측 여백을 둔다. 긴 제목은 말줄임하며
필드 너비는 부모 영역을 넘지 않게 제한한다.

## 라우트 탐색 디자인과 조작

초기 화면에는 ‘라우트 개요’만 표시한다. 노드를 클릭해 고정한 뒤 하단 목록에서
실행 흐름을 선택하면 ‘전체 영향 지도’와 그 흐름에 관련된 페이지 탭을 노출한다.
흐름을 바꾸면 관련 페이지 탭도 갱신한다. hover/focus 미리보기만으로 화면을 전환하지 않는다.

라우트 카드는 중립색과 일정한 크기를 유지한다. 연결된 노드만 그림자로 강조하며
선은 1.2px 두께와 이동하는 대시로 표현한다. 화살표 머리는 표시하지 않고 이동 방향·조건은
하단 텍스트에 유지한다. SVG path는 hover 때 교체하지 않으며 확대해도 선 두께는 고정한다.
기존 공통 `.preview` 스타일과 충돌하던 이름을 분리해 hover 시 크기·배치 변화를 방지했다.
모션 감소 환경에서는 선의 이동 효과를 끈다.

- 지도 위 휠: 커서 위치를 기준으로 확대·축소(15~300%).
- 빈 영역 드래그: 지도 이동. 노드 배치는 바꾸지 않는다.
- 확대·축소 버튼, 전체 맞춤, 지도 focus 후 +/-·Home·방향키로도 조작한다.
- 하단 이동 조건·실행 흐름 목록: 최대 340px에서 세로 스크롤. 지도 줌과 별도로 동작한다.
- 페이지 상세의 단계·상태 변화 패널도 최대 높이 내에서 세로로 탐색한다.

브라우저에서 60개 라우트·182개 연결과 35개 실행 흐름의 합성 입력으로
확대·맞춤·스크롤 및 가로 넘침을 확인했다. 이는 실제 프로젝트 분석의 정확성이나
수천 개 노드의 프레임 성능을 입증한 측정은 아니다.
