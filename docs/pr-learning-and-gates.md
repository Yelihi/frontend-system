# PR의 판단을 재사용하고 제출 전에 검사하기

2026-10-09 현재 소스 기준. 설치본에는 다음 release와 플러그인 업데이트 후 반영됩니다.

## 두 종류의 지식

책·웹표준·디자인 패턴 등은 근거와 조건을 갖춘 공통 지식입니다. 모두 정량적 정답인 것은
아닙니다. PR에서 드러나는 상태의 수명, 허용할 의존성, API 소유권 등은 프로젝트의 판단입니다.
두 종류를 연결하되, 특정 프로젝트의 선호를 공통 필수 규칙으로 바꾸지 않습니다.

```text
fs-review pr https://github.com/owner/repo/pull/123
fs-review pr https://github.com/owner/repo/pull/123 learn
```

첫 명령은 읽고 평가합니다. `learn`은 대상 프로젝트에 후보·근거와 확인된 결정을 남깁니다.
둘 다 GitHub 댓글을 게시하거나 제품 코드를 수정하지 않습니다. 수정 요청이 함께 있으면
기존 권한 안에서 plan/work로 이어갑니다. 첫 분석이나 승인된 계획이 없다면 필요한 선행
작업을 진행하며, 리뷰 댓글만으로 새로운 요구사항이나 사용자 동의를 만들어내지 않습니다.

AI는 댓글 당시 코드와 현재 코드, 답글과 최종 선택을 구분합니다. 사람의 의견도
반례·근거·적용 조건을 검토하여 다음 중 하나로 분류합니다.

| 결과 | 의미 |
| --- | --- |
| reusable | 다른 상황에도 조건부 적용할 수 있는 후보. 아직 공용 지식 승인은 아님 |
| project-only | 이 프로젝트에서 확인된 선택. 범위와 재검토 조건을 보존 |
| needs-context | 결론을 바꿀 정보 부족. 코드에서 먼저 찾고 필요한 질문만 전달 |
| rejected | 잘못된 전제·반례·과한 처방. 기각 근거를 설명하고 승격하지 않음 |

공유할 후보는 사용자가 `fs-knowledge add`로 요청하면 pending PR로 전달합니다.
active 선택은 관리자, review는 근거 검토, sync는 유효한 merged 자료의 변환입니다.
이 절차를 생략하고 PR 댓글을 learned 색인에 바로 넣지 않습니다. 비공개 프로젝트의 내용은
로컬 학습 요청만으로 외부에 게시하지 않습니다. [상세 절차](../references/workflows/pr-feedback.md).

## AI는 맥락을 어떻게 파악하는가

FS가 모든 코드의 의미를 자동으로 완성한 뒤 모델에 넘기는 구조는 아닙니다.
**호스트 AI의 필요한 범위 읽기와 도구의 사실 추출이 번갈아 진행됩니다.**

1. 요청·변경 범위·환경·기존 project.md/결정 요약을 읽습니다. 최초 전체 설명을 만들 때는
   기준 커밋의 파일 범위를 점검하지만, 작은 변경마다 모든 파일을 처음부터 정독하지 않습니다.
2. 변경 함수의 입력·출력·부작용을 읽고 호출자와 소비자를 찾습니다. 이벤트에서 시작할 수도,
   오류가 난 함수에서 거꾸로 시작할 수도 있습니다. import, callback, props, store 갱신,
   캐시 무효화, 오류/로딩 소비자를 필요한 만큼 연결합니다.
3. [추출기](../src/application/knowledge/code-triggers.ts)가 import 바인딩, 호출, JSX,
   매개변수 분기 등의 사실을 추출합니다. `parameter-dispatch`는 매개변수/속성을 리터럴과
   비교하거나 switch하는 구조입니다. 이 신호 자체는 결함·SOLID 위반 판정이 아닙니다.
4. [라우팅](../src/application/knowledge/routing.ts)은 코드 신호, 요청·파일 이름·구조의
   검색어, 인용을 갖춘 AI 해석으로 후보를 모읍니다. 등록된 의미 신호 ID를 사용하며,
   검색 점수가 실제 적용 가능성을 증명하지 않습니다.
5. AI는 선택한 지식의 조건·반례·조사 질문을 읽고 빠진 관계만 추가 조사합니다.
   필요할 때 `includeRelations:true`로 최대 200개의 제한된 관계 사실을 받습니다.
   동적 호출·고차 함수·지원하지 않는 구문·잘린 결과는 미확정으로 남깁니다.
6. 과거 결정의 범위·확인된 의도·유효한 근거를 현재 상황과 비교합니다. 동일 조건이면 재사용,
   예외이면 제외/대안 검토, 새 의도이면 질문합니다. 코드만으로 미래 요구사항을 발명하지 않습니다.

예를 들어 `edit(analysis, {type: ...})`를 발견해도 곧바로 클래스로 바꾸지 않습니다.
각 이벤트가 연산을 이미 고정하는지, 인자가 다른 helper를 거쳐 오는지, command가 저장·전송·재생되는지,
공통 validation과 상태 수명이 보존되는지를 확인합니다. 이벤트별 직접 호출이 더 적합할 수도,
명령 객체가 도메인 계약이어서 유지해야 할 수도 있습니다. 이 질문을 지식에 구조화하는 것이 sync의 역할입니다.

문맥을 실제로 이해했는지 해시가 증명하지는 않습니다. 해시는 읽은 자료가 바뀌지 않았는지
검사하며, 해석의 정확성은 코드 근거·반례·실행 결과로 별도 검토합니다.

## PR 전 검사

```text
fs-review pre-pr --base origin/main --plan <plan-id>
```

검사 순서는 **버그·보안 → 도메인 요구/범위 → 유지보수**입니다. 과도한 렌더링을 측정 없이
확정 버그라고 하지 않고, 필수 브라우저 검사를 실행하지 못했다면 통과로 기록하지 않습니다.
요청하지 않은 기능·추상화·검사 약화도 검토합니다. 선택적인 스타일 제안만으로 제출을 막지는 않습니다.

계획에 `pr-safety`, `pr-scope` 의미 검토를 명시하고 기존 final check/review 기록을 재사용합니다.
최종 리뷰는 의도한 변경이 커밋된 상태에 연결합니다. `check_pr_readiness`가 반환한 PR 범위를
`save_semantic_review.prScope`에 넣으며, 실제 대상 브랜치·merge-base·head·diff가 달라지면 재검토합니다.
이름이 같은 두 리뷰만 만든다고 내용의 타당성이 자동 증명되지는 않습니다.

쉘에서는 `fs pr-check . --base origin/main --plan <plan-id>`로 같은 검사를 실행할 수 있습니다.
승인된 실행의 완료, 현재 필수 검사, 두 리뷰, 전체 변경 파일의 범위 검토가 빠지면 종료 코드 1입니다.
준비 완료인 경우만 FS가 이미 허용된 PR 생성 작업으로 넘어갑니다. 검사 자체는 PR을 만들지 않습니다.
기존 계획에는 PR 검토 의무를 명시적으로 반영해야 하며, 일반 구현 완료에 새 의무를 몰래 추가하지 않습니다.

GitHub의 PR 이벤트 CI는 **생성 후 병합을 막는 역할**입니다. 로컬 절차는 다른 클라이언트나
웹에서의 생성을 차단하지 않습니다. 강제 병합 제한은 원격 required checks/rulesets를 설정해야 합니다.
이번 변경은 해당 원격 설정이나 Git hook을 자동 설치하지 않습니다.
[검사 절차·CI 경계](../references/workflows/pr-readiness.md).

## 효과 측정

[v16 평가](../test/evals/fs-comparison/v16/README.md)는 같은 과거 판단 자료를 제공한 일반 AI와
FS 절차를 비교합니다. 반복 질문, 올바른 결정 재사용, 조건이 달라진 예외 구분을 별도로 셉니다.
잘못된 댓글을 기각하는지와 필요한 질문까지 생략하지 않는지도 확인합니다. 토큰 비용은 함께 기록합니다.
통제된 재생 사례의 질문 수는 실제 사람의 설명 시간 감소와 다릅니다. 이후 PR을 숨긴 시간순 실사용
평가에서 사용자가 의도·판정 기준을 확인해야 실제 효과를 주장할 수 있습니다.
