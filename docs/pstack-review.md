**pstack 검토와 FS 비교 결과의 원인 분석**

검토일: 2026-10-04. 대상은 `cursor/plugins`의 `pstack` 0.15.9, 커밋 [`e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a`](https://github.com/cursor/plugins/tree/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack)이다. 변경되는 main 대신 이 버전에 판단을 고정했다.

총 161개 파일을 확보하고 Git blob 해시와 대조했다. 텍스트·코드 154개와 이미지 7개다. 각 파일의 역할, 주요 규칙·실행 경로·테스트 대상, FS 반영 여부는 [파일별 검토표](pstack-file-review.md)에 기록했다. 스킬 본문은 실행 지시로 채택하지 않고 검토 자료로 읽었다. pstack 설치, 외부 자동화 실행, 전체 테스트 실행, FS와 pstack 간 모델 성능 비교는 하지 않았다. 아래 TypeScript 반례만 로컬 컴파일러로 별도 확인했다.

**판단**

현재 관측 결과는 “FS가 지식을 전혀 찾지 못했다”가 아니다. 일반 AI도 해결한 작은 명시적 계약에 FS가 분석·근거 연결·승인·실행 기록 비용을 추가했고, 그 비용에 상응하는 규정 위반 감소는 관찰되지 않았다. 제가 제안해 온 설계도 이 부분을 인정해야 한다. 추적 가능한 절차를 만들었다는 사실을 더 좋은 구현이 나온다는 증거로 취급하면 안 된다.

pstack에서 가장 참고할 것은 새 라우팅 엔진이나 많은 에이전트가 아니다. 조건에 맞는 작업 절차 선택, 호출자 관점의 설계 예시, 반복되는 지적을 실행 가능한 제약으로 바꾸는 방식이다. 다만 FS에는 이미 관련 기능이 상당 부분 있다. 유사한 문서를 더 추가하기보다 현재 기능이 실제 위반을 잡는지 검증하고, 비용이 큰 중복을 줄이는 방향이 적합하다.

현재 FS의 [policy.ts](../src/application/policy.ts)는 required 규칙에 자동 검사 또는 의미 리뷰를 요구하고 검사 파일을 보호한다. [design-evidence.ts](../src/application/design-evidence.ts)는 근거·지식·결정·규칙·이슈 연결과 최신성을 확인한다. [workflow-store.ts](../src/application/workflow-store.ts)의 `saveReview`는 해당 규칙·파일·시도·리비전이 존재하고 모든 리뷰 항목을 다뤘는지 확인한다. 그러나 리뷰 문장의 결론이 참인지는 서버가 판정하지 않는다. FS에 검증 기능이 없다는 뜻이 아니라, 보장하는 범위를 구분해야 한다는 뜻이다.

예컨대 “UI가 전송 계층에 직접 의존하지 않는다”를 검사 ID와 연결해도, 연결된 스크립트가 실제로 별칭·재수출·허용 예외를 검사하는지는 별도의 문제다. 현재의 유효/무효 예제 및 검사 보호 기능을 실제 프로젝트 규칙에 맞춰 채우고 반례로 검증해야 한다.

**pstack이 실제로 제공하는 것**

매니페스트의 공개 스킬 루트에는 50개 SKILL.md가 있고 그중 24개가 원칙이다. 주 진입점은 `poteto-mode`, 작업별 절차는 23개다. 별도로 에이전트 2개, 장기 작업·PR 상태 관리 스크립트, 비활성 Benny 자동화 자료가 있다. 이 매니페스트에는 MCP 서버나 실행 훅이 선언되어 있지 않다. 라우팅은 주로 모델이 요청을 읽고 적절한 문서를 선택하는 방식이다. [매니페스트](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/.cursor-plugin/plugin.json), [진입 스킬](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/SKILL.md).

| 비교 항목 | pstack | 현재 FS와의 관계 |
| --- | --- | --- |
| 작업 절차 선택 | 조사·버그·리팩터링·성능·장기 작업을 구분 | FS도 작업 모드가 있다. 작은 승인 작업에서 전체 준비 절차를 얼마나 재사용하는지가 개선 지점이다. |
| 지식 후보 검색 | 스킬 설명, 원칙 이름, 모델의 판단 | FS는 AST 사실·구조 트리거와 요청 검색을 이미 결합한다. pstack으로 교체할 근거가 없다. |
| 설계 구체화 | 호출 예시부터 타입·시그니처·소유권·모듈 형태를 작성 | FS의 자연어 계획에 필요한 부분만 코드 예시로 추가할 가치가 있다. |
| 사용자 결정 | 일부 설계 단계는 별도 checkpoint가 없으면 구현으로 진행 | FS의 사용자 선택을 대신할 수 없다. 중요한 선택은 기존 결정 절차를 유지한다. |
| 검증 | 실제 앱 관찰, 검사 명령, 반례, PR별 증거 기록 | FS의 기존 검사 정책에 재현 가능한 실행 절차를 연결하는 데 참고한다. |
| 다중 모델 | arena·interrogate·swarm으로 후보·검토·분담 실행 | 비용이 증가할 수 있다. 같은 모델 비교에 몰래 추가하면 통제변인이 깨진다. |
| 지속적 학습 | reflect·correct가 반복된 교정을 일반화하고 구조적 제약을 제안 | FS 지식 검토와 연계 가능. 일회성 선호를 전역 규칙으로 자동 승격하지 않는다. |

참고할 실행 구조는 `watch-pr`다. 외부 GitHub 응답을 읽는 부분, 상태를 판정하는 부분, 사용자에게 보여주는 부분을 나누고, 잘못된 상태 조합을 타입과 테스트로 제한한다. 반복적인 상태 확인은 스크립트가 맡는다. 이는 FS에서도 기계적인 해시·기록·상태 집계를 모델이 반복 작성하지 않게 하는 방향에 참고할 수 있다. 다만 이것은 PR 감시 도구이며 프론트엔드 지식 검색 엔진이 아니다. [types.ts](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/scripts/watch-pr/types.ts), [policy.ts](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/scripts/watch-pr/policy.ts), [컴파일 반례](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/scripts/watch-pr/types.compile.ts).

**FS에 반영할 우선순위**

아래는 검토 제안이며 이번에 구현한 기능이 아니다. 먼저 기존 기능을 확장할지 확인하며 새 엔진을 기본 선택으로 삼지 않는다.

| 순서 | 변경 후보 | 기존 위치 | 완료를 판단할 근거 |
| --- | --- | --- | --- |
| 1 | 미결정 선택 입력을 상태에 맞게 표현. open에는 선택값을 요구하지 않고 resolved에는 유효 선택을 요구 | `design-evidence.ts`, `mcp.ts` | 미결정 초안이 한 번에 저장되고, 선택 없는 승인·존재하지 않는 선택은 거절. 서버가 답을 임의 생성하지 않음 |
| 2 | 승인된 작은 작업의 근거·정책을 재사용하고 변경된 범위만 다시 검토 | `fs-plan`, `fs-work`, `task-context.ts`, `analysis-receipts.ts` | 같은 계약·코드·지식에서 불필요한 재분석/입력이 감소. 관련 코드·정책 변경 시 재검토는 유지 |
| 3 | 규칙마다 실제 검사·정상 예·실패 예·제외 예를 연결하고 검사 능력을 검증 | `policy.ts`, `rules/`, 프로젝트 검사 설정 | 알려진 위반을 거절하고 유효 구현/제외 대상을 통과. 검사 이름만 연결한 항목을 검증 완료로 표시하지 않음 |
| 4 | 중요한 설계 결정에 호출 예시, 공개 타입·시그니처, 상태 소유자, 허용 의존성을 함께 기록 | `evidence-led-design.md`, 기존 plan/decision 구조 | 사용자 승인 이후 공개 계약의 임의 확장·입력 변경·의존 방향 위반을 검출. 내부 구현의 허용 자유도는 보존 |
| 5 | sync 검토에서 지식의 조건·예외·반례·판단 질문을 확인하고 반복 실패를 환류 | 기존 knowledge review/sync와 후보 규칙 | 지식을 많이 읽었는지가 아니라 어떤 승인 결정·검사에 쓰였는지 확인. 근거 없는 전역 강제 규칙은 생성하지 않음 |
| 6 | 해당 프로젝트의 실제 실행·재현 절차를 유지 | 기존 verification 정책·프로젝트 스크립트 | UI/상태 문제는 실제 사용자 경로로 관찰. 실행 불가는 미검증으로 남고 정상 결과로 집계하지 않음 |

1~3부터 좁게 변경하고 같은 평가로 비용과 거절 정확도를 확인하는 편이 합리적이다. 문서를 줄였다는 이유로 근거, 사용자 결정, 검사 보호를 제거하면 FS의 목적을 잃는다. 반대로 경량화를 위해 작은 작업마다 별도의 새 승인 흐름을 추가해서도 안 된다.

예를 들어 지식이 “요청 정책을 공통화할지 검토하라”라면 다음까지 이어져야 한다.

```mermaid
flowchart LR
  A[코드 사실과 트리거] --> B[조건과 예외가 맞는 지식 후보]
  B --> C[정책 차이와 선택지를 사용자에게 제시]
  C --> D[승인된 API와 소유권 계약]
  D --> E[연결된 검사와 반례]
  E --> F[구현 결과와 위반 판정]
```

코드에 `fetch`가 있다는 사실만으로 오류나 새 계층 필요성을 확정하지 않는다. 동일한 인증·오류 정책을 공유하기로 결정한 경우에만 대상 호출자, 입력 객체 소유권, 콜백 오류 전달, 재시도 횟수를 계약과 검사로 고정한다. 다른 정책의 요청은 제외한다. 이 구조의 상당 부분은 이미 FS에 있으므로, 추가 문서보다 마지막 검사 연결의 실제 효과를 확인해야 한다.

[architect](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/architect/SKILL.md)의 호출 예시 중심 설계와 [correct](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/correct/SKILL.md)의 반복 지적을 구조적 제약으로 옮기는 방식이 이 제안의 주된 참고점이다. 모든 지식을 자동 수정 규칙으로 만들 수 있다는 뜻은 아니다. 팀의 선호·트레이드오프는 사용자 결정으로, 검사할 수 없는 판단은 의미 리뷰로 남긴다.

**그대로 가져오면 안 되는 부분**

- `architect`의 기본 자동 진행과 `never-block-on-the-human`의 방향은 FS의 중요한 사용자 선택을 생략하는 근거가 될 수 없다. 이미 승인된 실행상의 세부 처리만 자동화한다.
- 여러 모델·여러 후보·모든 PR의 많은 검증 작업을 기본으로 추가하지 않는다. `multi-phase-plan`은 PR마다 10개 live 검증 lane까지 요구한다. 이는 현재 FS의 비용 문제를 해결한다고 볼 수 없다.
- `no-comments`는 상당히 강한 개인 코드 스타일이다. FS의 근거·주의사항·외부 제약 주석을 일괄 삭제하는 규칙으로 채택하지 않는다.
- Cursor의 Task, loop, 모델 이름, transcript 경로와 외부 `cursor-team-kit` 의존성을 Codex에 그대로 복사하지 않는다.
- Benny의 Slack·티켓·PR 자동화를 FS의 기본 지식 관리에 넣지 않는다. 사용자 설정과 배포 자료를 분리하고 기존 수정안을 먼저 검증하는 원칙만 참고한다.

이 제한은 추측만이 아니다. 파일에서 다음 범위를 확인했다.

| 항목 | 확인한 사실 | FS에 대한 의미 |
| --- | --- | --- |
| 계획 검사 | `check-plan.mjs`는 제목, 고정 문구, 체크박스, 10개 lane, 증거 경로 표기 등을 검사한다. 실제 제품 코드를 읽거나 증거 파일의 내용을 검증하지 않는다. | 계획서 문법 검사와 계획 준수 검사는 구분해야 한다. |
| 작업 ledger | `orch/store.ts`는 PR+SHA별 verdict와 증거 문자열을 저장한다. `record`는 증거가 참인지 실행해 확인하지 않는다. | SHA에 묶인 기록은 유용하지만 스스로 입증하는 시스템은 아니다. FS의 기존 근거 검사를 대체할 이유가 없다. |
| 타입 예시의 오류 | `patterns.md`는 start+duration 표현으로 음수 구간을 만들 수 없다고 설명하지만 `durationMs: number`에는 `-1`이 들어간다. | 좋은 원칙을 설명하는 문서도 예시 검증이 필요하다. |
| 실행 환경의 결합 | `orchestrate`와 해당 store의 frontier는 Graphite `gt`를 사용한다. 다른 PR 절차는 GitHub/Origin을 선택한다. | 실행 경로별 의존성을 조사해야 한다. 모든 pstack 기능이 같은 환경에서 즉시 실행되는 것은 아니다. |

타입 반례는 `type TimeRange = { start: Date; durationMs: number }`에 `durationMs: -1`을 대입한 임시 파일을 로컬 `tsc --strict --noEmit --skipLibCheck`로 검사했고 종료 코드 0이었다. 음수 금지는 경계 검증이나 검증된 생성 방식이 추가되어야 한다. 이는 pstack 전체가 잘못됐다는 결론이 아니라 지식 sync 전 예시·반례 검증의 구체적 필요성이다. [해당 예시](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/typescript-best-practices/references/patterns.md), [계획 검사 코드](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/scripts/check-plan.mjs), [ledger 구현](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/scripts/orch/store.ts).

**다음 검증은 기존 점수를 유지하면서 원인을 분리한다**

이번 11/11 동점을 지우거나 사후에 새 기준을 넣어 FS의 승리를 만들지 않는다. 현재 사례는 작은 승인 작업의 비용 회귀 검사로 유지한다. 별도로 실제 사용자 작업에서 발견한 계획 위반·불필요한 재질문·지식 적용 누락 사례를 수집하고, 평가 전에 계약과 정답·유효한 대안을 고정한다.

| 평가 | 통제하는 것 | 주 지표 |
| --- | --- | --- |
| 같은 계획의 구현 준수 | 같은 시작 코드, 계획, 사용자 답변, 모델, 제한 시간, 도구 조건 | 최초 계약 충족률, 금지 변경 수, 결정 위반 수, 수정 횟수 |
| 검사의 실효성 | 승인 규칙마다 유효/무효/제외 fixture와 고정 검사 버전 | 위반 검출률, 정상 코드 오탐률, 미검증 비율 |
| 질문·계획의 가치 | 같은 모호한 요청과 시작 코드, 사전 고정된 사용자 응답 정책 | 필요한 결정 발견률, 불필요한 질문 수, 답변 반영률. 근거·질문 의미는 블라인드 평가 |
| 실행 비용 | 동일 사례 반복, 순서 교차, 새 세션·작업 트리, 명시된 캐시 조건 | 준비/구현/수정의 시간, 비캐시·캐시 입력과 출력, MCP 횟수·실패, 성공당 비용 |

원인 분리 실험은 일반 AI → 같은 지식만 제공 → 같은 승인 계약과 실행 검사 제공 → 전체 FS처럼 기능을 단계적으로 추가해 비교할 수 있다. 각 조건이 무엇을 받았는지 공개하고 모델·검사·예산을 고정해야 한다. 질문/계획 생성의 효과와 같은 계획의 구현 효과를 한 점수로 섞지 않는다. 여러 모델·독립 리뷰의 효과를 보려면 별도 조건으로 둔다.

pstack의 [eval 절차](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/poteto-mode/playbooks/eval.md)는 비교 대상임을 드러내는 표현을 줄이고 실행 기록으로 절차 준수를 평가하도록 제안한다. FS runner의 `Both arms` 같은 실험 설명은 자연스러운 작업 요청으로 바꾸는 후보지만, 사용자 요구 규칙까지 숨기면 안 된다. [benchmark-checklist](https://github.com/cursor/plugins/blob/e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a/pstack/skills/benchmark-checklist/SKILL.md)의 반복·교차 측정도 참고할 만하다. 파일을 읽었다는 기록은 판단에 올바르게 사용했다는 증거와 별도로 집계한다.

지식을 저장하고 근거와 결정을 재사용하는 가치는 AI의 단일 작업 점수와 별도로 유지할 수 있다. 다만 “FS를 쓰면 더 엄격하고 더 저렴하게 구현한다”는 주장은 실제 반복 비교에서 규정 위반이나 성공당 비용이 개선될 때만 할 수 있다. 이번 검토에서 제품 코드와 기존 평가 결과는 변경하지 않았다.

## 구현 후속 기록

사용자의 구현 요청 후 같은 pinned snapshot의 architect/호출 예시 템플릿, how, principle-encode-lessons-in-structure를 다시 읽고 아래를 반영했다. 앞의 “변경하지 않았다”는 검토 단계의 기록이며, 이 절은 후속 구현 기록이다. pstack 코드를 복사하거나 해당 스킬을 실행하지 않았다.

| 반영 내용 | 구현·검증 |
| --- | --- |
| 상태에 맞는 입력 구조 | design-evidence의 입력을 status별 union으로 구분. open/excluded는 selected 생략 → null, resolved는 실제 ID 필수. open 저장 성공과 승인 거절, 잘못된 선택 거절을 회귀 검사 |
| 이미 읽은 근거 재사용 | task-context/MCP에 knownContextId. 최신 route와 프로젝트 해시가 동일할 때만 후보·discovery 재전송 생략. 정책·경고는 계속 반환. 소스/관련 설정/요구사항/프로젝트 문서 변경 시 메타데이터 복원 |
| 호출자 관점의 계약 | fs-plan과 evidence-led-design에 변경된 공개 경계의 호출 예·시그니처·소유권·의존 방향 기록. 내부 helper는 계속 재량 |
| 반복 교정을 실제 검사로 | fs-work는 반복 실패의 구체적인 bad case를 타입·기존 lint·회귀 검사로 막고 유효 대안도 확인. 새 보편 의무나 새 승인 절차는 추가하지 않음 |
| 지식 예시의 검증 | source review 지침에 컴파일/실행 주장에 대한 정상·반례·제외 조건 검증. 도구가 없으면 확인하지 않은 보장을 verified로 기록하지 않음 |
| 더 복잡한 고정 평가 | v5 주문 서비스와 15개 결함 교정. v4 격리/대화/사용량 수집 코드를 공유. 모델에 보이는 “Both arms/동일 비교용” 표현 제거 |

기존 policy의 규칙→검사/review 연결, guard와 evidence freshness를 재사용했다. 모든 source의 자동 반례 생성, 새로운 범용 검사 엔진, 모든 추론을 강제 규칙으로 바꾸는 기능은 만들지 않았다. 지식의 의미적 진실성과 UI 실제 동작은 기계적 기록 검증만으로 입증되지 않는다.

[v5 실행과 결과](../test/evals/fs-comparison/v5/README.md): FS 회귀 69개, 실행기 v4 7개/v5 3개, 독립 패키지 검사 통과. 정상 2개/결함 15개를 올바르게 판별했다. 이미 읽은 동일 분석 재요청은 한 예제에서 응답 30.4% 감소했지만 CPU·실제 총 토큰 절감은 미측정이다. 모델 비교는 중첩 sandbox 권한 오류로 호출 전 차단됐다. skill-creator의 quick_validate.py는 환경에 PyYAML이 없어 실행되지 않았고, 스킬의 기존 frontmatter는 수정하지 않았다. 패키지 검사는 네 스킬의 포함과 MCP 실행을 별도로 확인했다.
