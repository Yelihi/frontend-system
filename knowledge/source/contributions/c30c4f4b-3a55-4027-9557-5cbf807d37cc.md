# 변경된 UI 계약과 완료 이벤트의 캐시 검증

## 출처와 범위

- 작성 근거: 2026-10-13 프런트엔드 PR 검토에서 관찰한 회귀와 누락을 일반화한 기여자 해석. 특정 프로젝트의 비공개 코드와 사용자 데이터는 포함하지 않는다.
- 기술 근거: Next.js App Router 16 문서의 `unstable_cache` 및 `revalidateTag` 설명. 확인일 2026-10-13.
  - https://nextjs.org/docs/app/api-reference/functions/unstable_cache
  - https://nextjs.org/docs/app/api-reference/functions/revalidateTag
- 상태: 검토 전 후보. 한 프로젝트에서 얻은 관찰을 모든 프로젝트의 필수 규칙으로 취급하지 않는다.

## 관찰과 조건부 판단

### 1. 화면 계약 변경 뒤 소비자 상호작용 테스트 추적

페이지에서 제목, 링크, 탐색 위치, 사이드바 노출을 바꾸면 해당 화면으로 진입하거나 그 화면에서 이동하는 기존 Storybook `play` 함수와 브라우저 테스트가 이전 계약을 계속 기대할 수 있다. 단위 테스트, 타입 검사, 빌드가 통과해도 이런 테스트는 실패할 수 있다.

적용 조건: 변경된 UI 요소를 다른 스토리나 상호작용 테스트가 선택자·접근 가능한 이름·경로로 참조하는 경우. 변경 파일의 테스트뿐 아니라 그 화면을 **소비하는** 흐름을 검색하고, 실제 선택된 검사 명령으로 실행 결과를 확인한다. 테스트 단계가 완료로 표시돼도 실행하지 않은 스토리 테스트를 통과로 추정하지 않는다. 현재 위치의 접근성 속성이 바뀌면 화면 렌더링과 키보드·보조기기 의미도 함께 확인한다.

반례: 상호작용 스토리가 없거나 UI 계약에 영향을 주지 않는 내부 수정이라면 Storybook 전체 실행을 기계적으로 요구할 근거는 없다. 테스트 이름을 바꾸는 것으로 사용자 동작의 성공을 증명하지 않는다.

검증 예: 새 화면에 진입하는 흐름, 그 화면에서 다른 화면으로 나갔다 돌아오는 흐름, 삭제된 요소가 더는 선택되지 않는지 검사한다. 테스트 명령과 통과·실패 범위를 보고한다.

### 2. 시간 기반 캐시와 완료 후 최신성 계약

Next.js `unstable_cache`의 `revalidate`는 재검증 간격 설정이며 사용자에게 보이는 데이터의 최대 지연 시간을 단독으로 보장하지 않는다. 캐시된 데이터가 여러 완료·수정 경로에서 바뀐다면 각 성공 경로와 캐시 태그 또는 경로 재검증의 연결을 검토한다. 캐시 키와 태그가 사용자별 데이터의 경계를 유지하는지도 확인한다.

Next.js 16 문서는 `revalidateTag`의 일반적인 `max` 프로필이 stale-while-revalidate이며, `{ expire: 0 }`은 다음 요청에서 오래된 값을 제공하지 않고 재검증하도록 만든다고 설명한다. `revalidateTag`는 Server Action과 Route Handler에서 사용할 수 있다. `updateTag`는 Server Action 전용이므로 호출 위치와 버전을 확인해야 한다.

적용 조건: 사용자에게 완료 직후 갱신된 집계·목록을 보여줘야 하는 캐시, 그리고 그 데이터를 바꾸는 완료 이벤트가 실제로 존재할 때. 성공 후 무효화, 실패 시 무효화하지 않음, 사용자별 경계, 반환 결과와 화면 재방문의 조합을 테스트한다. DB 작업이 이미 완료된 뒤 캐시 무효화에 실패한 경우 실패 응답으로 완료를 뒤집지 않는지도 검토한다.

반례: 약간 오래된 데이터를 허용하는 콘텐츠라면 stale-while-revalidate가 적절할 수 있다. 아직 없는 완료 경로에 가상의 무효화 코드를 강제할 수 없다. 다른 캐시 계층이나 브라우저 라우터 캐시가 있다면 이 검토만으로 최종 화면 최신성을 보장하지 않는다.

## 이번 누락에서 얻은 검토 방법

계획의 테스트 목록에 통계 집계와 권한 검사만 있었고, 기존 상호작용 스토리와 모든 완료 경로는 포함되지 않았다. 자동 검사 목록도 해당 스토리 실행을 포함하지 않았다. 자체 의미 검토에서 타임아웃 수치를 최대 지연으로 해석해 실제 캐시 동작과 어긋난 설명을 승인했다. 따라서 리뷰에서는 계획에 적힌 검사와 **실제로 실행된 검사**를 구분하고, 최신성 주장에는 변경 이벤트·캐시 의미·재방문 결과를 함께 대조한다.

이 문단은 단일 사례에서 도출한 검토 관점이며 FS의 기존 규칙이 실행되지 않았다는 증거는 아니다. 적용 여부는 프로젝트의 캐시 API 버전, 실제 완료 경로, 스토리 테스트 존재 여부를 확인한 뒤 판단한다.

## 검토할 질문

- 사용자가 보는 최신성 계약은 재방문 시 즉시 갱신인지, 백그라운드 재검증 허용인지?
- 변경 화면을 소비하는 상호작용 스토리가 있는지, 어떤 검사 명령이 이를 실행하는지?
- 완료 경로가 Server Action, Route Handler, 외부 웹훅 중 어디에 있는지?
- 이미 존재하는 FS 검증·접근성 지식과 어느 부분이 중복인지? 중복이라면 새 규칙 대신 기존 참조의 조건·체크 보강으로 충분한지?
