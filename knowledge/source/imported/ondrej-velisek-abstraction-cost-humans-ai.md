## 원문 주장 요약

저자는 복잡성 은닉·의미 부여·재사용의 이익과 간접 참조의 비용을 비교하자고 제안한다. 여러 파일을 따라가야 하는 구조는 사람의 탐색과 에이전트의 문맥 수집 부담을 늘릴 수 있다.

계산기 네 변형의 실험에서 작업별 비용은 달랐다. 일괄 변경이나 결함 탐색에는 추상화가 유리한 사례도 있었다. 글의 **30% 비용 증가**는 실제 제품의 측정값이 아니라 모델의 외삽을 저자가 낮춰 제시한 추정치다.

예시는 단순 상수, 고정 JSX 목록, 객체 생성 래퍼, CSS 간접화, Context 소비 위치, 값 이름만 바꾸는 계층을 검토한다. 모든 추상화를 제거하자는 주장은 아니다.

## 검토 판단과 근거 한계

- 채택할 개념: 추상화의 편익뿐 아니라 호출·데이터 흐름을 이해하기 위한 탐색 비용도 설계 검토 대상이다. 이 문서는 개념 자료이며 강제 규칙이나 자동 리팩터링 지시가 아니다.
- 수치의 일반화는 보류한다. 작은 합성 앱의 의도적인 12개 추가 계층, 작업 구성, 모델·도구·캐시 조건을 실제 프로젝트와 동일시할 수 없다. 본문은 394회 실행을 언급하지만 보조 결론의 상관 분석은 314회를 명시한다. 분석 대상·집계 버전의 관계는 확인하지 않았다.
- 본문은 특정 일괄 수정 실험에서 bash를 제한했다고 밝힌다. 도구 조건이 다른 결과를 하나의 공정한 비교처럼 해석하지 않는다. 반복 횟수만으로 외적 타당성이나 구현 정확성이 보장되지 않는다.
- 비용·시간과 코드의 신뢰성은 별도 결과다. 읽은 파일이나 토큰이 줄어도 요구사항 누락, 중복 검증의 불일치, 실패 처리 손실이 생기면 개선으로 판단할 수 없다.

## FS에서 적용을 검토할 조건과 반례

다음은 FS 검토 의견이며 원문의 실험으로 입증된 사실이 아니다.

| 검토 대상 | 단순화 후보 조건 | 유지할 이유 / 반례 |
| --- | --- | --- |
| 객체 생성 함수·어댑터 | 필드를 그대로 전달하고 별도 계약이 없음 | 런타임 검증, 기본값, 불변식, 외부 API 변경 격리가 있으면 의미 있는 경계다. TypeScript 타입만으로 외부 입력이 검증되지는 않는다. |
| 상수·공통 UI | 이름과 재사용이 실제 변경 의도를 설명하지 못함 | 도메인 의미, 접근성, 테마, 함께 바뀌어야 하는 값의 일관성은 공유할 이유다. |
| Context 연결 | 도메인 전용 컴포넌트까지 단순 전달만 반복함 | 범용 컴포넌트의 명시적 props는 재사용·테스트에 유용하다. Provider 의존성과 렌더링 영향도 살핀다. |
| 파일·계층 분리 | 책임 없이 이동 경로만 늘어남 | 보안, 서버/클라이언트, 번들, 팀 소유권, 독립 변경 경계는 파일 수보다 중요할 수 있다. |

기존 [함께 수정되는 파일](frontend-fundamentals-code-quality-cohesion-colocate-related-files.md) 자료와 탐색 비용 관점이 연결된다. [매직 넘버와 로직의 응집](frontend-fundamentals-code-quality-cohesion-couple-magic-numbers-with-logic.md)은 공유 값이 필요한 반례다. 별개 글이므로 기존 출처와 합치거나 덮어쓰지 않는다.

## 후속 검증 제안과 반영 상태

- 실제 변경 요청으로 전후 구현을 비교하되 같은 수용 기준·모델·도구 권한·문맥·캐시 조건을 사용한다. 탐색 파일 수·왕복·비용·시간과 함께 동작·오류 처리·회귀 결과를 기록한다.
- 국소 수정뿐 아니라 공통 정책 변경·기능 추가·결함 수정도 포함한다. 변경 전후 모두 실패할 수 있는 독립 수용 검사를 유지하고, 평균만이 아니라 편차와 실패 사례도 보고한다.
- 위 검증은 제안이며 이번 수집에서 실행하지 않았다. FS의 비용 절감률이나 코드 정확성 보장 수치로 사용하지 않는다.
- source와 catalog에 등록하는 단계다. 배포 참조에 반영하려면 `fs-knowledge sync`가 필요하며 기존 프로젝트의 승인된 정책은 바뀌지 않는다.
