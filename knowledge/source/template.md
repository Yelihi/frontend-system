## 출처와 맥락

- 작성일:
- 출처: 직접 작성 / 공식 문서 URL과 절 / 글 / 책과 쪽수 / 프로젝트 경험
- 기술·버전: 언어, 프레임워크, 관련 라이브러리; 모르면 미확인
- 실행 환경: 브라우저 / SSR / 서버 / 기타
- 적용 범위: 프로젝트 전용 / 공통 지식 후보
- 지식 성격: 공식 계약 / 확인한 사실 / 팀 결정 / 경험 / 선호 / 가설
- 읽거나 보존한 범위: 전체 / 요약 / 일부 및 누락 범위

출처의 주장, 자신의 해석, 실제 관측을 구분합니다. 프로젝트 사례는 공유 가능한
최소 코드로 정리하고 인증 정보·개인정보는 제외합니다.

## 배운 내용 또는 요구사항

- 해결하려는 문제와 도움이 될 질문 표현:
- 기대하는 동작:
- 발생하면 안 되는 동작:
- 유지해야 할 기존 동작과 제약:

예: 두 주문 폼은 독립적으로 제출할 수 있어야 한다. 같은 폼의 진행 중 중복
제출은 차단하고 실패 후에는 재시도할 수 있어야 한다.

## 문제 코드와 재현

- 최소 코드 또는 파일·커밋:
- 시작 조건과 실행 명령:
- 재현 순서:
- 기대 결과:
- 실제 결과와 로그:

현재 동작 자체를 정답으로 삼지 않고, 요구사항과 관측을 분리합니다.

## 원인과 수정

- 확인된 원인과 근거:
- 아직 확인하지 않은 가설:
- 수정 코드 또는 diff:
- 이 방법을 선택한 이유:
- 대안과 선택하지 않은 이유:
- 구현·운영·유지보수 비용:

예: React 함수 인자로 의존성을 전달하는 방식과 기존 tsyringe 컨테이너를 쓰는
방식은 프로젝트의 상태 소유권·수명·기존 구조에 따라 비교합니다.

## 적용 조건과 반례

- 적용하기 적절한 조건:
- 적용하면 안 되는 조건:
- 아무것도 바꾸지 않아도 되는 좋은 코드:
- 기술·버전·실행 환경이 달라지면 다시 확인할 부분:

예: 제품 요구상 여러 화면이 하나의 주문 작업을 공유해야 한다면 폼별 상태
격리가 적절하지 않을 수 있다. 코드 모양만 비슷하다고 같은 해결책을 강제하지 않는다.

## 검증

- 실행 명령과 환경:
- 수정 전 실패한 assertion 또는 진단:
- 수정 후 결과와 로그·검사 ID:
- 정상 사례 / 오류 사례 / 적용 제외 사례:
- 작성·수정에 사용하지 않은 별도 사례의 결과:
- 아직 확인하지 않은 범위:

테스트 기대값을 바꾸었다면 제품 계약이 바뀐 이유를 명시합니다. 미실행과 환경
실패를 통과로 기록하지 않습니다. 의견 일치와 실제 동작 검증은 구분합니다.

```text
실행 가능한 사례는 정상·오류·적용 제외 조건을 검증하고 결과를 구분해주세요.
공용 필수 규칙 후보는 별도로 제시해주세요.
```
