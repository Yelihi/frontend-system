# FS 비교 v2 — 절차 비용과 구현 품질 분리

상태: **자동·브라우저·독립 의미 리뷰 교정과 실제 독립 세션의 접근 차단/검사 실행 점검을 완료했다.** 실행 조건과 순서는 `v2/run.py`가 `v2/frozen.json` 및 결과 manifest에 고정한다. [준비 및 본 실험 결과](v2/README.md)를 참고한다. 기존 주문 수량 실험을 이 두 질문의 답으로 재사용하지 않는다.

## 두 질문과 비교 조건

| 실험 | 일반 AI | FS 조건 | 확인할 차이 |
| --- | --- | --- | --- |
| A. 최우선 규칙·검증 절차의 비용 | 프로젝트 분석 → project.md → plan.md → 구현 → 테스트 작성·실행 → 결과 기록을 직접 수행 | 같은 산출물·규칙을 FS의 계획·정책·검증·완료 절차로 수행 | 같은 완료 기준에 도달하기까지의 실제 토큰·시간·재시도 |
| B. Clean Code·Clean Architecture 구현 품질 | 제품 요구사항과 공개 설계 원칙을 받고 구현·검증 | 같은 제품 요구사항·공개 원칙을 받고 고정한 FS 스킬·지식·도구로 구현·검증 | 익명화한 결과 코드와 사전 정답지의 일치도, 결함과 불필요한 구조 |

A에서는 **양쪽 모두 같은 최우선 규칙 원문과 실행 가능한 검사 명령**을 받는다. 일반 조건도 필요한 검사를 자유롭게 실행할 수 있다. 규칙을 일반 조건에서 숨기거나 문서·테스트 작성을 생략시켜 FS와 비교하지 않는다. FS 조건에서는 해당 규칙을 required 정책·검증 근거·완료 조건에 연결한다. 규칙 내용의 효과와 자동 강제 효과를 혼동하지 않는다.

A는 이 절차 묶음의 효과를 측정한다. FS가 추가로 제공하는 맥락 수집·기록·MCP 스키마 비용도 포함한다. 이를 검증 도구 하나만의 인과 효과로 부르지 않는다. A에서는 별도 학습 지식·선택적 디자인 도구를 처리 조건에 추가하지 않으며, 실제 로드한 자료·호출 도구로 조건 준수를 확인한다. 필요한 절차와 분리할 수 없는 기능은 시작 전에 명시한다.

B는 FS 전체 사용 효과다. 양쪽에 같은 공개 설계 원칙과 배점표를 제공하되, 구체적인 정답·평가용 테스트·결함 변형·다른 실행 결과는 제공하지 않는다. B의 일반 조건에는 project.md·plan.md 작성을 의무화하지 않는다. A와 B의 토큰·품질 결과를 합쳐 하나의 절감률로 계산하지 않는다.

## 양쪽에 공개할 제품 과제

기존 Next.js 예제를 바탕으로 별도 checkout fixture를 준비한다. 가격 판단, 서버 신뢰 경계, 원격 견적의 비동기 상태, 테스트 대체 가능성이 함께 드러나는 과제다. fixture의 초기 화면·API·공개 테스트·허용 변경 범위는 본 실험 전에 확정한다. 기존 v1의 단일 quantity API를 암묵적으로 새 계약에 덮어쓰지 않는다.

- 상품 A는 12,000원·재고 10개, B는 8,000원·재고 4개다. 장바구니 기본값은 A 1개, B 0개이며 0개 상품은 요청에서 제외한다.
- 요청 형식은 `{lines: [{productId, quantity}], coupon}`이다. 각 요청 수량은 숫자 정수 1~10, 상품 ID는 중복 불가, 빈 장바구니는 불가다. coupon 생략·빈 문자열은 할인 없음이다.
- `SAVE10`은 상품 합계의 10%를 원 단위 내림해 할인한다. 할인 후 상품 금액이 50,000원 이상이면 배송비 0원, 미만이면 3,000원이다. `SHIPFREE`는 상품 할인 없이 배송비만 0원이다. 쿠폰은 한 개만 받고 코드의 대소문자를 구분한다.
- POST `/api/quote`는 견적, POST `/api/orders`는 주문을 처리한다. 서버가 상품 가격·재고를 조회하고 계산한다. 클라이언트의 가격·할인·합계 필드는 거부하거나 무시하고 절대로 신뢰하지 않는다.
- 잘못된 JSON·자료형·수량·상품·쿠폰·중복 상품·빈 목록은 400, 수량은 유효하지만 재고가 부족하면 409다. 유효한 주문은 `{accepted: true, quote}`를 반환한다. quote의 공개 필드는 `subtotal`, `discount`, `shipping`, `total`이다.
- UI는 상품별 수량과 쿠폰을 변경하고 원격 견적을 표시한다. 입력 변경 시 이전 견적을 무효화하고 최신 입력의 응답만 반영한다. 오래된 성공·실패 응답 모두 최신 화면을 덮어쓰면 안 된다. 견적 대기·실패 상태에서는 주문할 수 없다.
- 주문 중에는 입력과 제출을 잠그고 중복 요청을 막는다. 실패하면 입력을 유지하고 재시도할 수 있으며, 성공하면 이전 오류를 제거한다. 견적 실패도 입력을 유지한 채 재요청할 수 있어야 한다.
- 접근 가능한 이름은 `Quantity A`, `Quantity B`, `Coupon`, `Total`, `Place order`, `Retry quote`다. 수량은 number input, 제출은 form을 사용하며 Coupon은 select 또는 text input을 허용한다. 주문 성공은 `Order received`로 표시한다. 오류는 `Checkout error`라는 이름과 alert 또는 aria-live를 제공하고, 해소하면 메시지를 비우거나 표시를 제거한다. 키보드 조작, 오류 전달, 360px 가로 넘침을 확인한다. Total은 이름이 있는 output 요소다. 특정 암묵적 role·DOM 위치·CSS 선택자를 추가로 요구하지 않는다.
- 실제 결제·재고 차감·인증·DB·외부 서비스 연동은 범위 밖이다. 새 상태 라이브러리·DI 컨테이너·범용 플러그인 구조는 요구하지 않는다.

## 공개할 최우선 규칙과 설계 원칙

아래는 이 fixture에 적용하는 계약이다. 모든 프로젝트의 유일한 Clean Architecture 정의로 일반화하지 않는다. FS의 [공통 규칙](../../../mandatory-rules/common/review.md)과 [품질 기준](../../../references/frontend-quality.md)을 사례별로 구체화한다.

| ID | 양쪽에 공개할 규칙 | 관측할 근거 |
| --- | --- | --- |
| R1 | 가격·할인·배송·유효성 판단은 UI·HTTP·스토리지 없이 실행 가능해야 한다 | 실제 업무 함수에 직접 경계값·대체 상품 데이터를 입력 |
| R2 | 계산 규칙은 한 곳에서 정의하고 견적·주문 경로가 사용해야 한다 | 실제 두 호출 경로와 중복 분기 확인; UI 입력 검증과 서버 검증 자체는 중복 결함이 아님 |
| R3 | 서버는 신뢰할 수 있는 가격·재고로 재검증한다 | 변조된 가격·합계와 재고 부족 요청 |
| R4 | UI·요청 조정·업무 판단·외부 I/O의 책임과 의존 방향을 구분한다 | 도메인의 React/Next/fetch/storage 의존 여부와 실제 호출 그래프 |
| R5 | 합계는 불필요하게 복제하지 않으며 원격 견적은 요청 입력과 함께 식별한다 | 상태 소유권, 파생값, 이전 입력 응답의 처리 |
| R6 | 중복 요청·오래된 응답·실패 후 복구·접근성 기본을 보존한다 | 지연 성공/실패, 빠른 재입력, 재시도, 키보드 시나리오 |
| R7 | 요구한 기능에 필요한 구조만 추가한다 | 각 계층·추상화의 실제 호출자와 보호하는 변경 이유 |
| R8 | 기존 검사의 보장을 보존하고 수정한 업무 계약을 실제 테스트한다 | 정상/위반 예제, 공개 검사 및 독립 채점; 테스트 개수 자체는 점수가 아님 |
| R9 | 현재 소스에서 실행한 근거로만 완료를 보고한다 | 마지막 제품 변경과 검사 순서·소스 해시·실제 실행 로그 |

## A: 산출물 동등성과 비용 계산

두 조건에 같은 문서 내용 계약을 준다. project.md에는 현재 구조·실제 진입점·검사 명령·제약, plan.md에는 변경 범위·책임 배치·규칙별 검증 계획, 최종 기록에는 실행 명령·결과·미확인 범위를 요구한다. 파일 길이·문체는 강제하지 않는다. FS의 네이티브 기록 경로를 허용하며 같은 문서를 다른 경로에 중복 작성시키지 않는다. FS 내부 관리 파일은 제품 품질 점수에서 제외하지만 작성·조회 토큰은 포함한다.

**적격 완료**는 문서 내용 계약, 공개 기능 계약, R1~R9의 필수 보장과 보호된 검사에 대한 외부 판정을 모두 충족한 상태다. FS의 자체 complete나 모델의 성공 선언만으로 판정하지 않는다. 미실행은 통과가 아니다. 동일 완료 기준을 만족하지 않은 실행의 짧은 답변을 절감으로 인정하지 않는다.

- 실제 입력·캐시 입력·출력·제공되는 추론 토큰, 총 토큰(input + output), 비캐시 입력(input − cached input), wall time을 모델별로 기록한다. 캐시와 추론을 중복 합산하지 않는다.
- 실행 전체 비용에는 최초 문서/정책 준비, 도구 설명·결과 읽기, 구현·테스트, 거부된 호출과 자체 수정, 최종 검증·기록을 포함한다. 준비 비용을 FS 조건에서만 제외하지 않는다.
- 회차별 값, 중앙값·범위, 적격 완료 수/시도 수를 함께 제시한다. `절감률 = 1 − FS 총 토큰 중앙값 / 일반 총 토큰 중앙값`이며 음수는 증가다. 완료율·품질이 다르면 이 수치만으로 효율 우위를 선언하지 않는다.
- 보조값 `전체 시도 토큰 합 / 적격 완료 수`는 실패 비용을 포함한다. 적격 완료가 0이면 산출 불가다. 성공한 실행만 골라 집계하지 않는다.
- 문서/구현/검증 단계별 토큰은 제공자가 실제 사용량을 나누어 반환할 때만 보고한다. 문자 수나 도구 호출 수를 토큰으로 환산하지 않는다. 단계별 실측이 없으면 전체 토큰과 단계별 호출·시간을 구분한다.
- 이번 A는 처음부터 작성하는 비용이다. 누적 기록 재사용에 따른 절감·손익분기점을 이 결과로 주장하지 않는다.

## B: 구현 품질 채점

기능·신뢰 경계·접근성의 필수 실패를 별도로 표시한 뒤 설계 점수를 낸다. 필수 실패를 가독성 점수로 상쇄하거나 FS 문서가 많다는 이유로 코드 점수를 올리지 않는다.

| 기준 | 배점 | 각각 5점인 두 확인 항목 |
| --- | --- | --- |
| Q1 업무 규칙 독립성 | 10 | React/HTTP 없는 실행 / 상품·재고 데이터를 바꿔 실행 가능 |
| Q2 규칙 단일 정의 | 10 | 견적·주문이 같은 계산 규칙 사용 / 할인·배송 판단을 다른 경로에 재구현하지 않음 |
| Q3 의존 방향 | 10 | 업무 코드가 UI·프레임워크·구체 I/O에 의존하지 않음 / I/O 연결이 바깥 경계에 있음 |
| Q4 응집도 | 10 | UI가 가격 정책·서버 신뢰 판단을 소유하지 않음 / 전송 코드와 업무 결정의 책임이 식별 가능 |
| Q5 상태 소유권 | 10 | 불필요한 전역 장바구니·파생 합계 복제 없음 / 원격 견적·입력·오류의 수명과 소유자가 명확함 |
| Q6 비동기·오류 설계 | 10 | 오래된 성공과 실패 모두 무시 / 잠금 해제·입력 보존·재시도가 일관됨 |
| Q7 코드 이해 가능성 | 10 | 이름·자료형이 단위와 의미를 드러냄 / 검증·정상·오류 흐름을 불필요한 간접 호출 없이 추적 가능 |
| Q8 구조의 필요성 | 10 | 사용하지 않는 확장점·서비스·추상화 없음 / 새 의존성·계층마다 현재 요구에서 확인되는 역할이 있음 |
| Q9 테스트 실효성 | 10 | 실제 업무 로직이 경계·오류 계약으로 검증됨 / 경계 통합·비동기 전이가 구현 자체 mock 없이 검증됨 |
| Q10 변경 영향 | 10 | 배송 기준 변경이 정책 소유 위치에 한정됨 / 상품 조회 대체가 UI·순수 계산의 재작성 없이 가능 |

각 5점 항목은 증거 충족 5, 위반 0, 판정 불가 U다. 누락·중단으로 필요한 코드가 없는 항목은 0, 평가 도구의 고장이나 판단 불일치는 U로 기록한다. U가 있으면 100점 만점의 확정 점수를 발표하지 않는다. Q10은 숨겨진 고정 정책 변형·대체 I/O로 확인하며 수정 LOC만으로 판단하지 않는다. 허용되는 대안과 반례는 정답지에 고정한다.

평가자는 모델명·조건·실행 순서를 제거한 제품 코드·테스트와 공통 명세를 받는다. FS 기록·자체 평가 답변은 설계 채점에서 숨기며 문서/절차 평가는 별도로 한다. 자동 검사와 근거를 요구하는 익명 코드 리뷰를 결합한다. 작성 세션이 자신의 구현을 채점하지 않는다. 리뷰 판단 차이는 보존하고 같은 정답지로 독립 재판정하며, 새 기준을 사후 추가하지 않는다. 코드 특징으로 조건을 추측할 수 있으므로 완전한 블라인드를 주장하지 않는다.

## 시작 전에 끝낼 준비

1. checkout fixture와 양쪽 공통 공개 검사, 평가자 전용 외부 검사를 작성한다. A/B 프롬프트와 허용 파일·도구·자료 목록을 각각 고정한다. 현재 v1 run.py/score.mjs는 이 명세의 실행기가 아니다.
2. 정답지의 서로 다른 정상 구현 두 가지와 결함 변형을 채점해 정상 대안을 오판하지 않고 의도한 결함만 검출하는지 확인한다. 모델 본 실험 결과를 보고 채점기를 조정하지 않는다.
3. fixture·프롬프트·규칙·FS 버전·채점기·정답지·환경·실행 순서·제한 시간을 해시로 고정한다. 초안 단계에서는 고정 완료나 평가 구현 완료로 표시하지 않는다.
4. 구현 세션에서 정답지·외부 테스트·이전 결과를 읽을 수 없도록 파일/도구 접근을 분리하고 접근 차단을 실제 확인한다. 경로만 숨기거나 읽지 말라는 지침만으로 블라인드가 보장됐다고 하지 않는다. 현재 호스트 권한을 넓히는 방식으로 해결하지 않는다.
5. 양쪽의 빌드·브라우저·검사 실행 가능성을 같은 권한으로 사전 확인한다. 불가능하면 본 실험을 시작하지 않는다. 과거 실험의 full-access 설정을 현재 권한에 그대로 재사용하지 않는다.

현재 fixture는 `checkout.contract.json`에 실제 업무 함수의 module/export를 등록한다. 공개 호출 계약은 `(input, catalog 배열) → {subtotal, discount, shipping, total}`, 유효성 실패는 status 400/409를 가진 Error다. 파일 배치는 자유이며 실제 제품이 사용하지 않는 채점 전용 함수를 허용하지 않는다. `src/catalog.js`의 `loadCatalog()`와 두 `app/api/*/route.js`의 `POST(Request)`를 유지한다. package/lockfile·설정·공개 기존 테스트 9개는 보호하며 제품·추가 테스트·기록은 수정 가능하다. 완전한 공개 프롬프트는 `prepare.py --experiment A|B`로 생성한다. 현재 `typecheck`는 `checkJs:false`인 JS/JSX 구문·모듈 검사로, 엄격한 정적 타입 보장을 뜻하지 않는다.

최초 비교는 Astra·Sol·Luna, 동일 medium, 조건별 3회로 설계한다. A 18회와 B 18회를 **별도로** 집계한다. 모델 이용 가능성과 동일 설정 지원은 실행 시 확인하며 대체 모델을 조용히 섞지 않는다. 모든 실행은 새 세션·동일 초기 소스·독립 파일 사본으로 시작하고 project.md·plan.md·FS 기록·빌드/테스트 산출물도 초기화한다. 순서는 미리 정해 교차 배치하고, 양쪽의 시간·수정 기회 제한을 같게 둔다.

본 실험 중 채점 오류가 발견되면 버전 전체를 보류한다. 교정 후 같은 버전의 모든 보존 결과물에 외부 채점을 다시 적용하거나, 정답 노출 등 통제가 깨졌으면 양쪽을 새 버전으로 재실행한다. 원점수·수정 이유·새 점수를 모두 남기고 유리한 실행만 교체하지 않는다. 모델 실패·규칙 위반·시간 초과는 결과이며 재측정 사유가 아니다. 인프라 제외는 사전 기준·증거·원자료와 함께 따로 기록한다.

## README 결과표 형식

- A: 모델 / 조건 / 회차별 토큰 / 중앙값·범위 / 비캐시 입력 / 시간 / 적격 완료 / 전체 시도 비용÷적격 완료 / 절감률.
- B: 모델 / 조건 / 필수 실패 / Q1~Q10 근거와 점수 / 판정 불가 / 고정 결함 탐지 / 정책·I/O 변경 영향 / 회차별 결과.
- 미실행 값은 빈칸이나 0점으로 채우지 않고 미실행으로 쓴다. 두 실험의 결론을 분리하고 원자료·코드 diff·검사 결과·판정 근거를 연결한다.

## v2 실행 환경 고정 보충

- 같은 설치 의존성의 독립 복사본, 새 ephemeral Codex 세션, medium, 회차당 900초, 최대 세 번의 전체 구현/수정 시도를 사용한다. A 18회 후 B 18회이며 반복마다 모델 순서와 조건 선후를 교차한다. 상세 순서는 frozen manifest가 기준이다.
- 명령과 FS MCP는 같은 제한 파일 권한을 사용한다. 평가 저장소의 정답지·채점기·이전 결과는 직접 읽기·심볼릭 링크·MCP에서 EPERM을 확인했다. macOS의 Chromium IPC 제약 때문에 저장소 읽기가 차단된 별도 Chromium에 localhost Playwright 연결을 사용한다. 브라우저 file URL 접근 차단도 확인했다. 이는 해당 경계의 실측이며 완전한 VM 격리 주장은 아니다.
- 양쪽에 동일한 `mandatory-rules/` 원문을 제공한다. A의 FS는 계획·정책·검사·완료 도구만 노출하고 `references/learned` 및 source knowledge를 제공하지 않는다. 분리 불가능한 절차 설명·기본 설계/검증 지침의 비용은 포함한다. B의 FS에는 현재 전체 지식 스냅샷과 MCP를 제공한다. 실제 호출·읽기는 실행 로그로 확인한다.
- 설치된 전역 스킬은 설정에서 비활성화하고 개인 설정·메모리·플러그인·앱·웹 검색·하위 모델을 사용하지 않는다. CLI가 유효하지 않은 전역 스킬 하나의 파싱 경고를 출력하는 사실은 준비 기록에 남겼다. 준비 세션과 구현 세션의 사용량은 분리한다.
- 양쪽의 Next 파일 감시는 같은 `WATCHPACK_POLLING=true`를 사용한다. 공개 검사와 업무 계약은 유지한다. 직접 POST 채점은 fixture의 `@/*` 별칭과 Next의 확장자 생략 import를 해석한다. NextResponse·별칭을 사용한 정상 변형도 본 실행 전에 전체 110개 사례로 교정했다.
