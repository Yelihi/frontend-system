# FS 비교 v3 — 코드 기준 충족과 수정 여정

상태: **원문 검토 게이트와 판정기를 구현·검사했고, 실제 gpt-6-sol 한 쌍을 실행함. 일반 AI는 세 단계 완료, FS는 마지막 단계에서 300초 시간 초과.** v2 결과/정답지/원로그는 변경하지 않는다. v3는 질문에 따른 정보 획득과 후속 변경을 포함하는 별도 실험이며 v2와 직접 합산하지 않는다. [작동 설명](../../../../docs/fs-runtime-guide.md)을 먼저 검토한다.

반례를 함께 준비했으며 내부 구조를 문제지에서 정하지 않는다. 로컬 회귀 검사 4개는 통과,
새 브라우저 교정·모델 비교는 격리 오류로 미실행이다. 질문 뒤 전체 답변을 동일하게 제공하는
통제 조건이므로 아래의 선택적 상호작용 실험 전체를 완료한 것은 아니다.

## 판정 질문

1. FS가 프로젝트에 합의한 좋은 코드 기준을 얼마나 충족하는가?
2. 지식의 원문→참조 변환과 코드 맥락→참조 선택·채택이 적합한가?
3. 초기 질문·분석 비용이 후속 변경·결함 수정의 횟수와 누적 비용 감소로 회수되는가?

우선순위는 **기능 필수 조건과 코드 기준 충족 → 불필요한 변경 억제 → 수정 횟수 → 누적 토큰·시간**이다. 비용 감소는 가설이며 질문·문서·검사가 증가한 비용도 전부 포함한다. 질문이 많거나 참조를 많이 읽었다는 이유로 점수를 주지 않는다.

## 비교 조건

| 트랙 | 양쪽 조건 | 판정 가능한 내용 |
| --- | --- | --- |
| equal-information | 같은 확정 요구·답변·코드 기준·공개 검사. 일반 AI도 같은 기준을 볼 수 있음 | 동등한 정보에서 FS의 적용·검증·유지보수 효과 |
| interactive | 같은 초기 요청과 비공개 고정 답변집. 양쪽 모두 질문 가능 | 질문 선택, 정보 확보, 합의 후 구현까지의 실제 절차 효과 |

interactive는 질문에 따라 획득 정보가 달라질 수 있다. 이를 알고리즘 단독 효과라고 부르지 않는다. 어떤 정보를 얻었는지 답변 ID·실제 질문·턴·제공 시각을 기록한다. 답변집은 구현을 암시하지 않는 제품 의도·제약만 포함한다. 답변집 밖의 질문에는 동일한 미확정 답변 정책을 적용한다. 운영자가 FS에만 유리한 조언을 추가하지 않는다. 자연 사용자와의 탐색 사용은 별도 사례 연구로 기록하고 통제 비교와 합산하지 않는다.

## 코드 기준과 정답지

실행 전에 각 과제에 적용되는 기준을 사용자와 확정하고 manifest에 고정한다. 평가 후 기준을 완화하거나 비적용으로 바꾸지 않는다. 정답은 특정 파일 트리가 아니라 관측 가능한 보장과 허용되는 여러 구현이다.

| 기준 | 구현에서 확인할 근거 | 잡아야 할 결함 변형 |
| --- | --- | --- |
| 업무 판단·신뢰 경계 | 실제 진입점부터 순수 업무 판단까지의 호출 경로, 변조 입력 처리 | UI/HTTP/구체 I/O에 업무 규칙 종속, 클라이언트 값 신뢰 |
| 상태 소유권·수명 | 상태 원본, 파생값, 무효화, 성공/실패 전이 | 불필요한 복제, 같은 논리 입력의 대기 정체, 오래된 실패 반영 |
| 의존 방향·변경 국소성 | 실제 대체 I/O 실행, 정책 변경의 영향, 중복 판단 | 쓰이지 않는 주입 지점, 두 경로의 정책 불일치 |
| 필요한 구조만 유지 | 추가 helper/계층의 실제 호출자와 보호하는 보장 | 미사용 factory, 요구와 무관한 추상화, 불필요한 전면 재작성 |
| 실패·복구·접근성 | 재진입, 지연, 오류, 복구, 키보드/이름의 실제 행동 | 잠금 누락/미해제, 대기 중 제출, 상태에 따라 깨지는 이름 |
| 검사의 실효성·근거 정직성 | 중요한 반례의 탐지, 최종 소스 검사, 모델 보고와 원로그 일치 | 정상만 보는 약한 검사, assertion 삭제, 미실행 만점 선언 |

각 항목은 passed/failed/unverified와 파일·실행 근거로 판정한다. 미검증은 통과가 아니다. 독립 리뷰에서는 일반/FS 조건을 가리고 동일 기준을 사용한다. 과제와 관계없는 프레임워크 지식을 채택하지 않는 것도 올바른 판단이다. FS 고유 로그를 남겼는지는 제품 코드 품질 점수로 쓰지 않는다.

기능 필수 실패가 있으면 적격 완료가 아니다. 종합 품질 점수를 만들지 않고 기능/필수 기준의 개별 판정과 미검증 상태를 나란히 표시한다. v2의 Q100이 제품 실패를 가리는 문제를 반복하지 않는다.

## 과제와 단계

전체 실험의 후보는 기존 checkout의 초기 fixture와 외부 행동 검사다. 이번에 실행을 준비한 최소 파일럿은 별도의 DOM 없는 checkout controller이며 아래 maintenance 기록으로 구분한다. v2 기준을 덮어쓰지 않고 v3에서 별도 합의·해시 고정한다. 검색/상태 변경 과제와 유지가 정답인 작은 UI 과제를 추가 평가용으로 분리하며, 해당 fixture·반례 교정 전에는 준비 완료로 표시하지 않는다.

한 여정은 `initial`(요구 구체화·첫 구현), `change`(사전 고정한 정책/I/O 변경), `repair`(독립 평가가 찾은 실패의 동일 형식 피드백과 수정)로 구성한다. 원래 요구를 위반한 수정과 새 요구 구현은 다른 횟수로 센다. 처음부터 실패가 없으면 repair 단계는 변경 없음으로 기록하고 실제 사용량만 집계한다. 취향에 따른 추가 수정은 통제 실험에 섞지 않는다.

모델·트랙·반복·arm마다 새 원본/의존성/컨텍스트로 시작한다. **여정 내부는 이전 단계의 코드와 합의 기록을 이어간다.** 이는 후속 비용을 측정하기 위한 통제 조건이다. 새 세션에서의 복원 비용은 별도 resume 트랙으로 평가하고 같은 표의 비용과 섞지 않는다. 일반 AI도 자체 문서·검사·대화를 유지할 수 있다.

기존 세 모델의 정확한 ID·추론 설정은 새 manifest에 기록한다. 각 셀 최소 3회와 교차 실행을 시작 기준으로 하되 표본이 작다는 한계를 유지한다. 에피소드·단계 예산, 답변 정책, 도구·네트워크 권한, 지식/Skill/fixture/채점기 해시, 실행 순서를 **실행 전에** 고정한다. FS에만 시간을 연장하지 않는다.

## 수집 항목

- 제공자의 실제 input/cachedInput/output, 제공되면 reasoning. 총 토큰은 input+output이고 캐시·추론을 다시 더하지 않는다. 누락은 null이다.
- 준비/질문/첫 구현/검증/수정/후속 변경의 턴 구간. 제공자가 턴별 사용량을 주지 않으면 단계별 토큰을 추정하지 않는다. 단계 total을 누적 전체 total과 중복 합산하지 않는다.
- productEditRounds: **판단→제품 변경 묶음→검사/리뷰** 한 회. 파일 저장 횟수·apply_patch 호출 수를 수정 횟수로 대신하지 않는다. raw diff·소스 hash와 연결한다.
- repairRounds: 원래 합의한 기준 실패를 고치는 변경 묶음. 새 요구 변경과 분리한다. FS MCP attempt 수는 별도 보조값이다.
- 검사 실행 수와 시간, 동일 소스 반복 검사, 도구 호출 실패, 반환 문자 수. 문자 수는 토큰 대체값이 아니다.
- 질문 수, 중요한 미확정 사항의 해소 여부, 답변 ID, 실제 사용자 시간. 고정 답변 시뮬레이션은 실제 사용자 노동 시간으로 계산하지 않는다.
- 지식의 후보 노출/본문 열람/조건 판정/채택/코드 반영/반례 근거. 로그에 없는 적용은 미확인으로 남긴다.

결과표는 모델·트랙별 초기 품질/후속 품질/적격 여정 수/수정 횟수/초기 토큰/누적 토큰/사용자 시간을 표시한다. 실패·시간 초과를 포함한다. 모든 사용량을 받은 경우에만 전체 토큰÷적격 여정 수를 계산한다. 적격 0이면 산출 불가다. 손익분기점은 **동등 기준을 충족하는 단계까지의 실제 누적값**으로만 계산한다.

## sync 자체의 별도 평가

작은 고정 원본 묶음에 사실·조건·버전·반례·상충 경험·부분 수집·정정/삭제를 포함한다. 평가자가 원문별 필수 보존 주장과 금지된 과장을 사전에 작성한다. 원문 해시 통과와 의미 충실도를 별도로 판정한다. 관련/무관/제외 기술/검색 없음 사례를 두고 검색 회귀용과 평가용을 분리한다. 이후 실제 코드의 상태·이벤트·기술에서 적합한 참조와 비적합 참조를 고정한다.

현재 기존 지식 69개 전체의 의미를 새로 검토했다고 주장하지 않는다. 기존 인덱스에는 retrievalChecks가 없었으며, 이번에 기존 개발용 검색 사례에서 7개를 연결했다. 이는 독립 평가용 정답지가 아니며 전체 참조의 의미 검토를 대체하지 않는다. 사례가 없는 인덱스는 미검증 경고로 남는다. 정확히 변환됐더라도 잘못 적용될 수 있으므로 sync 평가와 적용 평가를 합친 한 점수만 제시하지 않는다.

## 집계 도구와 실행 전 남은 준비

`score.mjs`는 독립 평가자가 작성한 `manifest.json`과 `journey.json`의 집계기다. 소스의 좋고 나쁨을 자동 추론하는 채점기가 아니다. manifest는 `{version:3, stages:[{id, criteria:{기준ID:{weight,required}}}], ...고정조건, hash}`이며 hash를 제외한 객체의 JSON.stringify 결과에 SHA-256을 계산한다. journey는 manifestHash/model/replica/arm/track/stages를 갖는다. 단계 필드는 [검사 예제](score.test.mjs)에 있다. 실제 evidence 경로·원로그 검토는 독립 평가자의 책임이다.

```sh
node --test test/evals/fs-comparison/v3/score.test.mjs
node test/evals/fs-comparison/v3/score.mjs manifest.json journey.json
```

`score.mjs`의 가중 점수는 과거 집계기 기능이며 새 파일럿 결과에는 사용하지 않는다.

현재 완료: 코드 개선, 원문 검토 게이트, 회귀 검사, 평가 설계, [유지보수 파일럿](maintenance/README.md)의 계약/실행기/판정기와 반례 교정(정상 3/3·결함 21/21), 실행 시도의 manifest와 로그. 초기 격리·실행기 오류를 수정한 뒤 실제 한 쌍을 실행했고, 일반 AI는 세 단계 완료, FS는 두 단계 통과 후 마지막 단계 시간 초과였다. 이 기존 결과는 단계마다 새 컨텍스트에서 코드·문서를 복원한 조건이다. 이후 여정 내부의 세 단계/재수정은 같은 대화를 재개하도록 실행기를 수정했고, 누적 토큰의 중복 합산도 방지했다. 로컬 회귀 검사 6개는 통과했으며 새 조건의 실제 비교는 아직 미실행이다. [실제 결과와 설계 오류 해석](maintenance/README.md)을 새 조건 및 준비용 교정 결과와 구분한다. 사용자 응답 선택을 포함한 전체 상호작용 평가는 여전히 별도다.

미완료: 다중 모델 반복 비교, 전체 UI/아키텍처 독립 리뷰, 고정 답변집과 대화를 유지하는 상호작용 실험, 실제 사용자 경험 측정. 연결 실패는 모델 품질 실패가 아니고, 판정기 교정은 FS의 성능 증거가 아니다. v2 원자료는 수정하지 않았다.
