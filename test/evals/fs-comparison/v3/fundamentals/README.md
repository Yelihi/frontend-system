## 이번 과제가 묻는 것

기존 checkout 파일럿은 문제지에서 순수 정책 함수와 controller 분리까지 정했다. 이번에는 실제 [React 주문 화면](fixture/App.jsx)의 공개 입출력만 유지하고, 내부 함수·상태·컴포넌트·파일 배치는 모델이 결정한다. 일반 주문과 선물 주문이 같은 화면에 있고 입력, 검증, 견적, 분석 이벤트, 주문, 실패·재시도를 다룬다. 단순한 정책 숫자 변경만 평가하지 않는다.

현재 코드는 한 컴포넌트에 두 폼 상태와 이벤트 흐름이 함께 있다. 예를 들어 아래 함수는 견적과 분석 전송을 함께 수행한다.

```js
async function getQuote(api, values) {
  const quote = await api.quote(values);
  await api.track('quote-viewed', values);
  return quote;
}
```

이를 무조건 분리해야 정답이라고 정하지 않는다. 분석 이벤트가 기존 계약인 경우를 보존하고, 분석 실패가 주문 실패로 번지는 것은 막아야 한다. 같은 모양의 두 폼도 실제 정책 관계에 따라 공통화/분리의 판단이 달라질 수 있다.

## 실제 저장된 지식과 판정의 연결

원격 문서를 새로 수집하거나 지식·Skill을 수정하지 않았다. [scenario.json](scenario.json)의 sourceIds는 저장된 Frontend Fundamentals 원문 요약 6개를 가리킨다. 원문 전문이 아닌 기존 요약이며 신규 구조화 리뷰 기준에서는 legacy-unreviewed다. 평가용으로 읽었다고 일괄 승인하거나 sync 상태를 바꾸지 않았다.

| 저장된 지식 | 이번 과제에서 관찰할 내용 | 과잉 적용을 막는 반례 |
| --- | --- | --- |
| 좋은 코드를 위한 4가지 기준 | 가독성·예측 가능성·응집도·결합도의 근거 | 하나의 종합 점수나 보편적 파일 구조로 환산하지 않음 |
| 로직 종류에 따라 합쳐진 함수 쪼개기 | 각 폼의 상태·견적·제출 흐름을 실제 호출 경로로 설명할 수 있는지 | 함수/Hook 분리만으로 렌더 성능 향상을 주장하지 않음 |
| 같은 종류의 함수는 반환 타입 통일하기 | 반환 계약과 호출자의 판단이 일치하는지 | quote의 금액 응답과 submit의 주문 ID는 의미가 다르므로 억지 통일하지 않음 |
| 숨은 로직 드러내기 | 분석 이벤트의 시점과 실패 영향이 합의와 일치하는지 | 견적 분석이 기존 계약인 일반 주문/shared 조건은 보존 |
| 폼의 응집도 생각하기 | 수량과 MEMBER 쿠폰의 관계 검증이 같은 정책 변경과 함께 갱신되는지 | 선택 메시지를 필수화하거나 모든 필드를 같은 검증 규칙으로 묶지 않음 |
| 중복 코드 허용하기 | 독립 정책 변경이 다른 주문을 바꾸지 않는지 | 같은 정책이면 두 진입점이 함께 변경되어야 함. 중복 제거·허용 어느 한쪽을 강제하지 않음 |

연결된 배포 참조는 `code-quality-context-and-contracts`, `code-quality-change-boundaries`다. 이 ID와 평가자가 기대하는 판단은 모델 요청에 정답으로 넣지 않는다. [개발용 검색 진단](routing-probe.json)에서는 이 React 코드의 정적 접근성·상태 트리거와 한국어 질문에 대한 코드 품질 참조 검색을 확인했다. 작성자가 고른 질문이므로 독립 정확도나 모델의 올바른 채택을 입증하지 않는다.

## 두 제품 조건

| 조건 | 첫 계획 뒤 전달하는 제품 의도 | 후속 변경 |
| --- | --- | --- |
| independent | 일반/선물 할인은 독립 운영. 선물은 주문 성공 뒤 gift-ordered, 일반은 기존 quote-viewed 계약 유지 | MEMBER는 일반 주문에만 추가. 선물 SAVE/빈 쿠폰은 그대로 |
| shared | 두 주문이 같은 할인 정책. 두 주문 모두 기존 quote-viewed 계약 유지 | MEMBER를 두 주문에 함께 추가 |

공통으로 분석 전송 실패가 주문을 막으면 안 되며, 선택 선물 메시지와 두 폼의 독립 입력·대기 상태를 보존한다. 구현 방법은 지정하지 않는다. 공개 API 주입 지점은 기존 화면의 통합 경계이며, 내부에 특정 계층이나 순수 함수 export를 새로 만들도록 요구하지 않는다.

## 비교 조건과 정보 통제

| 조건 | 접근 가능한 지식 | 절차 |
| --- | --- | --- |
| plain | 기존 코드와 제품 요구·동일한 제품 답변 | 일반 모델의 계획·구현 |
| knowledge | plain + FS와 같은 전체 배포 지식/공통 규칙 | 일반 모델의 계획·구현 |
| fs | knowledge + FS Skill/MCP | fs-plan → fs-work |

plain 대 fs는 전체 사용 경험의 차이이고, knowledge 대 fs는 동일한 지식에 FS 절차를 추가한 차이다. 이 둘을 같은 효과라고 부르지 않는다. FS에서만 반환된 트리거, 인용 오류, 후보 0개, 참조 열람 및 체크 판단 도구 호출을 `knowledgeTrace`로 기록한다. 쉘을 통한 직접 본문 읽기와 의미적 적용은 원로그·코드 리뷰가 더 필요하며 도구 호출만으로 채택 완료를 선언하지 않는다.

질문 능력과 구현 정보량을 구분하기 위해 **첫 질문 뒤 양쪽에 동일한 고정 답변 전체를 제공**한다. 어떤 질문을 했는지 따로 판정하되, 질문하지 않은 사실도 구현 전에 동일하게 알게 된다. 이 조건은 질문마다 필요한 답만 선택적으로 돌려주는 완전한 상호작용 실험이 아니다. 자연 사용자 시간 절감도 측정하지 않는다.

실제 모델 호출 순서는 다음과 같다.

```text
새 저장소·새 대화
  → questions: 기존 코드 분석, 필요한 질문과 대안
  → plan: 고정 제품 답변을 반영한 최종 계획
  → work-initial: 모의 사용자의 구현 승인 후 구현·검사
  → plan-change: MEMBER 요구의 영향 분석과 수정 계획
  → work-change: 모의 승인 후 후속 구현·검사
```

같은 여정에서는 명시적인 동일 thread ID를 재개한다. 조건·제품 프로필이 바뀌면 저장소와 대화를 초기화한다. 계획 턴에서 제품 파일의 최종 해시가 달라지거나 새 제품 파일이 생기면 그 여정을 protocol-failed로 끝내며 work를 시작하지 않는다. 순간 수정 후 원복 등은 원로그 리뷰도 필요하다. 고정 답변의 모의 승인 기록을 실제 사용자의 선택이나 노동 시간으로 설명하지 않는다.

기존 격리·MCP·프로세스 정리·누적 토큰 차감 실행기를 재사용한다. 기본 호출 제한은 양쪽 모두 300초, 행동 검사 실패 뒤 같은 대화에서 단계당 최대 1회 재수정이다. 프로필별 실행 순서를 교차한다. 기본은 한 모델에 조건 3개 × 프로필 2개, 최소 30회 모델 호출이며 이는 반복 통계가 없는 개발 파일럿이다. 질문·계획·수정 비용도 모두 포함한다. timeout/누락은 0 토큰으로 대체하지 않는다.

## 판정

자동 행동 검사는 최초 14개, 후속 18개다.

- 기존 SAVE와 선택 메시지, 수량/이메일/쿠폰 전달, 서버 견적 금액 사용
- 제품 조건에 따른 분석 이벤트 종류·순서, 분석 실패 격리
- 견적/주문 실패 뒤 입력 보존과 재시도
- 같은 폼의 중복 요청 차단과 다른 폼의 독립 진행
- MEMBER의 대상·수량 관계와 선물 기존 동작 보존
- 이미 정상인 money.mjs 유지

브라우저 판정기는 격리한 broker를 통해 실제 React 이벤트를 실행한다. 실제 네트워크는 막고 API 응답을 통제한다. 브라우저가 없으면 unverified이며 다른 검사로 대체 통과시키지 않는다. 빌드 오류는 수정 가능한 제품 실패다. 정상 참조 4종과 결함 변형 14종을 검사하는 교정 단계가 모두 통과하기 전에는 모델을 호출하지 않는다. 참조 구현은 판정기 교정용이며 모델에게 공개하지 않는다.

다음은 별도 리뷰이며 자동 행동 통과를 대신하지 않는다.

| 항목 | 기록할 근거 |
| --- | --- |
| 필요한 질문 | 답변집의 정책 관계·이벤트 계약·선택 메시지·상태 독립성 중 어떤 미확정 결정을 실제로 물었는지. 단순 질문 개수 아님 |
| 계획의 판단 | 코드 관찰 → 대안·비용 → 제품 답변 → 선택 이유. source가 선택을 강제했다는 설명만으로 통과하지 않음 |
| 설계 이행 | 계획 승인 전후의 코드 snapshot, 실제 호출·상태 흐름, 계획과 다른 선택의 근거 |
| 코드의 변경 용이성 | independent/shared 조건의 후속 diff와 관련 기능 보존, 가독성/계약/응집도/결합도별 설명 |
| 지식 적용 | 관련 참조의 조건·제외 조건과 apply/keep/not-applicable 판단, 코드와 검사 근거 |

reviewCriteria는 [scenario.json](scenario.json)에 실행 전 고정한다. 가능하면 조건 이름을 가린 코드와 계획을 독립적으로 리뷰한다. 현재 결과에는 이 리뷰를 수행한 것처럼 채우지 않으며 `unverified`를 유지한다. “파일이 줄었다”, “Hook이 늘었다”, “FS 기록이 있다”는 품질 점수가 아니다. 둘 다 기준을 충족하고 수정 비용도 같다면 차이가 없다는 결과를 그대로 받아들인다.
