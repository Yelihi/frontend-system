### 실행기 수정 — 연속 대화 조건

- 모델/반복/arm별 새 저장소와 새 대화로 시작한다. 같은 여정의 세 단계와 실패 후 재수정은 명시적인 thread ID로 `codex exec resume`한다. ID가 누락되거나 바뀌면 비교를 중단하며 `--last`를 사용하지 않는다.
- 최초 계약은 첫 턴에 전달한다. 이후에는 새 요구 또는 실패한 검사 ID만 전달하고 이전 대화를 재개한다. TASK.md에는 누적 요구를 보존한다. 기존 계획·작업을 이어가되 변경된 요구에 필요한 수정은 허용한다.
- 세션을 저장하므로 `--ephemeral`을 사용하지 않는다. 평가용 대화는 CLI 세션 저장소에 남지만, 모델 도구에 개인 세션 저장소 읽기 권한을 추가하지 않는다. 다른 실험/개인 대화를 참조하지 않는다. [공식 resume 사용법](https://developers.openai.com/codex/noninteractive/).
- Codex 0.159.3의 `turn.completed.usage`는 [해당 버전 소스](https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/exec/src/event_processor_with_jsonl_output.rs)의 `usage_from_last_total`에서 thread 누계를 반환한다. 원누계는 `cumulativeUsage`, 이번 호출의 증가분은 `usage`로 저장한다. 증가분만 합산한다. 카운터 누락·리셋·형태 변경은 추정하지 않고 중단하며, 시간 초과의 미완료 사용량은 null이다. CLI 버전도 manifest에 기록한다. 버전 변경 시 이 누계 의미를 다시 확인해야 한다.
- 본 비교 전에 모델당 짧은 두 턴으로 임의 문자열을 기억하고 재개 후 돌려주는지 확인한다. 이 사전 검사는 비교 토큰에서 제외해 별도 저장한다. `--preflight-only`는 여전히 모델 호출 0회이고, `--session-check-only`는 모델당 2회 호출 후 끝난다.
- 새 manifest는 version 2, `equal-information/continuous-session-maintenance`다. 기존 기록·판정기·지식·300초 한도는 바꾸지 않았다. FS 본체의 절차 경량화는 이번 수정에 포함하지 않았다.

로컬 회귀 검사 **6개 통과**: 실제 로컬 모의 프로세스로 resume 인자·누계 차감·ID 오류·카운터 리셋·timeout을 검사했고, 전체 실행기 모의 실험으로 양쪽 대화 분리와 세 단계/재수정의 대화 유지·증가분 합산을 확인했다. 준비 실행의 manifest 생성과 판정기 교정(3/3, 21/21)도 통과했다. 실제 모델의 대화 복원과 새 조건의 성능 결과는 외부 터미널 실행 전 **미검증**이다.

## 무엇을 측정하나

### 사용자 질문과 트레이드오프는 이번에 측정하지 않았다

현재 runner는 이미 확정된 계약을 전달하며 사용자 답변을 돌려주는 루프가 없다. `policy.mjs`의 순수 계산, `checkout.mjs`의 주입 I/O, 공통 정책, 중복 제출 처리까지 문제지에서 정했다. 양쪽에 같은 지식 본문도 제공했다. 따라서 이번 결과는 **확정된 기준을 구현하는 작은 작업에서 일반 AI도 잘했다**는 증거다. FS의 질문 선택·합의 도출·조직 지식 발견까지 효과가 없다는 결론은 이 실험에서 나오지 않는다. 동시에 측정하지 않은 효과를 FS의 장점으로 확정할 수도 없다.

상호작용 평가는 아래처럼 별도 조건으로 진행해야 한다. 다음은 **실행 설계이며 아직 구현·실행한 결과가 아니다.**

1. 같은 모호한 최초 요청을 준다. 예: “가격 미리보기와 주문 기능을 만들고 실패하면 다시 시도할 수 있게 해주세요.” 구조·숨은 업무 결정을 최초 요청에 미리 풀어 쓰지 않는다.
2. 실행 전에 제품 의도·제약의 답변집과 필수 결정 ID를 고정한다. 예: 미리보기와 주문에 같은 할인 정책을 사용하는지, 주문 요청 중 추가 클릭을 무시할지 예약할지, 뒤늦은 응답을 현재 화면에 반영해도 되는지. 답변은 제품 의도만 설명하고 함수·폴더 구조를 지시하지 않는다.
3. 양쪽 모두 같은 질문/답변 채널을 사용할 수 있게 한다. 질문이 다루는 결정에만 같은 답변을 준다. 질문의 의미와 답변 ID 매핑은 작은 첫 실험에서는 조건을 가린 운영자가 고정 규칙으로 판정한다. 답변집 밖의 질문은 동일하게 “미정”으로 처리하고 임의 조언을 덧붙이지 않는다.
4. 같은 최초 요청에 대해 상반된 제품 의도를 가진 답변집도 각각 실행한다. 예를 들어 두 진입점의 정책이 함께 바뀌는 제품과 실제로 독립적인 프로모션을 가진 제품이다. 특정 공통화 구조를 무조건 만드는 구현이 두 경우 모두 높은 평가를 받지 않도록 한다.
5. 같은 대화에서 구현·후속 변경까지 이어가고, 사용자 결정에 따라 고정한 행동 검사와 독립 코드 리뷰로 판정한다. 파일 모양 하나를 정답으로 강제하지 않는다.

## 다시 실행하기

저장소 루트의 일반 터미널에서 실행한다. 현재 Codex 내부 제한 환경에서의 실패를 회피하는 옵션은 제공하지 않는다. `codex` 인증과 해당 모델 접근, 지원되는 `codex sandbox` 환경이 필요하다. 설치된 executor와 macOS 경로를 재사용하므로 다른 OS에서는 permission_config 이식과 격리 검증이 먼저 필요하다.

```sh
npm run build
# 모델 호출 없이 판정기 확인
node test/evals/fs-comparison/v3/maintenance/evaluate.mjs calibrate /tmp/fs-maintenance-calibration.json
# 실제 모델을 호출하지 않는 양쪽 권한·Git·FS MCP 사전 검사
python3 test/evals/fs-comparison/v3/maintenance/run.py --preflight-only
# 작은 두 턴으로 대화 재개 확인: 실제 모델 2회 호출, 사용량/비용 발생
python3 test/evals/fs-comparison/v3/maintenance/run.py --models gpt-6-sol --session-check-only
# 위 검사에서 Session check passed를 확인한 뒤 실행
# 최소 한 쌍: 연결·격리 통과 시 실제 모델 사용량/비용 발생
python3 test/evals/fs-comparison/v3/maintenance/run.py --models gpt-6-sol
# 파일럿 실행 확인 후 다중 모델 반복
python3 test/evals/fs-comparison/v3/maintenance/run.py --models gpt-6-astra gpt-6-sol gpt-6-luna --repeats 3
```

`--prepare-only`는 manifest·교정 결과만 작성한다. 실행 결과는 새 `results/<시각>/`에 저장하고 기존 결과를 덮어쓰지 않는다. 각 호출의 요청/원로그/실제 usage, 외부 판정, 코드 snapshot, journey.json과 summary.json을 남긴다. 모델/arm별 완료 여정·재수정·토큰은 이 원자료에서 비교한다. 모든 사용량이 있고 적격 여정이 1개 이상일 때만 `모든 시도의 총 토큰 ÷ 적격 여정 수`를 계산한다.
