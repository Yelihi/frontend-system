# v13 — 실제 흐름 분석·변경 감지·계획 저장

2026-10-07. 기존 Next 주문 테스트 앱을 복사하고, 새 모델 세션이 실제 코드에서
분석과 HTML을 생성하게 했습니다. 사전에 작성한 흐름 JSON이나 정답 그림은 제공하지
않았습니다. 최초 4회와 발견한 결함 수정 후 FS 2회를 분리해 보존합니다.

## 무엇을 고쳤나

1. **기존 파일의 새 호출부를 놓치던 최신성 검사:** 명시된 `scope.files` 외에도
   `discoveryRoots`의 소스/설정/데이터 내용 해시를 저장합니다. 추가·삭제만 감지하던
   경우와 달리 기존 checkout 모듈이 새 소비자가 되어도 stale로 판정합니다.
   관련 없는 내용 변경도 stale로 판정할 수 있는 보수적인 방식입니다. 범위 밖 파일,
   동적 호출의 의미, 런타임 완전성을 보증하지 않습니다. 이전 기록은 재분석이 필요합니다.
2. **동일 파일 반복 읽기:** 한 조회 안에서 inventory/해시/지식 검사를 공유하고,
   페이지에 포함된 기록만 최신성을 검사합니다. 다음 조회에서는 다시 읽습니다.
   큰 파일은 스트림으로 해시를 계산하며 AI에 전달하는 소스 읽기 한도와 분리했습니다.
3. **근거 위치:** 흐름 인용은 지정된 줄에서 시작해야 합니다. 가까운 다른 줄의 인용을
   수용하지 않으며, 실패 시 실제 위치를 안내합니다. 인용 일치는 해석의 증명이 아닙니다.
4. **지식 조사 명세:** 기존 Effect 자료를 검토하고 실제 호출부·외부 동기화 여부·
   소유권과 보존 계약·제외 조건을 추가했습니다. 적합한 외부 동기화는 유지하고 소유권이
   불명확하면 임의로 적용하지 않는 회귀 검사를 추가했습니다. 새 원격 자료 검증은 아닙니다.
   71개 참조 중 명세 3개, 직접 참조 66개 중 3개입니다. 나머지 직접 참조 63개는
   legacy 상태로 남습니다. 출처가 뒷받침하지 않는 조건을 만들어 일괄 승인하지 않았습니다.
5. **실제 실행에서 발견한 두 문제:** 한국어 고정 HTML 때문에 영어 요청을 받은 모델이
   생성 파일을 직접 번역해 반환 해시와 달라졌습니다. `language: en|ko` 옵션과 생성 파일
   직접 수정 금지 지침을 추가했습니다. 또한 최초 `project.md` 생성과 기존 문서의 수동
   갱신을 혼동해 계획 저장이 실패했습니다. 저장된 FS 계획 요청은 최초 기준 문서 생성을
   포함하되, 시각화만 요청하거나 쓰기를 금지하면 생성하지 않는다고 명시했습니다.
   기존 기준 문서 갱신은 계속 명시적인 요청이 필요합니다.

## 코드 의미 대조

최초 실행의 일반 AI와 FS 모두 다음 핵심 내용을 설명했습니다.

| 확인한 실제 코드/요구 | 대조 결과 |
| --- | --- |
| form이 `submit(1)` 호출, UI 수량 입력 없음 | 두 조건 모두 구분 |
| closure별 pending과 React status는 다른 역할 | 두 조건 모두 구분 |
| invalid quantity는 전송/상태 쓰기 전에 reject | 두 조건 모두 설명; 현재 UI로는 발생 불가 |
| 실패 후 finally로 guard 복원, 명시적 재시도 | 두 조건 모두 보존; 자동 재시도 제안 안 함 |
| API는 고정 JSON, 응답 body를 UI가 소비하지 않음 | 두 조건 모두 실제 범위와 영속 저장 미확인 구분 |
| availability server action의 반환값을 표시하지 않음 | 두 조건 모두 설명 |
| 새 wrapper는 미연결, 인스턴스 간 독립성 유지 | 두 조건 모두 후속 분석/계획에 반영 |

FS가 더 많은 기록을 남겼지만 이 사례에서는 핵심 판단의 우위를 확인하지 못했습니다.
부실한 첫 FS 전달을 수정했다고 설계 품질·비용의 비교 우위로 해석하지 않습니다.
