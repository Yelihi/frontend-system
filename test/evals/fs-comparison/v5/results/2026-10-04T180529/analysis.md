최신 보완으로 실제 비용·품질이 개선됐다는 증거를 얻지 못했다. 일반 AI는 외부 계약 검사 14/14로 완료했다. FS는 구현 호출이 600초 제한에 걸려 외부 채점과 구현 토큰이 미집계됐다. FS 내부 완료 기록은 남아 있으므로 제품 코드 실패, 내부 절차 완료, 평가 실행의 정상 종료를 구분한다. 원본 summary.json과 이벤트 로그를 수정하지 않았다.

## 새 최적화가 실제 사용됐는가

### 저장 분석 재사용: 등록 누락으로 0회

save_project_context에 진술 9개를 저장했지만 reuse.dependencies / reuse.interpretations가 있는 진술은 0개였다. get_work_context 3회가 각각 관련 진술 8개를 반환했고, 모두 `No reusable dependency binding` 사유로 needs-review였다. 재사용된 의미 트리거는 매번 0개다. 현재 스킬과 evidence-led-design 문서를 실제 읽은 로그도 있으므로 이전 버전만 사용한 실행으로 볼 수 없다.

백엔드의 재사용 연결은 테스트에서 동작했지만 실제 최초 분석 절차가 그 입력을 만들도록 충분히 유도하지 못했다. 선택 필드와 지시문만 추가한 구현의 한계다. 재사용 없는 진술 요약이 오히려 응답에 추가됐다. 이를 캐시 적중이나 효과 검증으로 집계하면 안 된다. knownContextId도 사용하지 않았지만 세 요청의 범위/목적이 달랐으므로 이 값 하나로 해결됐을 문제라고 주장하지 않는다.

### 결정 부분 수정: 4회 시도 중 1회 성공

준비 단계에서 빠진 knowledgeIds와 기존 문서 인용을 수정한 패치 1회는 성공했다. 저장 직후 contractDiagnostics가 빠진 지식 연결을 드러냈고, 승인 시도 전에 수정할 수 있었다.

사용자 답변을 받은 뒤 패치 3회는 실패했다.

| 순서 | 실제 오류 | 원인 |
| --- | --- | --- |
| 1 | changes의 ruleIds, issueIds가 허용되지 않음 | open 결정에는 두 연결이 비어 있었고 resolved로 바꾸면서 연결해야 했다. 패치 API가 이 흔한 변경을 지원하지 않음 |
| 2 | USER_DECISIONS.md가 routed source/pinned requirement가 아님 | 준비 때 저장한 route에는 새 답변 문서가 없음 |
| 3 | 맥락을 갱신한 뒤에도 같은 문서 오류 | get_work_context는 새 receipt를 발급하지만 기존 계획의 route를 자동 교체하지 않는다. decisionUpdates는 저장된 route를 재사용하므로 갱신만으로 해결되지 않음 |

결국 get_revision(full) 2회와 전체 evidence 교체로 돌아갔다. 조회는 전체 contract 1회, full 2회였고 decisions 조회는 0회였다. 이 동작은 부분 수정 기능 자체가 전혀 작동하지 않는다는 뜻은 아니지만, 이번에 가장 중요했던 답변→근거 갱신→결정 확정 흐름을 충분히 지원하지 못했음을 보여준다.

나머지 MCP 오류 1회는 save_semantic_review의 `Review must address all required rules`였다. 공통 리뷰에 8개 규칙을 연결한 뒤 한 단계 관련 규칙만 제출해 거절됐다. 이후 전체 규칙을 담는 리뷰 기록을 반복 작성했다. 별도로 stderr에는 UI 테스트 파일 교체 중 apply_patch 인자 오류도 있다. MCP 오류 수에는 이를 섞지 않았다.

## 반복 비용과 시간 초과 해석

- 준비 단계에서 제품 9개 파일을 셸로 읽은 뒤 read_project_source 11회로 main 자료를 읽었다. 두 읽기의 목적은 다르지만 변경 없는 제품 본문이 반복 노출됐다.
- 준비에서 여러 워크플로 문서를 읽고, 구현에서 fs-implement/testing-and-transition도 추가로 읽었다. 응답 문자량은 모델 토큰이나 소요 시간의 직접 귀속값이 아니다.
- 제품 4개 파일은 첫 수정 이벤트에서 함께 고쳤지만 실행 기록은 service-boundaries/controller/ui 3단계로 진행했다. 기록된 검사 5회, 시도 시작 3회, 리뷰 저장 4회, 실행 저장 4회였다.
- service-boundaries 후반 검사와 controller 검사는 동일 sourceHash에서 같은 test/build를 실행했다. 다른 검사 일부는 UI 테스트가 추가·변경된 뒤 수행됐으므로 모두 불필요한 반복으로 단정하지 않는다.
- 양쪽 모두 브라우저 기동 실패와 대체 UI 검사 작성 비용이 있었다. FS만의 비용으로 계산하지 않는다.

600초를 늘리면 최종 응답이 남을 가능성은 있지만 이것은 비용 원인 수정이나 성능 개선의 증거가 아니다. 개별 추론/도구별 사용량은 없으므로 각 오류가 몇 초·몇 토큰을 낭비했는지는 계산하지 않았다.

## 다음 보완의 우선순위 — 아직 구현하지 않은 제안

1. 최초 분석 저장에서 재사용 가능한 관계의 등록 또는 재사용하지 않는 이유를 점검한다. 모든 사실에 임의의 의미 트리거를 강제하지 않는다. 적합한 트리거가 있는 사례에서 누락을 보여주고 분석 단계에서 해결한다.
2. 기존 결정 ID의 규칙/이슈 연결과 새 답변 문서의 route 갱신을 같은 부분 수정 흐름으로 지원한다. 새 receipt에 대한 명시적 후보 판단과 기존 승인 무효화는 유지한다. stale route 오류는 어떤 저장 입력을 바꿔야 하는지 안내해야 한다.
3. 실제 두 턴 절차를 회귀 검사한다: open 결정 생성 → 새 USER_DECISIONS.md → 새 맥락 → 부분 수정 → 근거 검증 → 승인. 기존 정적 문서만 쓰는 패치 검사는 이 실패를 놓쳤다.
4. 같은 소스·정책·명령에서 검사 결과를 단계 간 활용할 수 있는 조건과, 단계별 리뷰의 실제 규칙 범위를 정리한다. 이미 한 번에 수정한 작은 범위를 기록 때문에 여러 단계로 나누지 않도록 한다.
5. 그 뒤 동일 예산에서 재실행한다. 토큰 수 외에 reusable 진술 등록 수, 실제 재사용 수, 패치 성공률, 중복 조회/검사 수를 함께 확인한다.

원문 수집/지식의 품질이 나빠서 생긴 결과라고 확정할 수 없다. 이번에 직접 확인한 문제는 저장 분석의 실제 활용과 계획 변경 API, 검사 기록의 사용 흐름이다. 근거를 보존하는 목적을 유지하면서 이 경로부터 고쳐야 한다.
