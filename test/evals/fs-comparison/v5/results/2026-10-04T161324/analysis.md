# v5 실제 비교: 계약 준수 동점, FS 추가 비용

두 조건 모두 첫 구현에서 14/14를 통과했다. 이번 과제에서는 FS의 계획 준수·수정 횟수 우위를 확인하지 못했고 비용은 더 컸다. 제품 파일 7개의 최종 바이트도 모두 동일하다. 기존 결과의 실패나 미검증을 정상으로 변경하지 않았으며 이번 결과도 원점수 그대로 해석한다.

근거: [원본 summary](summary.json), [계산·파일 해시](analysis.json), [고정 실행 조건](manifest.json). 모델은 gpt-6-sol, 1쌍, 순서 plain → FS, 호출당 600초, 총 모델 호출 4회다. 각 조건은 새 프로젝트/새 세션에서 시작하고 준비→구현은 같은 세션을 이어갔다.

## FS 절차는 실행됐지만 결과물 차이로 이어지지 않았다

FS는 main 소스 읽기, project.md 근거 저장, 코드/지식 라우팅, 미결정 Q1/Q2 저장, 사용자 답변 반영, 계획 승인, 작업 시작, 테스트/빌드, 호스트 의미 리뷰, 완료 기록까지 실행했다. 본문 열람은 MCP read 도구 대신 셸 cat으로 이루어졌다. 준비 단계에서 request-policy-boundaries, React 상태 모델과 접근성 참조 3개 본문을 읽은 로그가 있다. 따라서 “FS를 전혀 쓰지 않았다”로 설명할 수 없다. 다만 지식의 올바른 해석이나 독립적인 품질 판단까지 이 호출 기록이 입증하지는 않는다.

두 조건 모두 사용자 답변에 따라 콜백 원본 오류 전달과 실패 시 이전 목록 유지를 반영했다. 질문 주제와 선택 범위는 처음부터 제공했으므로 미지의 설계 문제를 발견한 결과는 아니다. 두 구현 모두 테스트 9개를 작성했고 브라우저 클릭은 실행하지 않았다고 보고했다. FS의 호스트 리뷰 passed/내부 verified와 외부 평가의 semanticReview=unverified는 다른 주장이다.

## 추가 비용에서 확인한 문제

원로그: [FS 준비](layered-orders-fs/prepare/0/model/events.jsonl), [FS 구현](layered-orders-fs/work/0/model/events.jsonl).

1. 준비 단계 save_revision에 verification=`behavior-test and semantic-review`, `behavior-test, build, and semantic-review`처럼 enum에 없는 값을 넣어 실패했다. open 선택값 생략 문제는 이번에는 재현되지 않았다.
2. 구현 단계에서 새 라우팅 결과에 없는 이전 후보 5개를 판단 목록에 남겨 save_revision이 실패했다. 준비 요청의 후보는 11개, 사용자 답변을 추가한 구현 요청은 7개였다. 이전 판단과 현재 후보를 수작업으로 대조하는 부담이 드러났다.
3. 새 후보 javascript-iteration-promises-and-resources를 apply로 기록한 뒤 결정의 knowledgeIds에 연결하지 않아 approve_revision이 거절됐다. 연결을 추가하고 다시 승인했다. 이 거절은 근거 연결 보호가 작동한 사례지만 제품 코드의 결함을 발견한 것은 아니다.

그 결과 save_revision 5회 중 성공 3회, approve_revision 2회 중 성공 1회로 최종 계획은 v3가 됐다. 사용자에게 새 설계 결정을 세 번 받은 것이 아니라 답변 반영과 기록 정합성 보정이 포함된 버전이다. 준비에서 소스를 셸로 읽은 다음 read_project_source로 공식 근거를 다시 읽었고, 구현에서는 셸 test/build 후 도구의 delivery 검사도 실행했다. 일부는 근거 고정·완료 기록에 필요한 절차지만 그 비용이 실제로 존재한다. 개별 도구의 인과적 시간 기여도는 이번 자료로 분리하지 않았다.

knownContextId는 세 번의 get_work_context 모두에서 사용되지 않았다. 다만 요청문·요구사항·소스 범위가 달라 contextId도 모두 달랐다. 따라서 이를 사용했으면 이 비용을 크게 줄였을 것이라고 단정할 수 없다. 앞서 고정 예제로 확인한 30.4% 응답 감소는 이 실제 실행의 총 토큰 절감이 아니다.

## 복잡성 증가의 한계

v5는 여러 파일·계층을 검사하지만 시작 코드에 이미 client/repository/controller/UI 구조와 공개 인터페이스가 제공돼 있다. 양쪽이 실제 변경한 제품 파일은 4개, 교체된 소스 줄은 8줄이다. `if (true)`를 세대 비교로 복원하는 등 승인된 계약으로 답을 찾기 쉬운 결함도 있다. 최종 제품 파일 7개가 모두 같은 것은 이 좁은 수정 공간과도 관련이 있다는 해석이 가능하다.

이 한계를 이유로 이번 동점을 무효화하지 않는다. **제공된 계획에 따른 이 수정 작업에서는 일반 AI도 모든 검사를 지켰고, FS의 추가 절차는 측정 가능한 구현 개선을 만들지 못했다.** 파일 수를 더 늘리는 것만으로 FS의 가치를 입증할 수는 없다. 반대로 모든 상황에서 두 방식의 품질이 같다는 결론도 아니다.

기존 v4와 과제·프롬프트·제한 시간이 달라 5.55배→7.34배를 수정의 인과적 성능 퇴보로 단정할 수 없다. 두 실행 모두 추가 비용을 정당화하는 구현 준수 개선을 관측하지 못했다는 사실은 유지된다.

## 다음 변경을 판단할 기준

우선 새 유료 비교를 반복하기보다 이 로그에서 확인한 세 가지 실패와 중복 절차를 고정 회귀 사례로 삼는 편이 낫다. enum 복합 입력을 스키마에 맞게 안내하고, 현재 후보와 이전 판단의 차이를 도구가 명시하며, 승인 전 필요한 지식→결정 연결 누락을 저장 응답에서 보여주는 방향이다. 필수 검증이나 사용자 결정을 삭제해서 비용을 낮추어서는 안 된다.

이후에도 같은 확정 계획 구현에서 개선이 없다면, FS의 가치는 프로젝트 지식·판단 이력 관리와 계획 수립 지원으로 한정해 설명해야 한다. “더 엄격하고 더 저렴하게 구현한다”는 주장은 아직 근거가 없다. 별도의 계획 수립 평가는 사용자가 원할 때 사전 기준을 고정해 진행하고 이 부정적 구현 결과를 대체하지 않는다.
