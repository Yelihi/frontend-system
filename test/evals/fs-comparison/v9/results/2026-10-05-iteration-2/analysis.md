# 두 번째 보완: 부분 개선, 전체 비용·완료율 목표 미달

후보를 고정한 뒤 새 대화에서 기존 FS/수정 FS를 공유·독립 세션에 각각 실행하고,
수정 FS의 자격 증명 갱신 전이 사례를 추가했다. 모델·원문·답변표·600초 제한은 동일하다.
첫 refresh 질문은 제공자 capacity 오류로 실패했고, 동일 초기 사본의 새 여정으로 복구했다.
원래 실패는 보존했다. 완성된 여정은 5개 선택 사례 중 4개다.

| 조건 | 완료 턴/2 | 확인된 총 토큰 | 비캐시 입력+출력 | 시간 합계(초) | MCP 실패 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 공유 기존 FS | 2 | 939,528 | 81,288 | 606 | 0 |
| 공유 수정 FS | 1 | 417,560+ | 47,768+ | 966 | 4 |
| 독립 기존 FS | 2 | 1,171,439 | 102,255 | 831 | 6 |
| 독립 수정 FS | 2 | 1,639,563 | 88,203 | 857 | 2 |
| 갱신 수정 FS — 복구 | 2 | 2,061,098 | 114,090 | 866 | 5 |

공유 수정 FS는 계획 저장·복사 후에도 최종 턴이 600초를 넘었다. 저장 산출물은
분석할 수 있지만 완료로 세지 않는다. 해당 턴 사용량이 없으므로 `+`는 하한이다.
독립 수정 FS의 총 토큰은 기존 대비 40.0% 증가했고 비캐시 입력+출력은 13.7%
감소했다. 캐시 상태를 통제할 수 없고 표본은 하나이므로 전체 비용 개선으로 해석하지 않는다.

독립 수정 계획은 같은 값 교체를 보존하고 다른 값 교체의 A→B→A 이력을 구분하며,
POST의 미제공 결정을 별도로 남겼다. 기존 FS 계획도 다른 값 교체 억제를 명시하지만
구체적인 이력 메커니즘을 확정하지 않았다. 이는 구체성 차이이지 기존 계획의
실행 오류가 증명됐다는 뜻은 아니다. 실제 구현 코드는 실행하지 않았다.

갱신 수정 계획은 교체 뒤 정상 응답을 보존하고 mounted portal 수명을 구분했다.
다만 이전 credential 버전의 401을 억제하는 별도 정책까지 확정했다. 질문은 401을
포함했지만 답변은 같은 논리적 세션에서 pending work를 보존한다는 수준이다.
이 인증 전용 예외가 허용되는지는 추가 확인이 필요하다. 따라서 이 사례를 무조건
정답 또는 FS 고유의 품질 우위로 처리하지 않는다. 첫 회 원문 AI는 이 정책을 열어 두었다.

오류는 미등록 domain 필터, 빈 reuse.interpretations, 누락 summary, 모호한 인용 위치,
존재하지 않는 test script, 출처 연결 등에서 발생했다. 파일 기반 입력은 실제 사용됐고
검증은 계속 동작했다. 파일 전송만으로 전체 토큰이 줄었다고 주장할 근거는 없다.

세 번째 보완은 거대한 revision payload 스키마의 필요 시 열람과 같은 서버 검증,
입력 전 domain/reuse/script 확인, 저장 전 일괄 검토 및 완료 후 불필요한 재작성 방지다.
기존 승인·근거·필수 검사 조건을 완화하지 않는다. 이 결과를 숨기거나 덮어쓰지 않는다.

전체 실제 생성 호출은 11회, 완료 턴 9회, 사용량 누락 2회다. 확인 가능한 합계는
6,229,188토큰 이상, 비캐시 입력+출력 433,604 이상이다. 원자료는
[비용 장부](generation-cost-ledger.json), [무결성 검사](integrity-audit.json),
[기계적 요약](mechanical-summary.json)에 있다. 독립 수정 결과는
[independent-new/plan/project/plan.md](independent-new/plan/project/plan.md),
갱신 결과는 [refresh-new-recovery/plan/project/plan.md](refresh-new-recovery/plan/project/plan.md).
이 문서는 코디네이터의 근거 검토이며 독립 블라인드 리뷰 결과가 아니다.
