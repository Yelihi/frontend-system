# 세 번째 보완: 전달량 감소와 실제 비용 개선은 다르다

기존 FS와 수정 FS를 공유·독립 세션에서 새로 실행하고 수정 FS의 credential rotation
사례를 추가했다. 지식 파일·모델·질문/계획 프롬프트·답변표·600초 제한은 유지했다.
선택한 5개 여정 중 3개가 두 턴을 완료했다. 공유 기존 FS는 계획 턴 시간 초과,
갱신 수정 FS는 계획 턴에서 제공자의 capacity 오류로 중단됐다. 둘을 분리한다.

| 조건 | 완료 턴/2 | 확인된 총 토큰 | 비캐시 입력+출력 | 시간 합계(초) | MCP 실패 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 공유 기존 FS | 1 | 411,104+ | 47,968+ | 1,080 | 4 |
| 공유 수정 FS | 2 | 1,192,014 | 86,990 | 720 | 2 |
| 독립 기존 FS | 2 | 949,866 | 94,186 | 865 | 3 |
| 독립 수정 FS | 2 | 1,359,622 | 130,054 | 780 | 2 |
| 갱신 수정 FS | 1 | 369,220+ | 67,396+ | 455 | 1 |

도구 목록의 입력 스키마는 44,748 → 30,250문자(-32.4%)로 줄었다. 전체 스키마는
읽기 전용 tool-help의 payloadSchema에 남고 같은 서버 검증을 통과해야 한다. 이것은
정적 입력 스키마 크기 측정이지 모델 토큰 절감률이 아니다. 공유 수정 FS 질문 단계는
비용이 줄었지만 전체 기존 여정의 사용량은 시간 초과로 없어 비용 비교를 완성할 수 없다.
유일하게 양쪽이 완료된 독립 사례에서는 수정 FS의 총 토큰이 43.1%, 비캐시 입력+출력이
38.1% 더 많았다. 전체 비용 개선 목표는 달성하지 못했다.

공유 수정 FS는 저장·최종 응답을 끝냈고 전달된 plan.md도 저장된 projection과 동일하다.
그러나 기존 계약 d-preserve의 confirmation 누락 진단이 남았다. 열린 q1은 의도한
사용자 결정 대기이지만 이 누락은 수정 가능한 기록 문제다. 따라서 CLI 응답 완료를
승인 가능한 계약 완성으로 계산하지 않는다. 저장이 성공했다는 사실도 의미적 정답이 아니다.

공유 수정 계획은 같은 토큰 교체를 새 generation으로 처리하고 정상·반례 시나리오를
제시한다. 다만 disposed view의 갱신 금지를 Session.expire 금지까지 확장하고, read
순서 규칙을 authentication 효과에도 적용했다. 답변은 각각 view 갱신과 items/errors/
pending을 정했으므로 이러한 추가 범위를 확정하려면 별도 근거 또는 확인이 필요하다.
이 부분을 더 좋은 설계라는 이유만으로 사용자 결정으로 간주하지 않는다.

독립 기존 계획은 token equality가 모든 continuation을 검사하면 충분하다고 기술한다.
A→B→A 이력을 구분하지 못하는 해석이 여전히 허용된다. 수정 계획은 scoped generation을
선택지 비용에 요구하면서도 rationale에 token equality가 유효하다고 표현해 명확성이
부족하다. 첫·둘째 보완의 명시적 A→B→A 추적 개선이 항상 재현됐다고 주장할 수 없다.
또한 수정 계획은 사용자가 조건부로 허용한 내부 메커니즘을 다시 사용자 결정 대기로
남겼다. 질문이나 open 항목이 많다는 것만으로 점수를 주지 않는다.

네 번째 보완은 effect/owner/event 범위와 actual answer를 대조하고, 의도한 open과
수정 가능한 진단을 구분하며, 기존 계약 confirmation과 script 입력 조건을 명확히 한다.
공유·갱신 사례의 알려진 문제를 대상으로 새 여정을 실행한다. 새 기존 FS 대조군이
없는 표적 회귀 시험이므로 이를 일반적 비용 우위 증명으로 바꾸지 않는다.
