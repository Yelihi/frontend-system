# 첫 보완 비교 — 결과 보존

첫 보완은 독립 세션 계획에서 변경 이력을 구분해야 한다는 제약을 구체화했지만, 전체 비용·안정성 개선에는 실패했다. 두 원래 상황의 FS 총 처리 토큰은 이전 버전 2,147,106 → 첫 보완 2,298,013으로 증가했다. 추가 credential-refresh 상황의 첫 보완은 계획 턴 600초 제한 내 완료하지 못했다. 이 실행을 성공한 계획으로 세지 않는다.

동일 모델·프롬프트·지식·답변표의 새 대화로 이전 FS, 첫 보완 FS, 원문 AI를 공유/독립 세션에서 비교했다. 별도로 고정한 credential-refresh 상황에서는 원문 AI와 첫 보완 FS를 실행했다. 총 16개 생성 호출 중 15턴 완료, 1턴 시간 초과다. 제품 구현은 요청하거나 실행하지 않았다.

## 관측한 판단과 한계

- 첫 보완의 독립 계획은 A→B→A를 명시하고 raw token equality alone is insufficient라고 제한했다. 이전 버전은 generation 또는 조건에 맞는 token comparison을 허용해 해당 반례의 금지를 덜 구체적으로 표현했다. 이전 버전이 반드시 잘못된 코드를 작성할 것이라는 증거는 아니다. 원문 AI도 다른 토큰 교체에 generation을 증가시키는 방식을 제시했다.
- 첫 보완의 공유 계획은 미정 항목을 남겼으면서도 disposed submit의 auth effect를 일괄 차단하는 요구를 적었다. 답변표가 확정한 것은 disposed view 갱신 금지이며 현재 세션의 만료까지 결정하지 않았다. 다만 복합 질문에 일반적인 unknown 답변을 덧붙인 평가 입력 자체가 어느 하위 선택이 미정인지 모호하게 만들었다. 명확한 답변 위반 점수로 단순 집계하지 않고 확인할 설계 가정으로 보존한다.
- 추가 상황의 원문 AI는 rotation만으로 pending work를 무효화하지 않으며, 이전 credential의 401 처리에 대해서는 별도의 미정 선택을 남겼다. 첫 보완의 미완료 계획은 UI 결과를 보존하면서 예전 credential의 401은 generation으로 차단하도록 정했다. 이 부수 효과의 정책이 답변에서 충분히 도출되는지 추가 확인이 필요하다. 완료한 FS의 우위로 사용할 수 없다.
- 신규 계획 저장의 긴 payload 재전송이 병목이다. main evidence 버전 누락, reconsiderWhen 누락, 중복 인용, 아직 없는 test 스크립트 지정이 실제 재시도를 일으켰다. 검증을 완화해서 통과시키지 않았다.

질문 단계만 보면 첫 보완의 토큰이 줄었지만 전체 계획 단계까지 합치면 결과가 달랐다. 첫 결과에서 유리한 단계만 선택하지 않는다. 반례 표현, 계획의 불확실성 관리, 운영 비용, 완료 여부를 분리해서 본다.

## 다음 보완과의 구분

[실행 중 버전 구분](mid-run-maintenance.md)처럼 이 결과는 첫 보완의 고정 runtime으로 생성했다. 이후 추가한 draftFile 제출·계획 복사·형식 기본값·미정 선택 대조는 이 결과에 포함되지 않는다. 별도 iteration-2에서 새 대화로 비교한다. 실패한 계획에 답을 주고 수정한 결과를 새 비교로 세지 않는다.

보조 모델 검토와 원문 대조 결과는 추가 기록에서 구분하며, 이 단계의 관측을 통계적 우위나 대규모 코퍼스 효과로 일반화하지 않는다.
