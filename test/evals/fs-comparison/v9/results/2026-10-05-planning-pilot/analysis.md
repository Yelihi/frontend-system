# v9 실제 비교 — 2026-10-05

**지식을 제공하면 질문이 구체화되는 사례는 있었지만, FS가 같은 원문을 받은 AI보다 판단을 일관되게 개선했다는 증거는 얻지 못했다.** FS의 지식 검색·본문 참조·결정 연결은 확인했다. 그 연결 이후의 추론 오류도 확인했으며 처리 비용은 더 높았다.

이 기록은 [사전 프로토콜](../../protocol.md)에 따른 질문·계획 비교다. 제품 구현의 테스트 통과율, 리팩터링 완료율, 장기 유지보수 비용을 측정한 것은 아니다. 결과를 본 뒤 지식이나 채점 기준을 바꿔 성공으로 재분류하지 않았다.

## 비교 조건과 입력

동일한 `gpt-6-sol`, reasoning medium으로 일반 AI / 원문 두 편을 받은 AI / 실험용 learned index가 빈 FS / 같은 원문을 sync한 FS를 비교했다. 공유 세션과 독립 세션의 두 상황에서 총 8개 여정을 완료했다. 각 여정은 새 대화·새 코드 사본에서 질문을 생성하고, 관련 질문에 대한 고정 답변을 받은 뒤 같은 대화에서 미승인 계획을 작성한다.

코드는 프레임워크에 종속되지 않은 TypeScript 소스 7개다. 화면의 검색·조회·주문·인증·비동기 완료·폐기를 포함한다. 소유권과 동일 토큰 교체의 의미가 상황별로 다르므로 지식을 무조건 적용하거나 무조건 공통화하면 안 된다. 주제별 질문이나 완성된 설계를 모델에게 미리 전달하지 않았다. 답변 매핑은 코디네이터가 실제 질문에 맞는 고정 답변만 선택했다.

K1의 지식 두 편은 실험용으로 작성한 요청 정책 경계와 논리적 신원·수명에 관한 문서다. 기존의 모든 Toss 자료나 사용자의 축적 지식 전체를 대표하지 않는다. 실제 등록·검토·sync API와 검증을 거쳤지만 정규화 메타데이터는 작성해 제공했다. 자유형 지식을 AI가 자동 변환하는 품질은 별도 평가가 필요하다.

## 판단의 실제 차이

### 구체적인 질문에는 지식의 영향이 보였다

같은 토큰 문자열로 교체할 때의 의미를 질문 또는 선택지에서 명시한 실행은 일반 AI 0/2, 원문 AI 2/2, 기본 FS 1/2, 지식 추가 FS 2/2였다. 이것은 특정 논점의 관찰이며 전체 질문 품질 점수가 아니다. 일반 AI의 넓은 질문도 관련 답변을 얻을 수 있었다. 필요한 질문의 수가 많다는 이유만으로 높은 점수를 주지 않는다.

[일반 AI의 공유 세션 계획](shared-ordinary/plan/project/plan.md)은 같은 토큰 교체도 revision을 증가시키도록 정했지만 해당 identity 결정은 답변받지 않았다. 사용자에게 확인할 설계 가정을 구현 항목으로 확정한 사례다. 이미 받은 답변과의 모순이나 실행된 제품 결함으로 분류하지는 않는다.

### 지식을 참조한 FS도 적용 판단을 잘못했다

[지식 추가 FS의 독립 세션 계획](independent-fs-K1/plan/project/plan.md)은 같은 토큰 교체가 신원을 유지하고 다른 토큰 교체가 신원을 바꾼다는 답변을 받았다. 그런데 비동기 완료 때 요청 당시 토큰과 현재 토큰 문자열을 비교하면 충분하다고 판단했다.

`A → B → A` 교체를 생각하면 첫 A에서 시작한 요청과 마지막 A의 요청은 다른 논리적 신원에 속한다. 문자열은 같지만 오래된 요청의 완료를 허용하면 안 된다. [반례 기록](aba-witness.json)은 이 계획의 주장을 반박한다. 이것은 실행 후 발견한 탐색적 반례이며 모델이 생성한 구현을 실행한 결과나 사후 추가한 종합 점수가 아니다.

[일반 AI의 독립 세션 계획](independent-ordinary/plan/project/plan.md)은 이 반례와 세션별 generation을 명시했다. [원문 AI의 계획](independent-raw-K1/plan/project/plan.md)도 다른 토큰 교체 때만 증가하는 generation을 제안했다. 따라서 지식의 검색·참조가 성공했다는 사실만으로 적용이 정확하다고 결론 내릴 수 없다.

### sync·trigger에서 확인한 것과 확인하지 못한 것

두 FS-K1 상황에서 두 지식 후보가 검색되고 본문을 읽었으며 판단·결정과 연결됐다. [공유 상황의 영향 조회](recovery/shared-fs-K1/knowledge-influence.json)와 [독립 상황의 영향 조회](independent-fs-K1/knowledge-influence.json)에 저장된 메타데이터 해시가 일치한다. 독립 세션에 전역 인증 상태를 강요하지 않는 제외 조건도 유지됐다.

[본문 보존 검사](corpus-audit.json)는 원문과 sync된 참조 본문의 일치, contentHash, 지식이 무조건적인 필수 규칙으로 변환되지 않았음을 확인한다. 그러나 메타데이터가 원문의 핵심 조건을 충분히 표현했는지, 모델이 이를 올바르게 해석했는지는 이 검사만으로 알 수 없다.

후보는 코드 트리거뿐 아니라 요청 검색과 범위 검색에서도 발견됐다. 이번 네 조건만으로 **sync와 trigger 각각의 독립적인 인과 기여를 분리할 수 없다.** 이 부분을 보려면 같은 지식·절차를 유지한 채 검색 경로만 바꾼 추가 실험이 필요하다.

## 평가자의 검토도 검증했다

별도 모델에 조건명 대신 중립적인 P01–P08 ID를 주어 계획을 검토시켰다. 실제 답변과 상충하는 계획 및 타당한 계획 두 예제로 분류를 확인했다. 두 예제 통과는 평가 정확도 추정치가 아니다. FS 특유의 문체·기록 용어로 조건을 추측할 수 있어 완전한 블라인드도 아니다.

보조 검토의 [인용 210건](reviews/quote-audit.json)은 모두 전달한 텍스트에 존재했다. 하지만 평가 자료에서 package.json과 내부 FS 기록을 빠뜨려 생긴 오탐이 있었다. 실제 package.json은 scripts가 비어 있으며, 공유 FS-K1의 구조화된 draft와 semantic review도 저장돼 있었다. 해당 지적은 [보충 원자료](review-supplement.json)와 MCP 기록으로 기각하고 평가자 원문은 보존했다.

구조 선택 질문이 불필요하다는 의견은 사용자가 원하는 설계 논의 역할과 충돌하므로 자동 감점하지 않았다. 최신 조회의 오류와 세션 전체 401 부수 효과의 관계도 답변 범위가 애매하므로 추가 확인 대상으로 남겼다. [최종 대조 기록](adjudication.json)에 채택·기각·미판정 이유가 있다. 인용 일치는 판단의 진실성을 보장하지 않는다.

질문 자체의 정확한 인용은 일반 AI 25/26, 원문 AI 31/31, 기본 FS 27/27, 지식 추가 FS 26/26이다. 일반 AI의 한 불일치는 README 인용의 대소문자 차이이며 도메인 사실의 오류로 확대 해석하지 않았다.

## 실행 무결성과 구현 검증

- 선택된 8개 여정의 대화 ID는 모두 다르며 각각의 계획은 자신의 질문 대화를 이어받았다.
- [입력 보존](source-integrity-audit.json): 제품 소스·답변·질문·런타임을 보존했다. 모델이 만든 제품 코드를 호스트에서 실행하지 않았다.
- [격리 확인](cell-isolation.json): 8개 프로젝트의 상호 읽기 차단과 4개 실제 MCP 연결을 확인했다. 사전 검사에서 생긴 합성 기록은 보존 후 모델 노출 전에 제거했다.
- `npm run check`: 타입·린트 및 Node 검사 94개 통과. [로그](validation/check.log).
- 패키지 검사, fs-plan 스킬 검사, Python 실행기 검사 3개 통과. 승인·근거 최신성 검증을 완화하지 않았다.
- FS 네 여정 모두 미승인 named revision을 저장하고 영향 조회를 수행했다. 열린 결정은 승인 대상이 아니며 승인 도구를 호출하지 않았다.

실행 후 공개 실행기에 입력 스냅샷 보관과 검토용 공유 격리 경계를 보강했다. 실제 유료 검토는 처음부터 공유 경계를 적용한 별도 실행 스크립트를 사용했다. 이후 문서·보조 실행기 수정으로 유료 모델을 다시 호출하지 않았다. [변경 구분](post-run-provenance.json)처럼 생성 프롬프트·설정·run_cell과 보조 검토 프롬프트는 당시 동결본과 AST/문자열 기준으로 동일하다.

## 이 결과로 정할 다음 과제

지식이 질문을 구체화하는 가능성과 지식 연결의 실행은 확인했다. FS만의 품질·효율 우위는 아직 입증하지 못했다. 이번에는 검색 실패만을 원인으로 볼 수 없으며, **사용자 결정에서 도출한 설계가 그 결정의 반례를 견디는지**가 구체적인 보완 지점이다.

비용은 근거 위치 확인과 main/working 기록 혼동, 구조화된 입력 재전송을 먼저 줄일 필요가 있다. 도구가 거부한 잘못된 근거를 그대로 통과시키는 방식은 쓰지 않는다. 앞으로 반복 실행과 새로운 상황에서 확인해야 하며 이 작은 코퍼스의 결과를 대규모 지식·실사용 만족도·장기 수정 횟수로 일반화하지 않는다.
