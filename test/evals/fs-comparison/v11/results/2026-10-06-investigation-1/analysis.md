# v11 실제 모델 결과 — 2026-10-06

**12회 모두 완료했습니다. 새 조사 절차의 지식 연결·근거 저장은 확인했지만,
이번 사례에서 FS의 설계 판단 또는 비용 우위는 확인하지 못했습니다.**
완료는 격리된 리뷰 생성의 완료이며, 제품 구현·런타임 검증 통과를 뜻하지 않습니다.

## 고정 조건과 검증 범위

`gpt-6-sol`, medium, 네 상황 × 일반 AI / 같은 원문 AI / FS, 각 한 번입니다.
각 실행은 새 스레드와 동일 초기 코드 사본으로 시작하고, 최대 두 호출만 병렬로
실행했습니다. 호출 제한은 600초이며 시간 초과는 없었습니다. 입력과 런타임은
[manifest.json](manifest.json)에 고정했고, 실행 중 수정하거나 좋은 결과가 나올
때까지 재시도하지 않았습니다. 셀 내부의 도구 오류 복구 비용은 모두 포함합니다.

세 조건 모두 같은 소스·소유자 계약을 받고 `review.md`를 작성했습니다.
원문 AI와 FS에는 동일한 조사 질문·조건·대안·보존 계약을 제공했습니다.
FS는 실제 스킬/MCP를 사용하고 조사 기록 저장도 추가로 요청받았습니다.
따라서 아래 수치는 **그 추가 기능을 포함한 전체 작업 비용**이지, 동일 산출물에
라우터만 추가했을 때의 순수 비용 배수는 아닙니다.

평가용 지식 한 건을 격리된 런타임에 등록·검토하고, 조사 명세를 필수로 확인하는
sync 검증을 실행했습니다. 검색·양성 트리거·무관한 음성 트리거 검사를 통과했고,
`withoutInvestigation`과 `unpublished`는 비어 있습니다([sync.json](sync.json)).
실제 원문을 모델이 자동 변환한 실험은 아니며, 실제 공용 지식은 변경하지 않았습니다.

Git/CLI/MCP preflight와 파일 접근 격리 검사가 통과했습니다.
12개 스레드는 모두 다르고, 제품 소스 및 런타임 해시는 모두 유지됐습니다.
제공된 fixture의 타입 검사는 모델 실행 전 수행했습니다. 생성된 제품 코드는
실행하지 않았으며, 모델들은 수행하지 않은 테스트의 통과를 주장하지 않았습니다.
실시간 사용자 응답 대신 제공된 계약만 사용하고 남은 질문은 미결로 종료했습니다.

## 설계 판단의 실제 차이

실행 전에 고정한 관찰 항목으로 생성 리뷰를 직접 읽었습니다. 사례 작성자가
판정했으며 독립적인 블라인드 평가가 아닙니다. 문서 길이·질문 수·클래스 사용을
점수로 만들지 않았고, 임의의 가중 합계도 만들지 않았습니다.

| 상황 | 일반 AI | 같은 원문 AI | FS | 관찰 |
|---|---|---|---|---|
| direct | [리뷰](direct-ordinary/review/project/review.md): 작은 순수 함수와 공통 검증 유지, 복잡해질 때 helper | [리뷰](direct-raw-K1/review/project/review.md): 연산별 호출 API 선호, 공통 검증·최신 상태 소유 유지 | [리뷰](direct-fs-K1/review/project/review.md): API 변경은 가능하지만 지금은 기존 구조 유지 | 선호는 달랐지만 세 조건 모두 대안의 비용을 설명. 분리가 정답이라는 기준은 없으므로 원문/FS 어느 쪽의 승리로도 계산하지 않음 |
| replay | [리뷰](replay-ordinary/review/project/review.md): 공개 명령 경계 유지, 내부 helper 제안 | [리뷰](replay-raw-K1/review/project/review.md): 명령·재생 계약 유지, 내부 추출은 선택 | [리뷰](replay-fs-K1/review/project/review.md): 공개 경계 유지, 새 wire 형식 질문 | 세 조건 모두 이미 정해진 호환성을 보존 |
| mixed | [리뷰](mixed-ordinary/review/project/review.md): 브라우저 작업과 기록 명령 구분 | [리뷰](mixed-raw-K1/review/project/review.md): 내부 API와 공개 계약 구분 | [리뷰](mixed-fs-K1/review/project/review.md): 같은 구분, 새 동작 기록 여부 질문 | 세 조건 모두 미정인 기록 정책을 대신 결정하지 않음 |
| unknown | [리뷰](unknown-ordinary/review/project/review.md): 외부 소비자·호환성 질문 | [리뷰](unknown-raw-K1/review/project/review.md): 외부 소비자 부재를 단정하지 않음 | [리뷰](unknown-fs-K1/review/project/review.md): 외부 계약 미확인, 조사 pending | 핵심 질문은 세 조건에 모두 존재 |

구체적인 비교 근거:

- direct 원문 AI는 “favor operation-specific methods at the editor/caller boundary”를
  제안합니다. FS는 “Operation-specific methods are therefore viable”라고 인정하면서
  “without a demonstrated behavior or maintenance gain”을 이유로 현재 구조를 유지합니다.
  일반 AI도 현재 구조를 유지합니다. **같은 지식을 읽으면 같은 설계를 선택한다는
  보장은 없으며**, 이 차이만으로 지식 미적용이나 설계 실패라고 단정할 수 없습니다.
- mixed 일반 AI는 “Do not add the new actions to the existing `Edit` union until their
  replay semantics and field shapes are agreed.”라고 명시합니다. FS의 “Must either
  new browser action be persisted and replayed?” 질문은 중요한 질문이지만 FS만
  발견한 질문은 아닙니다.
- unknown 원문 AI는 “A search of this excerpt cannot settle those product requirements.”,
  FS도 “A search of this excerpt cannot settle those requirements.”라고 한계를 명시합니다.
- 열두 리뷰 모두 공통 검증·오류 반환·`needs-review`·불변 변환·성공한 최신 상태의
  연속 사용을 다룹니다. 읽은 리뷰에서 이 보존 조건을 명시적으로 깨는 제안이나
  분기만으로 SOLID 위반을 단정하는 결론은 발견하지 못했습니다. 이것은 정적 리뷰의
  관찰이며 구현 결과의 정확성, 완전한 테스트 계획 또는 모든 설계 위험 탐지를 뜻하지 않습니다.

질문의 타당성도 전부 같은 수준이라는 뜻은 아닙니다. 예를 들어 replay 일반 AI는
새 작업에도 `needs-review`를 적용할지 질문해 이미 정해진 전환 규칙과 새 작업의 성공
정의를 혼동시킬 여지가 있습니다. FS에도 이미 보존이 요구된 review status를 새 작업
설명 질문에 함께 묶는 표현이 있습니다. 후속 계획에서는 기존 보존 계약을 재논의하는
질문과 미정인 성공 의미를 더 명확히 구분할 필요가 있습니다.

## FS에서 확인된 연결

| 확인 항목 | 관찰 결과 | 의미의 한계 |
|---|---|---|
| 코드 → 지식 후보 | 4/4 실제 `parameter-dispatch` 신호와 후보 반환 | 평가용 지식 한 건의 직접 트리거 연결 |
| 전체 지식 본문 전달 | 4/4 `read_learned_knowledge`로 전체 본문 반환 | 전달 확인이며 모델 내부 추론에 미친 인과 효과는 아님 |
| 관계 조회 | 4/4 `includeRelations:true` 요청 | 완전한 호출 그래프나 관계 조회의 필요성·절감 효과를 증명하지 않음 |
| 조사 결과 저장 | 4/4 질문별 판단·인용 저장 | gate 통과가 해석의 정확성을 증명하지 않음 |
| 인용·최신성 | 4/4 저장 인용이 해당 코드와 일치하고 선언한 소스 해시 유지 | 선언한 범위 밖의 소비자까지 검사한 것은 아님 |
| 승인·실행 | 승인 호출 0, 제품 변경 0 | 리뷰 범위를 준수했으며 구현 성능을 측정하지 않음 |

저장 결과는 direct `reviewed / keep`, replay·mixed·unknown은 `pending / ask`입니다.
direct는 바꿀 수 있어도 유지하는 판단을, replay와 mixed는 기존 공개 경계를 보존하면서
새 작업의 형식·기록 결정을 남기는 판단을 저장했습니다. unknown에서는 호환성·명령
보존 질문을 `unknown`으로 남겼습니다. 기존 호환성이 알려진 replay의 pending을
“호환성 파악 실패”로 세지 않습니다. 미정인 새 작업의 결정을 기다리는 상태입니다.
모든 기록의 실행 검증 상태는 `unverified`이며, 정적 조사 완료와 실행 검증을 구분합니다.

[mechanism-audit.json](mechanism-audit.json)은 도구 응답·저장 파일·인용·해시를
다시 읽어 작성했습니다. 집계기는 단일 ID 지식 조회의 객체 응답도 처리하도록
수정했습니다. 최초 집계기의 배열 응답 가정 때문에 생긴 본문 전달 미탐을 바로잡은
것이며, 모델 산출물이나 고정 입력을 변경하거나 모델을 재실행한 것은 아닙니다.

## 비용을 늘린 구체적인 동작

1. **관계 정보를 중복 요청했습니다.** direct·mixed·replay FS는 `get_work_context`
   이후 `inspect_code_knowledge`를 두 번 호출하며 관계 정보를 다시 받았습니다.
   direct의 정규화 JSON 응답 크기는 각각 약 44,179 / 23,830 / 24,173자였습니다.
   근거에 계약 문서를 포함하려고 조사 범위를 바꾼 것이 이유 중 하나입니다.
   이는 문자 수이며 토큰 절감 가능량으로 바로 환산하지 않습니다.
2. **도구 입력 오류 3건을 복구했습니다.** mixed는 등록되지 않은 domain으로 검색해
   한 번 거부됐고, 계약 문서가 checklist 조사 `files`에 없어 저장이 한 번 거부됐습니다.
   unknown은 `status:unknown`에 `basis:owner`를 써 한 번 거부됐고 `basis:unknown`으로
   수정했습니다. 세 건 모두 복구됐으며 최종 리뷰와 일치하는 기록을 저장했습니다.
   이들은 제품 코드 오류가 아니라 MCP 입력 계약을 맞추는 과정의 오류입니다.
3. **스킬 지시와 구조화된 저장 자체에도 비용이 듭니다.** FS 네 실행은 스킬과 공통
   절차를 읽고 조사 질문별 판단을 작성했습니다. 일반/원문 조건에는 저장 의무가 없으므로
   비용 차이 전체를 중복 조회나 오류 탓으로 돌릴 수 없습니다. 캐시 입력을 포함한
   누적 컨텍스트 처리도 총 토큰을 키웁니다. 정확한 원인별 토큰 분해는 측정하지 않았습니다.

다음 비용 개선의 검증 가능한 후보는 이미 조회한 코드 관계의 재사용, 처음부터 계약
문서를 포함하는 조사 범위 정렬, 실제 등록 domain과 허용되는 status/basis 조합 안내입니다.
인용·미확인·승인 검증을 없애는 방식으로 비용을 줄여서는 안 됩니다. 이번 실행 중에는
구현·스킬을 바꾸지 않았으므로 이 후보들의 개선 효과는 아직 측정하지 않았습니다.

## 결론과 남은 범위

새 기능은 모델이 **코드 특징 → 조건부 지식 → 호출부·계약 조사 → 근거가 있는
유지/질문 판단 저장**으로 진행할 수 있게 연결됐습니다. 그러나 이번에는 일반 AI도
핵심 제약을 파악했고, 원문을 주는 것만으로도 조건부 설계 검토가 가능했습니다.
구조화된 기록의 존재를 더 좋은 설계 판단의 점수로 바꾸지 않습니다.

이것은 같은 핵심 코드의 네 맥락, 지식 한 건, 모델 한 종류, 셀당 한 번의 집중 회귀입니다.
대규모 프로젝트·지식 검색 정밀도, 자동 지식 변환, 실제 사용자와의 질문·답변,
장기 결정 재사용, 계획→구현 준수, 승인된 위반의 자동 수정, 기존 버전 대비 인과적
품질 개선은 측정하지 않았습니다. 기존 v10과는 과제·절차가 달라 직접 향상률을 계산하지
않습니다. **확인된 결과는 연결의 작동이며, 판단 우위와 비용 절감은 미입증입니다.**
