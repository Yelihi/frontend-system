# 전달량 보완 결과와 마지막 실패 재검증

같은 두 예제·프롬프트·지식·평가 기준으로 FS 분석/계획 4회를 새 세션에서 실행했다.
모두 산출물 저장과 소스/런타임 격리 검사를 통과했으며, 계획은 미승인이다.

| 사례 | 단계 | 총 토큰 | 비캐시 입력+출력 | 초 | MCP 오류 |
| --- | --- | ---: | ---: | ---: | ---: |
| 요청 | 분석 | 667,101 | 81,501 | 226.831 | 0 |
| 요청 | 계획 | 1,452,063 | 96,671 | 286.880 | 3 |
| 스타일 | 분석 | 688,203 | 72,395 | 208.876 | 0 |
| 스타일 | 계획 | 2,001,008 | 92,656 | 331.386 | 3 |

합계 **4,808,375 / 343,223 / 오류 6건**이다. 첫 FS의 5,728,903 / 315,271 / 21건과
비교하면 총 토큰은 16.1% 줄고 오류는 71.4% 줄었으나, 비캐시 입력+출력은 8.9% 늘었다.
따라서 전체 운영 비용이나 품질의 개선으로 해석하지 않는다. 같은 지식 AI보다도
사용량이 크다. 샘플링·캐시 변동이 있고 여러 수정을 함께 적용했으므로 단일 변경의
인과적 효과를 분리한 실험도 아니다.

계획 조회는 두 사례 모두 summary로 시작했고, 분석의 generic scope 오류는 사라졌다.
표준 $ref를 사용한 계획 도움말은 22,065 → 14,769자로 줄었다. 검사 조건은 유지했다.
계획의 오류는 조사 인용 line/confirmation, 적용 대상과 제외 조건의 혼동, 경로가
빠진 요구 문서 인용, 결정 연결이 없는 규칙이었다. [원본 집계](summary.json),
[기계적 연결 감사](mechanism-audit.json), [응답량 감사](response-size-audit.json)를 보존한다.

## 의미 검토: 저장 성공과 좋은 계획은 달랐다

두 계획은 새 호출자에 따른 stale을 확인하고 flow/finding을 갱신했다. 참조된 과거
기록의 해시·ID가 일치하며, 배경 서비스 토큰과 상호작용 인증 분리, 이후 편집 보호,
필수 variant 축/네 조합/팔레트/Indicator/store 경계를 다뤘다. 최종 저장 당시
두 contractDiagnostics는 비어 있었다. 그러나 다음 실패가 남았다.

1. **도메인 행동을 자의적으로 확대했다.** 요청 계획은 `order-validation [resolved, model]`로
   비유한 수량 거부를 확정했다. 원 계약은 검증 실패의 부작용을 제한했을 뿐,
   기존 `<1` 판정을 새로 확장하라고 정하지 않았다. 계획도 “Changes NaN and infinity
   behavior”라고 비용을 명시했다. 최초 FS/동일 지식 AI가 보존한 경계를 이번 FS는
   넘었다. 첫 비교의 한 차이를 안정적인 지식 효과라고 일반화할 수 없다.
2. **검사기가 잘못된 우회를 유도했다.** 스타일 검사기는 CVA 각 축에 defaultVariants가
   반드시 있어야 한다고 가정했다. 계획은 필수 props/기본값 없음 계약을 지키면서
   검사를 통과하려고 null defaults를 제안했다. 검사가 사용자의 계약을 표현하지 못한
   제품 결함이다. 기존 예제 코드나 점수를 바꾸어 감추지 않았다.
3. **예정 검사 명령의 본문이 틀렸다.** `script:test, command:npm test`를 그대로
   package.json에 설치하면 자기 호출이다. helper 상대 경로는 이전 보완판의 오류를
   고쳐 `../runtime/...`로 기록했지만, 검사 준비가 완료된 것은 아니었다.

## 실패를 반영한 최종 코드와 재검증

모델 출력·기준·토큰 집계는 변경하지 않았다. 이후 소스에 다음을 추가했다.

- 필수 domain 규칙은 user/existing 결정의 공급된 권한 근거에 연결되어야 한다.
  model 결정만으로 새 도메인 결과를 확정하면 승인/시작 검증에서 거부한다. 내부
  구현 선택과 도메인 결과를 분리한다. 이미 답한 계약은 재질문 없이 연결할 수 있다.
- CVA 정책에 `defaults:none`을 추가해 defaultVariants가 없는 승인된 형식도 검사한다.
  생략 시 종전 per-axis 요구를 유지하므로 기존 정책을 몰래 완화하지 않는다.
  `style-check.js --schema`로 입력을 읽을 수 있다. 공개 props 타입/실제 클래스 결과는
  별도 검사 대상이다. [CVA 공식 예제](https://cva.style/getting-started/variants/)도
  defaultVariants 없는 variant 설정을 제공한다.
- 직접 `npm test` / `npm run test` / `npm run-script test`로 자기 script를 호출하는
  정책은 수리 가능한 초안으로 남지만 승인/사용을 차단한다. 임의 shell과 간접 순환을
  전부 탐지하는 검사는 아니다.

[실제 실패 산출물 재검증](post-eval-guard-replay.json)은 추가 모델 호출 없이 원본 계획을
새 검증에 넣었다. 요청의 validation/draft-order는 model 권한만 연결되어 차단됐고,
스타일의 자기 호출도 차단됐다. draft-order의 결과는 이미 주어진 계약에 있으므로
기존 답변을 연결하면 된다. 비유한 값의 새 거부는 제안/미결정으로 남겨야 한다.

이것은 **승인 전 차단 개선**이지 모델이 더 좋은 계획을 생성했다는 재실험 결과가
아니다. 마지막 권한/CVA/자기 호출 보완 뒤 전체 모델 비교는 다시 하지 않았으며,
116개 코드 회귀와 배포 패키지 검사, 실패 산출물 재검증으로 확인했다. 모델이 잘못된
layer/authority를 선언하거나 근거를 오해하면 이 검사를 통과할 수도 있다. 자연어
계약의 의미 정확성과 모든 무단 변경을 자동 증명한다고 주장하지 않는다.

기존 지식·조건·코드가 새로운 질문과 결정의 차이를 일관되게 만드는지, 실제 개발자
대화와 대규모 코드에서 이 기록 비용이 상각되는지는 추가 검증이 필요하다. 이번 결과는
일반 AI 대비 FS의 설계 우위나 토큰 절감을 입증하지 못했다.
