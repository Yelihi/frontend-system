# v12 — 흐름 재사용과 변경 후 계획

같은 설계를 구현하는 능력 대신, 기존 프로젝트를 해석하고 그 해석을 다음 요청에서
정확히 재사용하는 과정을 비교합니다. 일반 AI / 실제 전체 지식 제공 AI / FS가
DOM 요청·캐시 프로젝트와 React/Tailwind 프로젝트를 분석합니다. 새 호출자와
사용자 답변을 넣고 문맥이 초기화된 새 세션에서 계획을 작성합니다.

- [실행 전 고정한 기준](protocol.md)
- [요청·캐시 예제](projects/request/README.md)
- [컴포넌트·공유 상태 예제](projects/styles/README.md)
- [실행기와 단계별 변경 입력](run.py)

각 호출은 gpt-6-sol medium, 900초, 최대 2개 병렬입니다. FS만의 추가 분석·계획 저장
비용도 포함합니다. 총 토큰과 비캐시 입력+출력, 실제 코드 흐름, 계약 보존, 조건·반례,
답한 질문의 재질문, 오래된 분석의 사용, 계획과 기록의 일치를 별도로 봅니다.
분석자에 의한 정성 판정이 포함되므로 블라인드 평가나 통계적 우위를 주장하지 않습니다.

## 비교 대상과 이유

| 단계 | 요청·캐시 프로젝트 | 컴포넌트·공유 상태 프로젝트 |
| --- | --- | --- |
| 초기 분석 | 이벤트 → 입력 → save → 요청/인증 → 낙관적 캐시 → 구독자/오류, 이후 편집과 이전 응답 | 클릭 → Button → store → 두 구독 페이지, props/네 가지 변형/정리 |
| 새 입력 | 서비스 토큰을 사용하는 background 호출자, 로그인 UI 효과 금지 | large/danger 호출자, 팔레트 유지·테마 토큰 미도입 답변 |
| 계획 확인 | 기존 입력 보존·재시도 금지·나중 편집 보호를 유지하며 인증 경계 수정 | 필수 props·네 조합·Indicator 제외·store 소유권을 유지하며 승인된 팀 정책 적용 |

기능 실행 점수가 아니라 **분석 근거 → 지식 조건 → 사용자 답변 → 제한된 변경 계획**을
검토합니다. 새 파일을 발견하는지, 답한 내용을 다시 질문하는지, 승인되지 않은 동작을
추가하는지, 같은 지식만 제공해도 같은 판단이 나오는지를 따로 봅니다. 조건별 1회이므로
점수를 합산해 일반적인 설계 우위라고 부르지 않습니다.

각 행은 두 프로젝트의 초기 분석과 변경 후 계획 합계입니다. 총 토큰은 도구 호출마다
다시 입력된 캐시를 포함하며 단일 컨텍스트 크기나 비용 금액이 아닙니다. 실패와 복구
사용량도 포함합니다. 사전 검사·FS 자체 검사에는 모델 호출이 없으며, 평가를 준비하고
검토한 상위 대화의 사용량은 이 표에 포함하지 않습니다.

비캐시 입력+출력 1,239,533 / 사용량 누락 0회**입니다. 지정 위치 산출물 기준 18/20이며,
위치 불일치 두 건도 결과·비용에 포함합니다. 후속 FS 두 버전은 각각 4/4 저장됐습니다.
첫 FS 대비 마지막 모델 실행의 총 토큰은 16.1% 줄었지만 비캐시 입력+출력은 8.9%
늘었습니다. 오류 감소를 운영 비용이나 설계 품질의 우위로 바꾸어 해석하지 않습니다.

확인한 결함이 있는 경우에만 다른 이름의 수정본을 실행했습니다. 일반/동일 지식의
변경 없는 실행을 좋은 결과가 나올 때까지 반복하지 않았습니다. `flow-2`, `flow-3`은
런타임 준비만 한 기록이며 모델 호출 0회입니다. 후속 코드 변화의 회귀 관찰이지
독립 holdout이나 블라인드 품질 평가가 아닙니다.

## 현재 확인한 의미 차이

첫 비교에서 모든 조건이 새 요청 소비자의 인증 분리, 새 Button 호출자, 필수 props와
팔레트/Indicator 경계를 반영했습니다. 일반 AI 요청 계획은 기존 `<1` 검증을 넘어
NaN/비유한 수량 거부를 추가했습니다. 같은 지식 AI와 FS는 수량 도메인 확대를
범위 밖으로 남겼습니다. 구체적인 범위 통제 차이지만 **같은 지식 AI도 같은 판단을
했으므로 FS만의 품질 우위로 해석할 수 없습니다.**

FS는 새 호출자에 따른 분석 stale을 감지하고, 갱신한 flow/finding 해시를 계획에
연결했습니다. 반면 첫 보완에서도 범위 밖 질문의 open 결정, 아직 준비되지 않은
검사 명령 문제가 남았습니다. 해시 일치나 빈 contractDiagnostics가 실행 성공·
의미 정확성·계획 승인 가능성을 모두 증명하지 않습니다.

마지막 모델 실행에서는 FS도 비유한 수량 거부를 자의적으로 확정했습니다. 이후
필수 domain 규칙의 공급된 권한 검증, CVA의 기본값 없음 정책, 직접 npm 자기 호출
차단을 추가했습니다. 보존한 실패 계획을 새 검증에 넣어 차단을 확인했지만, 이 마지막
보완 뒤 전체 모델 비교를 다시 수행한 것은 아닙니다. 모델의 의미 판단 우위는 미입증입니다.

## 검증 범위와 재현

[FS 검사 로그](results/verification-2026-10-06/npm-check.log): typecheck/lint 및
116개 회귀 통과. [배포 패키지 검사](results/verification-2026-10-06/package-smoke.log)와
네 스킬 형식 검사도 통과했습니다. [시각화 브라우저 검사](../../../../docs/examples/frontend-flow-browser-check.json)는
중첩/이벤트/단계, 데스크톱·모바일 넘침과 JS 오류를 확인합니다. Mermaid도 실제 SVG로
렌더했습니다. 예제 프로젝트 구현·앱 실행이나 런타임 성능 검사는 수행하지 않았습니다.

```sh
python3 test/evals/fs-comparison/v12/run.py prepare --output /absolute/new-result
python3 test/evals/fs-comparison/v3/maintenance/run.py --preflight-only --models gpt-6-sol --output /absolute/new-result/isolation
python3 test/evals/fs-comparison/v12/run.py analysis --output /absolute/new-result
python3 test/evals/fs-comparison/v12/run.py plan --output /absolute/new-result
node scripts/audit-flow-eval.mjs /absolute/new-result
```

첫 preflight의 무관한 검색어 때문에 새 조사 명세를 일괄 제외한 실패는
`flow-1/isolation-before-fixture-fix`에 보존했습니다. 규칙을 완화하지 않고 중립적인
프로토콜 probe로 정정했습니다. 첫 비교의 산출물 위치 불일치 2건도 보존하며,
그중 후속 단계에 필요한 분석 1건만 동일 바이트로 복사하고 복구 해시를 기록했습니다.

두 예제는 작고 알려진 조건으로 작성했습니다. 비교용 analysis.md와 FS의 추가
구조화 기록 비용을 모두 포함하므로 통상 작업의 정확한 비용 예측은 아닙니다.
대규모 프로젝트에서의 상각 효과, 자연어 원문의 자동 변환 정확도, 새 기능의 실제
사용자 대화, 구현 품질 향상은 이 실험으로 입증하지 않습니다. 실제 지식의 조사
명세 이전은 66개 direct 참조 중 2개이며 나머지는 legacy-checklist입니다.


## 실제 코드 기반 시각화 보완 (2026-10-07)

[주문 HTML](../../../../docs/flows/order-workspace.html)과

새 모델 비교를 실행하거나 이전 성능 결과를 변경한 작업은 아닙니다.

로컬 시각화 생성이 다음 비교 입력에 섞이지 않도록 준비 단계의 fixture 복사 및
입력 해시는 `.frontend-system`을 제외합니다. 제품 소스와 제공된 요구사항은 유지했습니다.
실행 검사에는 mock HTTP와 EventTarget을 사용했고 React 렌더는 측정하지 않았습니다.
브라우저 도구의 로컬 주소 보안 차단으로 이번 HTML의 시각적 검사는 미완료입니다.
