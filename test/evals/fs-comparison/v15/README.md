# v15 — 지식 검색과 설계 판단을 분리한 진단

기존 공개 지식 71개를 그대로 사용한다. 지식을 추가하거나 일반 모델이 지도록
원문을 숨긴 비교를 FS 고유 효과로 주장하지 않는다. 전체 FS 계획/구현 워크플로가
아닌 **검색 연결 부분의 진단**이다. [사전 고정 프로토콜](protocol.md),
[실제 코드·상황·사전 판정 기준](cases.json), [검색 질문](retrieval-cases.json).

## 연구를 반영한 변경

- [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)의 문맥 보존 원칙: 기존 제목·키워드·요약뿐 아니라 이미 검토된 적용 조건, 제외 조건, 체크 질문, 조사 지침도 검색한다. 새 임베딩 모델이나 BM25를 구현한 것은 아니다.
- [ALCE](https://arxiv.org/abs/2305.14627)의 평가 구분: 출처/인용의 존재, 그 인용이 결론을 뒷받침하는지, 실제 결정의 적합성을 분리한다. `matchedFields`는 검색어가 맞은 위치이며 의미 검증/신뢰도 점수가 아니다.
- [LongMemEval](https://github.com/xiaowu0162/LongMemEval)의 근거 직접 제공·지식 갱신 평가를 참고: 같은 코드에 채택/미채택/미확정/이전 결정을 대체한 현재 예외를 준다. 관련 지식만 직접 주는 oracle은 원인 진단용이며 제품 경쟁 조건이 아니다.

기존 근거 해시·조사 질문·미확정 의도·승인 검증은 유지했다. workflow 지침에는
지식의 주장 → 코드/계약 근거 → 적용 조건 → 반례를 기존 판단 기록 안에서 연결하고,
현재의 명시적 결정을 이전 기록과 구분하도록 보강했다. 새 기록 단계는 추가하지 않았다.
이 workflow 문구 변경 자체는 아래의 검색 전용 모델 실험으로 평가되지 않는다.

## 실제 코드의 trigger 연결

[제품 라우팅 관찰](measurements/routing.json)은 사례의 실제 코드와 자연어 요청을
`routeKnowledge`에 전달한 결과다. 모델이 의미 신호를 보충하지 않은 조건에서 8개 중
6개가 필요한 지식을 모두 후보로 받았다. 업무 이유가 다른 검증 함수와 여러 기기 간
잠금 사례에서 누락이 남았다. 후보 수는 5–10개로, 후보가 많아도 관련 근거를 놓칠 수 있다.
검색 단위 검사의 12/12를 전체 trigger 해석의 완성으로 해석하면 안 된다.

## 모델 비교

`gpt-6-sol`, medium, 사례마다 새 문맥, 최대 180초, 동시 실행 2개.
8개 사례 × 4개 조건이며 평가 기준·다른 실행·개인 설정의 파일 접근을 차단한다.

| 조건 | 제공 정보/도구 |
|---|---|
| ordinary | 코드와 현재/이전 사용자 결정; 추가 지식 없음 |
| raw | 같은 코드/결정 + 전체 공개 지식/색인, 일반 파일 검색 |
| fs-search | raw와 동일 + 실제 제품 검색/해시 검증 읽기를 호출하는 helper |
| oracle | 관련 공개 지식 본문만 직접 제공; 정답 결정은 제공하지 않음 |

`raw`는 변환 전 원문이 아니라 FS와 **동일한 공개 지식**이다. 따라서 raw와 fs-search의
차이가 검색 연결 도구의 추가 효과다. ordinary가 비공개 팀 정책을 몰라 질문하는 것은
올바른 보류로 기록하고, 지식 없이 위험한 판단을 한 것으로 감점하지 않는다.

## 실제 실행 결과와 중단 판단

2026-10-08, 32개 독립 세션 모두 완료. 입력 파일 변경·격리 실패·사용량 누락은 없었고,
32개 답변의 인용 문자열이 실제 파일과 일치했다. 인용 일치가 의미적 정확성을 뜻하지는 않는다.
[조건별 수치·전체 생성 답변·검색 추적](measurements/model-results.json),
[격리 검사](measurements/isolation.json), [코드 버전·검사 이력](measurements/provenance.json).

| 조건 | 완료 | 총 입력+출력 토큰 | 비캐시 입력+출력 | 도구 호출 |
|---|---:|---:|---:|---:|
| 일반 AI | 8/8 | 305,070 | 83,246 | 28 |
| 동일 지식 + 일반 검색 | 8/8 | 603,389 | 134,013 | 73 |
| 동일 지식 + FS 검색 도구 | 8/8 | 615,777 | 158,049 | 54 |
| 관련 근거 직접 제공 | 8/8 | 422,398 | 99,966 | 43 |

전체 1,946,634토큰, 비캐시 입력+출력 475,274토큰. 세션 수와 실제 도구/모델 응답 수는
같지 않다. 비용은 해당 CLI 사용량이며 청구 금액으로 환산하지 않았다. FS 검색 조건은
동일 지식 일반 검색 대비 도구 호출이 26.0% 적었지만 총 토큰은 2.1%, 비캐시 입력+출력은
17.9% 많았다. 단회 표본의 관측이며 반복 검증된 비용 우위가 아니다.

| 상황 | 담당 AI의 사후 답변 내용 검토 |
|---|---|
| 정책 채택 | ordinary는 모르는 팀 정책 본문을 요청. 나머지 세 조건은 JSX 고정 클래스·CVA 축·기존 색 보존을 연결했다. |
| 정책 미채택 | 네 조건 모두 스타일 재작성을 강제하지 않았다. |
| 정책 미확정 | 네 조건 모두 채택 여부를 질문하고 이미 결정한 팔레트는 재질문하지 않았다. |
| 정책 변경 | 네 조건 모두 이전 채택보다 현재의 범위별 예외를 적용했다. |
| POST 재시도 계약 미확인 | 네 조건 모두 일괄 재시도를 도입하지 않고 서버 계약의 필요성을 설명했다. |
| 변경 이유가 다른 검증 | 네 조건 모두 단순 중복을 이유로 도메인 플래그 공통화를 강제하지 않았다. |
| 단순 Badge | 네 조건 모두 불필요한 Compound/Context 도입을 거절했다. |
| 여러 기기 간 잠금 | 네 조건 모두 브라우저 잠금을 서버의 중복 방지 보장으로 취급하지 않았다. |

이 내용 검토는 실험을 만든 **동일 AI의 사후 검토**다. 독립된 사람의 블라인드 평가나
설계 정확도 100%의 증거가 아니다. ordinary의 정책 자료 요청은 정상적인 정보 부족 대응이며,
자료 접근이 있는 조건의 차이는 지식 제공 효과다. raw와 fs-search 사이의 핵심 판단 우위는
관찰되지 않았다. 원문 링크를 더 많이 달았다는 사실로 우위를 만들지 않는다.

원래 `actionMatches`는 ordinary 6/8, 다른 조건 7/8이다. 이 수치를 정확도로 쓰면 안 된다.
여러 기기 잠금 사례에서 네 조건 모두 잘못된 제안을 거절했지만, 채점자는 `keep/ask`를,
모델들은 제안을 바꾸라는 뜻의 `change`를 사용했다. 원래 결과는 보존했다. 다음 평가에서는
**제안 수용 여부와 현재 코드 변경 여부를 별도 항목**으로 정의해야 한다.

검색 연결의 한계도 실행에서 확인했다. 업무 검증 분리 사례에서 FS 검색은 필요한
`code-quality-change-boundaries`를 반환하지 못했고, 모델이 일반 파일 검색으로 찾아
답했다. 잠금 사례는 모델이 `Web Locks`를 검색어에 보충한 뒤 관련 지식을 받았다.
정책 변경 사례에서는 FS 도구를 제공했지만 모델이 본문을 직접 읽었다. 따라서 FS 조건의
모든 성공을 자동 trigger나 FS 검색의 성공으로 계산하지 않는다.

검색 helper는 실제 제품 함수의 후보 메타데이터와 참조 읽기 결과를 함께 반환한다.
한 번에 약 7,344–30,123문자가 출력됐으며 두 반환값 사이에 메타데이터 중복도 있다.
도구 호출 감소가 입력 토큰 감소로 이어지지 않는 원인 후보지만, 이 요인만 분리한
비교는 하지 않았다. 실험 중 반환 형식을 바꿔 서로 다른 조건의 실행을 섞지 않았다.

**첫 회차 후 모델 반복을 중단했다.** 사전 중단 조건인 판단 차이의 부재와 평가 기준의
모호성이 드러났기 때문이다. 조건을 어렵게 바꾸거나 특정 단어를 추가해 FS가 이길 때까지
이 사례들을 반복하지 않는다. 다음은 실제 프로젝트에서 사용자가 AI 제안을 수정했던
결정 사례와 그때 필요했던 근거를 수집하고, 제안 수용/수정 범위/미확정 의도를 독립적으로
판정하는 평가가 필요하다. 새 지식이 많아지면 자동으로 우위가 생긴다는 결론도 아니다.

## 재현

```sh
npm run build
python3 test/evals/fs-comparison/v15/test_runner.py
node test/evals/fs-comparison/v15/retrieval.mjs /tmp/fs-retrieval-new.json
python3 test/evals/fs-comparison/v15/run.py prepare --output test/evals/fs-comparison/v15/results/NEW_RUN
python3 test/evals/fs-comparison/v15/run.py run --output test/evals/fs-comparison/v15/results/NEW_RUN
```

현재 실행 환경의 기존 macOS Codex 격리 실행기를 재사용한다. 새 출력 경로가 필요하며,
실행 이력은 덮어쓰지 않는다. `prepare`는 모델을 호출하지 않고, `run`은 최대 32개 실제
모델 세션을 실행한다. 원시 대화·복사된 지식은 results 아래에 로컬 보관하고 Git에서 제외한다.
