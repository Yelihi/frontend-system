# v6: 4배 이상 확대한 운영 콘솔 계약 평가

v5와 별개인 사전 고정 과제다. 주문·재고·반품·지갑, 세션 교체, 중복 요청, 결제 실패 보상, 환불 성공 후 재입고 실패를 함께 다룬다. 단순 파일 복제가 아니라 여러 도메인에 걸친 성공/실패 순서와 원본 객체·오류 보존을 검증한다.

| 규모 | v5 | v6 | 배율 |
| --- | ---: | ---: | ---: |
| 변경 허용 제품 파일 | 7 | 32 | 4.57× |
| 기준 제품 코드 줄 수 | 71 | 386 | 5.44× |
| 기준 제품 코드 bytes | 3,124 | 19,116 | 6.12× |
| 독립 채점 항목 | 14 | 69 | 4.93× |
| 질문 후 제공하는 사용자 결정 | 2 | 8 | 4.00× |

보호된 format 함수와 평가용 런타임은 코드 규모에서 제외한다. 시작 코드에는 32개 파일에 각 결함이 있다. 2개 정상 구현과 38개 단일 결함 변이로 채점기를 교정한다. 교정은 모델 호출 0회이며 AI 우위의 증거가 아니다.

## 실행 전에 고정한 조건

- 모델 gpt-6-sol, 두 군 모두 같은 초기 Git 코드·계획·지식 원문·8개 답변.
- 군별 새 디렉터리·새 모델 문맥. prepare→사용자 답변→work는 해당 군의 같은 thread를 이어간다. 외부 실패 시 최대 한 번 수정 기회.
- 각 호출 시간 제한 2,400초(기존 600초의 4배). 두 군 동일. 타임아웃·누락 사용량은 그대로 보존한다.
- FS는 기존 근거·프로젝트 분석·지식 라우팅·결정·승인·실행 검증 절차를 사용한다. 준비 단계 제품 변경, 보호된 파일/의존성 변경은 금지다.
- 모델·채점 코드는 기존 제한된 실행기로 격리한다. 바깥 제어기에만 네트워크/실행 권한을 부여한다.
- 정답/변이/채점기는 모델에게 제공하지 않는다. 실제 실행 이후 채점 기준을 특정 결과에 맞춰 변경하지 않는다.

## 개선 판정

1. 품질: 69개 계약, 8개 결정, 금지 범위, FS 실행 증거를 별도로 기록한다. 통과 항목 수만으로 브라우저/유지보수성 전반의 우위를 주장하지 않는다.
2. 비용: 전체 토큰, 비캐시 입력 토큰, 시간, 외부 수정 회수, MCP 오류, 재사용·반복 읽기를 기록한다. 캐시 토큰 감소와 실제 청구액은 구분한다.
3. 먼저 현재 FS를 실측하고 관측한 병목만 수정한다. 같은 v6 과제와 기준으로 재실험하고, 수정 버전을 고정해 반복 확인한다. 좋은 결과만 선택하지 않는다.
4. v5와 v6는 다른 과제이므로 두 버전 간 토큰 변화는 FS 최적화 효과로 계산하지 않는다. 아직 실제 결과가 없거나 차이가 없으면 그대로 기록한다.

## 재현

```sh
python3 -m unittest discover -s test/evals/fs-comparison/v6 -p runner_test.py
python3 test/evals/fs-comparison/v6/run.py --calibrate-only
python3 test/evals/fs-comparison/v6/run.py --run --model gpt-6-sol
python3 test/evals/fs-comparison/v6/telemetry.py test/evals/fs-comparison/v6/results/<실행 ID>
```

계약은 PLAN.md, 질문은 compliance.json, API/의존성은 contract.json, 외부 채점은 evaluate.mjs다. UI는 제어된 hook/element 모의 실행과 esbuild 검사이며 실제 브라우저·React scheduler·화면 품질/접근성 전체 검증은 아니다. 질문의 존재와 답 반영을 검사하며 실제 사용자가 느끼는 질문의 적합성은 별도 평가 대상이다.

### 수정과 재실험

- **A→B:** 남는 읽기 예산을 긴 파일에 재분배(총 24,000자·해시·이어읽기 유지), 문서 CAS와 소스 해시 구분, 같은 planId의 baseline 연결. B1은 토큰 -28.1%였으나 같은 manifest의 B2는 절차 생략으로 실패했다.
- **B→C:** 실제 범위의 파일 이름을 검색 단서로 추가하고 scope-search 출처를 표시했다. 이름만으로 의미 트리거나 적용 판단을 생성하지 않는다. 분석 기록 선행 조건과 첫 편집 전 승인·실행 확인도 보강했다. C는 절차·지식 연결을 수행했으나 계층별 4개 issue, 검사 10회 등으로 527만 토큰까지 증가했다. 비용 회귀도 보존했다.
- **C→D:** 공동 승인·공동 배포 변경은 기본 하나의 실행 issue로 묶고 내부 작업 순서를 계획 안에 둔다. 독립 산출물·실제 승인 checkpoint·외부 선행 조건이 있을 때 분리하며 사용자 milestone과 기존 승인 경계는 유지한다. 등록 domain 사용, 의미 검토 후 완료 저장 순서도 명시했다. 강제 검증 guard와 모든 계약은 유지했다.

D1/D2는 **manifest가 완전히 같은 독립 재실행**이다. 두 번 모두 1개 issue, MCP 오류 0, 재사용 사실 1개 등록, 승인·시도·의미 검토·완료 저장 통과다. D1은 MCP 23회/검사 4회, D2는 29회/검사 8회다. D2는 답변 전 초안 기록, 추가 소스 확인, SSR 테스트 JSX loader 오류 1회 수정 등이 있어 더 비쌌다. D1에서는 양쪽 제품 파일 25/32개가 바이트 단위로 같았다.

D1/D2 평균 FS는 **2,853,774.5 총 토큰, 86,843.5 비캐시 입력, 733.094초**다. 최초 A의 FS 대비 각각 **33.2%, 34.3%, 24.0% 감소**했다. 개별 총 토큰 감소는 53.4%와 13.1%로 편차가 크다. 이 두 번에서 처리량 감소는 재현됐지만 통계적으로 안정적인 일반 개선율을 증명하지는 않는다.

동일 두 실행의 일반 AI 평균과 비교하면 FS는 총 토큰 **3.88배**, 비캐시 입력 **1.49배**, 시간 **1.67배**다. **FS 자체 최적화는 관측했으나 일반 AI 대비 구현 준수/비용 우위는 입증하지 못했다.** 캐시·출력 요율을 적용하지 않은 총 처리 토큰은 청구액이 아니다.


### 해석 범위와 확인 방법

고정 계획이 아키텍처·API·소유권·오류 처리까지 이미 양쪽에 주어져 69점의 천장이 반복됐다. 프로젝트를 확대했다는 사실만으로 FS의 효과가 생기지는 않았다. 32파일/386줄은 v5보다 크지만 실제 대형 제품을 대표하지 않는다. 사용자 질문의 존재와 답 반영은 검사하지만 질문의 적합성·근거의 설득력·사람의 판단 개선, 실제 브라우저와 장기 유지보수성은 이 점수로 판정하지 않는다. 코드 파일 유사도 또한 유지보수성 점수가 아니다.

- 각 실행 `analysis.md`: 원인과 해석, `summary.json`: 원래 채점·단계 기록, `telemetry.json/md`: 전체/비캐시 토큰·재사용·호출량.
- `comparability.json`: 조건/런타임 동일성. 최신 `aggregate.json`: 전체 회차 처리량(실패 포함)과 최종 고정 버전 2회 평균.
- `operations-console-{plain,fs}/work/0/snapshot/`: 실제 작성 코드. FS의 `.frontend-system/`에는 계획·결정·실행 근거가 보존된다. 생성 코드는 데이터로 검토하고 실행은 격리된 평가기로만 한다.
- 코드 회귀: 타입·린트·82개 테스트, 패키지 검증 통과. 실행기 4개와 집계기 4개 검사를 CI에도 포함했다. CI는 작성된 fixture/교정 검사만 수행하며 유료 모델 비교를 자동 호출하지 않는다. 원격 GitHub Actions 실행 결과를 의미하지 않는다.

링크가 열리지 않으면 저장소 터미널에서 `less test/evals/fs-comparison/v6/README.md`로 읽을 수 있다. 핵심 계약은 `PLAN.md`, 실제 코드는 위 snapshot 경로에서 확인한다.
