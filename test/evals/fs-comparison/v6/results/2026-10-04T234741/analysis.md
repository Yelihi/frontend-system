# 검색·선행 조건 보강 후 비교: 비용 증가

| 군 | 외부 계약 | 절차 적격 | 총 토큰 | 비캐시 입력 | 시간(초) | MCP 오류 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 일반 AI | 69/69 | 통과 | 461,491 | 47,870 | 383.655 | 0 |
| FS | 69/69 | 통과 | 5,267,923 | 124,201 | 1,136.093 | 2 |

두 군 모두 외부 수정 0, 결정/금지 위반 0이다. FS 총 토큰은 최초 FS보다 23.3% 증가했고 비캐시 입력은 6.1% 감소했다. 시간은 17.8% 증가했다. 이 회차 일반 AI 대비 총 토큰 11.42배다. 비용 개선으로 주장하지 않는다.

프로젝트 사실 5개 중 1개가 재사용 등록되어 두 context에서 신호를 냈다. request-policy-boundaries를 검색하고 본문을 읽어 적용 판단했다. 실제 후보 이유는 code-trigger이며 scope-search만의 효과로 해석하지 않는다. 별도 routing-diagnostic.json은 고정 입력의 기존 누락 후보/의미 발견 항목이 새 검색에서 나오며 의미 신호를 자동 생성하지 않음을 보여준다(모델 호출 0). 공개 index 진입점으로 검사했고 내부 routing 모듈 직접 import는 기존 순환 초기화 문제로 실패했다.

준비에서 프로젝트 기록→라우팅→계획, 작업에서 실제 사용자 승인→실행 초기화→baseline→attempt→편집 순서가 관측됐다. 뒤의 완료 기록도 수락됐다. 다만 domain ID를 추측한 검색 오류 1회와 의미 검토 전에 완료 저장한 오류 1회가 있었다.

이전 정상 실행들은 32개 파일을 하나의 실행 issue로 처리했다. 이번에는 shared-domain→repositories-services→workflows→ui의 4개 issue로 나눠 begin 4회, 검토 4회, 검사 10회, 실행 저장 7회를 사용했다. MCP 총 44회(직전 정상 B1은 26회). 뒤에서 앞선 도메인 검증을 보강하고 재검증했다. 브라우저 프로세스 권한 실패 1회 후 SSR/모의 이벤트 검증을 추가했다. 자동 검사의 통과가 실제 브라우저 검증은 아니다. 단계 수/모델 구현·검증 선택도 달라 단일 개입의 인과 효과는 확정하지 않는다.

다음 개입은 독립 배포/승인/외부 의존성이 없는 공동 변경을 한 실행 issue로 묶는 기본 계획 지침, 등록된 domain만 사용, 의미 검토 후 완료 저장 순서다. 기존 승인 경계/모든 계약/채점/검증 guard는 유지한다. 정답·변이·과제·제한은 고정한다。
