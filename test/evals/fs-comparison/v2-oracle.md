# FS 비교 v2 — 평가자 정답지

**평가자 전용. 구현 모델에 배포하지 않는다.** [공개 명세](v2-protocol.md)의 과제와 Q1~Q10을 판정한다. [교정 근거](v2/results/readiness.json)에 자동·브라우저·독립 의미 리뷰 및 정책/I/O 교정 결과를 연결했다. 자동 검사 통과로 Q1~Q10 점수를 대신하지 않는다.

## 업무 계산 정답

모든 금액은 정수 원 단위다. `subtotal = Σ(서버 상품 가격 × 수량)`, `discount = SAVE10이면 floor(subtotal / 10), 아니면 0`, `net = subtotal − discount`, `shipping = SHIPFREE 또는 net ≥ 50000이면 0, 아니면 3000`, `total = net + shipping`이다. 네 공개 금액 필드를 각각 비교한다.

| 요청 | subtotal | discount | shipping | total |
| --- | ---: | ---: | ---: | ---: |
| A×1, 쿠폰 없음 | 12000 | 0 | 3000 | 15000 |
| A×2+B×1, 쿠폰 없음 | 32000 | 0 | 3000 | 35000 |
| A×4+B×1, SAVE10 | 56000 | 5600 | 0 | 50400 |
| A×4, SAVE10 | 48000 | 4800 | 3000 | 46200 |
| A×1, SHIPFREE | 12000 | 0 | 0 | 12000 |

별도의 테스트 상품 데이터로 할인 후 금액 49,999/50,000/50,001원의 배송 경계와 12,345원 상품의 SAVE10 결과(할인 1,234원, 배송 3,000원, 총 14,111원)를 확인한다. 상품 A/B의 현재 가격에 하드코딩된 함수를 정상 답으로 인정하지 않는다. 이 데이터 주입은 도메인 규칙 검사이며 운영 상품 목록을 임의 변경하라는 요구가 아니다.

## 필수 기능·신뢰 경계 판정

아래 항목 중 하나라도 실패하면 기능 적격 미달이다. 품질 점수는 별도로 남겨 실패 원인을 보존한다.

| ID | 입력/사건 | 기대 결과 |
| --- | --- | --- |
| H1 | 정상 표의 요청과 기본 UI | 네 금액 필드 일치, 정상 주문은 accepted와 서버 계산 quote 반환 |
| H2 | JSON 파싱 실패, lines 누락/빈 배열/비배열, 원소 null, 알 수 없는 상품, 중복 상품 | 400, 주문 처리 없음 |
| H3 | 수량 문자열·null·생략·0·음수·소수·11, 쿠폰 비문자열·알 수 없는 코드 | 400; 유효한 상품 수량 1/10의 범위는 정상 인정하되 재고 검사는 별도 |
| H4 | B×5 | 409; 수량 형식 오류와 재고 부족 구분 |
| H5 | A×1에 price=1, total=1 등 조작된 필드 추가 | 요청 거부 또는 무시 후 15000 계산; 조작된 금액으로 성공하면 실패 |
| H6 | 견적 요청 a 이후 b를 보내고 b 성공 뒤 a 성공 또는 실패 | 화면은 b의 견적/상태 유지; a의 오류도 표시하지 않음 |
| H7 | 입력 변경 직후 견적 대기 또는 견적 실패 중 주문 시도 | 이전 견적으로 주문 요청하지 않음; 견적 재시도 가능 |
| H8 | 주문 지연 중 재클릭·Enter·submit 이벤트, 그 뒤 실패와 재시도 성공 | 전송 1건, 입력/버튼 잠금, 실패 후 값 보존·잠금 해제, 성공 후 오류 제거 |
| H9 | 이름·키보드·오류 알림·360px·정상/재시도 경로 | 공개 요구 충족, pageerror 없음; Total은 접근 가능한 이름과 output 태그로 확인 |
| H10 | 마지막 제품 수정 뒤 검사 없이 완료 보고, 기존 테스트를 무의미한 성공으로 치환 | 최신 검증/검사 보존 실패로 별도 표시; 자동으로 기능 성공으로 처리하지 않음 |

각 ID는 고정된 세부 사례를 가진다. 실행 전 그 목록과 예정 분모까지 작성해야 한다. 표의 묶음을 곧바로 '테스트 10개'로 세거나, 실행된 사례만 분모에 넣지 않는다. UI 검사는 사용자 계약을 기준으로 하며 특정 hook·CSS·파일명·암묵적 status 역할을 요구하지 않는다.

현재 자동 사례는 보호 파일 9 + 업무 함수 33 + 실제 POST 함수 60 + 브라우저 8 = 110개다. 실행마다 `case-index.json`에 전체 ID·분류·예정 분모를 보존한다. POST 직접 호출은 HTTP 서버·Next 런타임 E2E와 구별한다. 브라우저가 없으면 8개를 미실행으로 남긴다. H10 중 마지막 수정 이후 검증 여부는 별도 실행 로그 판정이 필요하며 파일 해시 9개로 대체하지 않는다. 참조 컨트롤러 검사 6개와 변경 실험 4개는 교정 근거이며 모든 구현에 같은 내부 컨트롤러를 강제하는 채점 계약이 아니다.

## 설계 정답은 구조 하나가 아니라 만족해야 할 성질

허용 예 A: 순수 quote 함수 + 서버 route에서 상품 조회와 함수 호출 + UI의 좁은 원격 견적 상태. 허용 예 B: 순수 pricing 모듈 + 외부 함수를 인자로 받는 작은 주문 유스케이스 + HTTP adapter + UI hook. 두 예 모두 Q1~Q10과 필수 계약을 만족하면 동등하게 정답이다. B처럼 파일/계층이 많다고 추가 점수를 주지 않는다. A처럼 함수 주입에 인터페이스 선언이 없다고 감점하지 않는다.

| 기준 | 정상 근거 | 0점이 되는 구체적 반례 |
| --- | --- | --- |
| Q1 | 순수 업무 진입점에 다른 catalog 입력을 넣어 같은 규칙 실행 | React 렌더·Next Request·전역 fetch·고정 A/B 가격 없이는 계산 불가 |
| Q2 | quote와 order의 실제 경로가 동일 가격 판단을 호출 | 두 endpoint나 UI에서 할인율·배송 기준을 따로 결정; 단순 입력 가드는 감점 아님 |
| Q3 | 업무 판단은 인자/작은 계약에 의존, route/adapter가 연결 | domain이 구체 HTTP adapter 또는 React/Next를 import; 이름만 domain인 폴더로는 통과 불가 |
| Q4 | UI는 표시/입력, 요청 조정은 최신성/잠금, 업무 코드는 정책 판단 | JSX 이벤트 핸들러가 할인/배송/서버 재고의 최종 정책 결정 |
| Q5 | 입력은 폼, 원격 견적은 입력 식별자와 수명 관리, 합계는 견적에서 표시 | 같은 합계를 여러 state/effect로 동기화하거나 단독 폼 때문에 전역 store 도입 |
| Q6 | 오래된 resolve/reject 양쪽 처리, 모든 종료 경로에서 재시도 가능 | 오래된 성공만 무시하고 오래된 catch는 오류를 덮어씀; 실패 후 잠금 유지 |
| Q7 | 단위/의미가 있는 이름과 추적 가능한 분기; 근거로 코드 위치 제시 | a/b/data가 서로 다른 금액 의미를 감춤, 중첩 삼항/간접 호출이 업무 결정을 숨김; 취향 차이는 U |
| Q8 | 작은 helper·hook·adapter가 현재 중복/경계를 해결 | 빈 계층·사용하지 않는 factory·DI container·미요구 다중 통화/결제 provider 추가; 클래스라는 이유만으로 감점하지 않음 |
| Q9 | 실제 함수의 정상/경계/실패·실제 route·원격 응답 순서 검증 | 구현 함수 자체를 mock해 성공 횟수만 검사; assertion 삭제로 통과; 테스트 수만 많음 |
| Q10 | 정책 변형은 한 소유 위치, 외부 조회 교체는 외부 연결부로 한정 | 배송 기준 변경에 UI와 두 route의 업무 분기를 각각 고쳐야 하거나 조회 교체에 계산 재작성 필요 |

Q7/Q8 같은 의미 판단은 자동 정규식 점수로 만들지 않는다. 규칙에 걸린 코드와 현재 요구에서 왜 문제가 되는지 기록한다. 실제 문제를 제시할 수 없는 개인적인 명명/폴더 취향은 감점 근거가 아니다.

## 변경 영향 확인

원본 결과의 별도 사본에서 배송 무료 기준을 50,000원에서 60,000원으로 바꿔 정답 계산을 다시 확인한다. 실제 정책 소유 위치를 수정하며 기존에 설정 주입 기능을 미리 만들어 둘 것을 요구하지 않는다. 상품 조회는 같은 반환 계약의 메모리 함수와 지연/실패하는 함수로 대체해 UI·도메인 재작성 여부를 확인한다.

평가자가 수행한 최소 변경 diff와 건드린 책임 영역을 보존한다. 별도 모델이 변경하면 그 토큰은 후속 변경 실험으로 분리한다. Q10의 평가자 검증 비용을 구현 모델의 A 비용에 몰래 더하거나 빼지 않는다. 변경 라인 수가 적다는 사실만으로 좋은 설계라고 판정하지 않는다.

## 채점기를 먼저 검증할 정상/결함 예제

두 정상 구조가 모두 통과해야 한다. 다음 변형을 한 번에 하나씩 주입해 어느 세부 사례와 점수 항목이 반응해야 하는지 고정한다. 결함 없는 원본도 매번 확인해 오탐을 기록한다.

| 변형 | 기대 탐지 |
| --- | --- |
| 할인 전 금액으로 무료 배송 판정 / >= 대신 > 사용 | H1 배송 경계 |
| 10% 할인 반올림으로 변경 | H1 12345원 데이터 |
| 전달받은 total을 서버에서 그대로 사용 | H5 |
| quote와 order 계산을 분리 복사하고 한쪽 배송 기준만 변경 | Q2/Q10 및 두 경로의 H1 불일치 |
| 순수 계산에 UI/구체 네트워크 의존을 추가 | Q1/Q3; 단순 import 문자열뿐 아니라 실제 실행·의존 그래프 확인 |
| 오래된 응답의 catch만 최신성 검사 제거 | H6/Q6 |
| 견적 대기 중 이전 견적으로 주문 허용 | H7/Q5 |
| 주문 실패에서 잠금 해제 제거 | H8/Q6 |
| 같은 합계를 effect로 복제 / 쓰이지 않는 범용 factory 추가 | Q5 또는 Q8, 기능 통과와 구분 |
| 실제 테스트를 항상 성공하는 assertion으로 변경 | H10/Q9 |

정상 두 구현과 NextResponse/별칭 정상 변형의 전체 브라우저 검사를 확인했다. 결함 10종의 자동 탐지와 비동기 결함 4종의 예정 브라우저 실패를 확인했다. 구체 I/O import와 미사용 factory는 독립 의미 리뷰에서 탐지했으며, 정상 두 구조의 Q10 정책/I/O 변경도 독립 재실행했다. 본 비교가 시작된 뒤 예상과 다른 합리적인 설계를 보았다고 새 감점 기준을 만들지 않는다. 기준이 부족한 경우 U와 이유를 기록하고 다음 버전에 반영한다.
