**1. 정책을 자동화하는 도구가 모델에게 내부 표현을 직접 조립하게 한다.**

FS 18회 중 **16회에서 총 28번**, 정책 검사가 `Missing or changed required script`로 실행되지 않았다. 실제 package 스크립트 변경이 아니라 정책 필드의 의미를 잘못 작성한 사례다. A Luna 14회는 `script: lint, command: npm run lint`를 저장했다. FS가 비교하는 값은 package.json의 본문 `eslint app src`다. B Luna 28회에서는 수정하면서 script 필드에 본문을 넣어 다시 실패했다.

[policyFailures](../../../../src/application/policy.ts)는 `scripts[check.script] !== check.command`를 검사한다. 그러나 같은 시스템의 capability와 검사 결과에는 `command: npm run lint`가 등장한다. 스키마의 두 필드는 설명 없는 문자열이다. [approveRevision](../../../../src/application/workflow-store.ts)은 보호 구조를 확인하지만 실제 script 본문 일치는 실행 단계에서 확인한다. 잘못된 정책이 승인된 뒤 드러나며, 정책 재저장으로 승인·revision이 바뀌어 근거 연결까지 복구해야 한다.

공개 R1~R9를 그대로 rule ID로 쓰면 소문자 전용 정규식에 걸린다. save_revision 실패 16건에는 이 문제와 version 누락·`test:unit` 같은 check ID 오류가 포함된다. `stage`와 `capabilities`, `stage:issue`와 `required:true`처럼 자연스럽게 함께 넣은 옵션도 실행 때 거부된다.

| MCP 실패 종류 | 건수 |
| --- | ---: |
| save_execution: 계약·근거 ID·최신성·attempt 연결 | 24 |
| run_project_checks: 옵션 충돌·승인 정책 없음 | 21 |
| save_revision: ID·필수 필드 등 입력 검증 | 16 |
| begin_work_attempt: 현재 승인 execution 연결 | 12 |
| get_change_context: Git 권한 오류 | 8 |
| save_semantic_review: findings·규칙·상태 계약 | 8 |
| get_revision / approve_revision | 2 / 1 |
| 합계 | **92/551 호출, 16.7%** |

92건이 전부 FS의 잘못된 거부는 아니다. 오래된 근거·틀린 ID를 막는 검사는 필요한 보호다. 문제는 올바른 ID·명령·상태를 시스템이 이미 알면서도 모델이 반복해서 복사·연결해야 한다는 점이다. policy/not-run 28회는 이 92건과 별도이며 제품 테스트 실패도 아니다.

수정 방향: script ID에서 실제 본문을 도구가 결정하고 정책 저장 전에 검증한다. 표시용 규칙 ID와 내부 ID를 명확히 매핑하고 옵션의 상호 배타성을 입력 단계에 드러낸다. baseline의 plan 범위 불일치로 발생하는 ENOENT와 reviewId/저장 record ID 혼동도 줄인다. 해시·승인·보호 검사를 없애는 방향은 아니다.

**2. 맥락을 줄이는 기능이 반복해서 큰 상태를 반환한다.**

MCP 전체 반환 텍스트 3,486,996자 중 get_work_context 46회와 get_workflow_context 50회가 **2,160,790자, 약 62%**를 차지했다. A Astra 02회의 get_work_context는 19,134→40,540→41,842자로 증가했다. 학습 지식을 제외한 A에서도 발생한다.

[taskContext](../../../../src/application/task-context.ts)는 profile·규칙·workflow·plans·프로젝트 문서를 함께 반환한다. [buildWorkContext](../../../../src/application/context/build-work-context.ts)는 mode에 따른 반환 필드 축소 없이 규칙·지식을 전달하며, 스킬은 계획·구현·검증 단계에서 재조회를 요구한다. save_revision과 approve_revision도 큰 revision 객체를 반환한다. 검사 성공 stdout은 이미 [summarizeChecks](../../../../src/application/run-capabilities.ts)에서 줄이고 있어 테스트 로그 축약만으로 해결되지 않는다.

수정 방향: 준비에는 필요한 규칙·계약, 구현에는 선택한 issue와 변경 사실, 검증에는 누락 근거·실패를 기본 반환한다. 저장 응답은 ID·hash·상태·변경 요약으로 제한하고 원문은 선택 조회한다. 단계별 실측 토큰은 없어 이 부분이 전체 토큰 증가의 몇 %를 만들었는지는 단정하지 않는다.

**3. 지식이 있어도 관련 지식을 고르지 못한다.**

B FS 9회 모두 지식 요약을 받았지만 명시적 검색·원문 조회는 관측되지 않았다. 실제 실패는 입력/응답 수명과 동기 중복 제출이었다. 반면 CSS 캐스케이드는 7/9회, 웹 앱 통합·DOM 자료는 각각 5/9회 노출됐다. React state 모델과 React 디버깅 사례는 각각 1/9회, derived-state/effects는 0/9회였다. 노출은 적용의 증거가 아니며 원문을 읽지 않았다는 사실만으로 요약도 무효라고 단정하지 않는다.

실제 B Sol 21회의 요청은 `Implement approved checkout contract in TASK.md`다. [searchReferenceIndex](../../../../src/application/knowledge/reference-index.ts)는 단어의 **부분 문자열 일치 수**를 세고 동점이면 ID 순으로 5개를 고른다. TASK.md 내용으로 검색어를 확장하지 않는다. conditions/exclusions도 이 함수에서 적용성 판단에 사용하지 않는다.

같은 인덱스·실제 검색 함수로 재현했다.

| 반환 항목 | 매칭된 단어 |
| --- | --- |
| code-quality-context-and-contracts | contract, in |
| accessibility-modal-focus | in |
| accessibility-static-validation | in |
| bundling-output-and-optimization | in |
| chromium-rendering-pipeline | in |

**상위 5개 중 4개가 전치사 `in` 하나 때문에 선택됐다.** React/stale/response/effect/state를 포함한 요청으로 재조회하면 state 모델·React 디버깅·derived effects가 상위에 등장했다. 이 재조회는 검색 진단이지 구현 품질 개선 실측은 아니다. 원 요청·매칭 단어·재현 결과는 분석 JSON의 retrievalReplay에 보존했다.

수정 방향: 읽은 요구사항의 프레임워크·상태 전이·오류 조건을 검색어에 포함하고 일반 단어/부분 문자열 우연 일치를 줄인다. 관련성 미달이면 억지로 5개를 채우지 않는다. 선택한 지식을 실제 설계 판단과 반례 검사에 연결한다. 우선 기존 69개 참조에서 관련 문서를 찾는지 확인해야 하며, 벡터 DB부터 추가할 근거는 없다.

**4. FS 완료 기록은 제품 계약 충족의 보증이 아니다.**

A Sol 04회와 B Luna 23회는 save_execution의 complete가 받아들여졌지만 제품 조건에서 실패했다. 04회는 주문 중 접근 이름 변경, 23회는 동등 입력의 견적 정체와 동기 이중 제출이다. B Luna 28회는 제품 조건을 통과했으나 실제 I/O 교체 검증 없이 Q10 만점을 선언해 전체 적격에서 제외됐다.

[saveReview/verifyReviews](../../../../src/application/workflow-store.ts)는 실제 파일·규칙·source hash·passed 상태를 확인한다. 모델이 작성한 evidence/conclusion 문장이 참인지는 독립적으로 증명하지 않는다. 현재 구조는 **검사 수행과 리뷰 기록**을 강제하지만 그 검사가 핵심 반례를 잡는지는 별개다.

예를 들어 B를 `0→빈 문자열/00→0`으로 편집하면 숫자로 정규화한 값은 같다. 핸들러는 요청 세대와 quote를 무효화하지만 effect 의존성은 바뀌지 않아 새 요청이 시작되지 않는 결함이 있었다. setState로만 잠그면 다음 렌더 전 두 제출이 모두 이전 false를 읽는 결함도 있었다. 독립 리뷰의 실제 JSX 전이 probe로 확인한 결과이며 모든 브라우저 스케줄에서 재현했다는 뜻은 아니다.

수정 방향: 해당 비동기 변경에 오래된 실패·동등 입력·같은 task의 이중 제출·재시도 반례를 연결한다. 모든 작업에 추가 모델 리뷰를 강제하기보다 위험이 있는 변경에 독립 검사를 선택한다. 완료 표시는 자동 검사 범위와 모델 의미 판단을 구분하고, 실행하지 않은 평가 항목의 만점 선언을 근거로 쓰지 않는다.

**5. 실행 환경 문제도 섞여 있으므로 모든 실패를 FS 탓으로 설명하면 안 된다.**

get_change_context 실패 8건은 차단된 사용자 Git 설정 파일 때문이다. [projectSnapshot](../../../../src/application/project-snapshot.ts)은 HEAD 조회 실패를 전부 null로 바꿔 권한 오류도 unversioned로 보고할 수 있다. 실제 로그에 commit:null·files:[]가 반환됐다. 같은 격리 환경이어도 FS가 Git 맥락 도구를 더 쓰므로 부담이 대칭적이지 않다.

B Sol 26회는 제품 미완료·시간 초과였지만 MCP는 5회, 호출 실패는 0건이다. [stderr](results/model-runs-2026-10-01T090255/26/model/stderr.log)에 native apply_patch helper의 권한 실패가 있다. 이후 미완료 시간 전체를 원인별로 분해할 수 없다. 이 회차의 0점을 FS 설계가 제품 코드를 망쳤다는 증거로 해석하면 과장이다. 사후에 회차를 제외해 성능을 높이지도 않는다.

수정 방향: Git 정보 접근 불가와 실제 미버전 관리를 구분한다. 허용된 환경의 Git·편집 경로를 사전 확인하고 두 조건에 동일하게 적용한다. 기존 결과를 유지하며 다음 실험에서 환경 비용을 별도 관측한다. 900초 이후 성공했을 것이라는 추정은 결과가 아니다.

**6. 평가의 한계는 현재 문제를 없애주지 않는다.**

- 강한 모델은 공개 설계 원칙만으로 만점에 도달했다. 이 비교는 기준이 제공된 AI에 대한 FS의 추가 효과다. 일반 조건의 요구를 낮춰 차이를 만들어서는 안 된다.
- 20개 이진 설계 항목은 만점이 많다. B Luna 일반 3회는 Q100이지만 필수 제품 조건에서 탈락했다. 기존 점수를 사후 변경하지 말고 설계 점수와 실제 결함·변경 성공을 계속 함께 본다.
- 첫 구현만 측정했으므로 기록 재사용 효과는 미검증이다. 초기 비용과 도구 오류는 이미 관측된 문제이며 재사용 가능성으로 정당화할 수 없다.
- A/B는 문서 의무와 지식 범위 등 여러 조건이 달라 지식만의 효과가 아니다. 지식 효과는 동일한 FS 절차에서 지식 제공 여부만 바꾸는 별도 비교가 필요하다.
- 단일 과제·조건별 n=3이며 시간 초과 7회는 사용량도 누락됐다. 향후 제공되는 누적 usage 이벤트가 있는지 확인해 중단 전 사용량을 보존한다. 문자 수로 누락값을 채우지 않는다.

**개선 순서는 정책 입력·참조 연결 → 반환 맥락 축소 → 관련 지식 선택·반례 연결이다.** 먼저 현재 로그로 재현 가능한 호출 계약·검색 회귀 검사를 만든다. 소규모 짝 비교로 오류 감소·응답량·완료율을 확인한 뒤 전체 비교를 반복한다. checkout의 숫자·ID에만 맞춘 수정은 피하고 다른 요청과 기존 프로젝트 변경에서도 확인한다.

기록·출처·검증 근거 보존 기능이 무가치하다는 결과는 아니다. 다만 **토큰 절감과 일관된 품질 향상 주장은 이 결과로 지지되지 않는다.** 다음 지식 추가 전에 이미 가진 규칙·지식이 오류 없이 선택·적용·검증되게 만드는 것이 우선이다. 이 문서는 원인 분석과 개선 제안이며 제품 코드 수정이나 개선 효과 측정 결과는 아니다.

## 추가 원인 재현과 구체적인 수정 계획

앞선 집계만으로 수정 효과까지 주장할 수는 없다. 그래서 실제 FS 함수에 독립 입력을 주는 [실행 가능한 진단](probe-contracts.mjs)을 추가했다. 분석 당시 저장소 루트에서 빌드된 FS를 대상으로 `node test/evals/fs-comparison/v2/probe-contracts.mjs`를 실행했다. 이후 수정판에서는 원 진단의 소스 해시가 달라 실행을 중단한다. 현재 회귀 검사는 `npm run check`로 실행한다. 임시 디렉터리만 사용하고 제거하며 모델 호출은 없다. [재현 결과](results/contract-diagnosis-2026-10-01.json)는 본 실험 점수와 구분한다.

| 재현 | 실제 관측 | 확인한 설계 문제 |
| --- | --- | --- |
| package 본문과 다른 `command`로 정책 작성 | 승인 성공 후 검사 `not-run` | 도구가 알 수 있는 잘못된 설정을 승인 이전에 걸러주지 않음 |
| delivery로 전체 정책 검사 실행 | 전부 passed, `full:false`, 완료 저장은 성공 | 모델이 보는 상태 이름과 완료 가능 여부가 일치하지 않음 |
| 공통 mandatory 규칙을 resolve한 ID를 정책 스키마에 전달 | 9개 모두 ID 검증 실패 | 읽기 우선순위용 규칙과 실행 정책이 같은 규칙 표현을 공유하지 않음 |
| pending 때도 제출 가능한 결함과 초기 제출만 보는 보호된 테스트 | 테스트 passed, 정책 상태 `verified`, pending 반례는 위반 | 근거의 최신성·무결성 확인이 행동 보장의 충분성 확인을 대신하지 못함 |

마지막 예제는 기록을 조작하거나 assertion을 삭제하지 않았다. 처음부터 pending 반례를 빠뜨린 테스트였다. 이는 보호 검사의 무력화나 새로운 보안 취약점이라는 뜻이 아니라, 문서에 명시한 “선언된 정책 범위의 verified”가 제품 정확성 보증으로 확대될 수 없음을 실행으로 확인한 것이다. mandatory ID의 차이도 본 실험에서 규칙이 누락됐다는 직접 증거는 아니다. 모델이 규칙 선택·ID 변환·정책 재서술을 해야 하는 경계를 확인한 것이다.

검사 재실행도 원자료에서 더 좁혀 집계했다. MCP가 실제 실행한 script 결과 251건 중 **75건은 같은 회차의 sourceHash·revisionHash·script·command가 이전 실행과 같았다.** 해당 회차는 02·04·11·18·19·21·31·33·35의 9개다. 이 중 **65건은 attempt도 같고 이전/현재 모두 stable·passed**였다. 쉘로 직접 실행한 검사는 포함하지 않았다. 환경 동등성까지 입증된 것은 아니므로 75건 전부를 무가치하거나 그대로 절약 가능하다고 계산하지 않는다.

B Astra 19회는 item_52/53/55에서 delivery → delivery+required → attempt 없는 delivery로 반복한 뒤, 완료 시 attempt 불일치와 부재로 두 번 거부됐다. B Sol 35회도 issue → delivery → required로 같은 소스의 같은 검사를 반복했다. `full:false`의 정확한 해석과 어떤 record가 완료에 유효한지 도구가 알려주지 않는 문제가 이 흐름과 함께 관측됐다. 이것만으로 모델 내부 의도의 전부를 확정하지는 않는다.

**근본 원인은 판단과 기계적 관리의 책임 배치다.** FS가 자동으로 처리할 수 있는 명령·ID·근거 연결은 모델이 조립하고, 실제 반례가 충분한지처럼 판단이 필요한 부분은 모델의 서술과 선택에 의존한다. 규칙의 priority도 현재는 읽기 순서이며 충돌 해결이나 자동 정책 등록이 아니다. 따라서 “규칙이 먼저 주어지니 더 적은 작업으로 더 좋은 결과가 나온다”는 연결은 구현만으로 성립하지 않는다.

이전에 스킬·문서·기록·검증 절차를 늘리는 방향을 제안하면서 각 추가 단계가 기존 작업을 얼마나 대체하는지 먼저 측정하지 못했다. 저장·해시·상태 전이의 정확성을 확인한 테스트를 실제 모델 사용성과 품질 효과의 근거로 확대해서는 안 됐다. 다음 수정은 같은 방식의 지침 추가로 끝내지 않는다.

**기존 테스트가 이 문제를 놓친 이유도 확인했다.**

- [policy-workflow.test.ts](../../../../test/policy-workflow.test.ts)는 사람이 올바른 ID·스크립트 본문·연결된 record를 조립한 fixture로 상태 엔진을 검사한다. 실제 공개 도구 응답을 받은 모델이 정책을 만드는 경계는 이 검사에 없다.
- [reliability-eval.test.ts](../../../../test/reliability-eval.test.ts)는 알려진 결함을 잡는 oracle를 사전에 준비한다. 그 oracle를 보존·실행하고 오래된 근거를 거부하는 능력은 검증하지만, 새 요청에서 모델이 충분한 oracle를 만드는 능력은 검증하지 않는다.
- [knowledge-index.test.ts](../../../../test/knowledge-index.test.ts)는 증상 키워드가 담긴 질의의 정답 포함 여부를 주로 확인한다. 게시된 인덱스 평가의 precision은 diagnostic으로 출력하지만 임계치를 assertion하지 않는다. 실제 짧은 작업 요청의 일반 단어로 관련 없는 결과가 섞이는 비용을 막는 기준이 부족했다. 합성 소형 인덱스에는 무관 질의/반환 거부 테스트가 있으므로 “검색 정확도 테스트가 전혀 없다”고 말하는 것도 틀리다.

| 순서 | 변경할 책임과 위치 | 기존 기능을 보존하며 확인할 기준 |
| --- | --- | --- |
| 1. 정책 입력 | policy/mcp/workflow-store에서 script ID를 선택하면 현재 본문·보호 해시를 결정적으로 구성. 표시 ID와 저장 ID의 명시적 매핑. 승인 전 실제 설정 일치 확인 | 이번 잘못된 명령 입력을 늦은 실행 실패로 넘기지 않음. 실제 스크립트 변경·보호 파일 변경·잘못된 승인 hash는 계속 거부. 모델이 명령 본문을 재작성할 필요 없음 |
| 2. 실행·완료 연결 | 저장된 issue 계약을 모델이 전체 재전송하지 않게 진행 갱신을 좁힘. 선택한 plan/step의 유효 attempt·check·review 연결과 누락 이유를 도구가 반환 | plan 간 근거 혼용·오래된 결과·시도 제한 우회는 계속 거부. 전체 검사 통과 시 완료 가능한 상태/누락 항목을 명시하고, 오해를 부르는 legacy full 필드와 정책 커버리지를 분리 |
| 3. 반복 작업 제거 | run-capabilities와 task-context에서 이미 보유한 근거·계약을 재사용. 동일 실행 경계에서 issue 검사로 delivery 전체 요구가 충족되면 다시 실행하지 않고 연결 | 소스·검사·정책·의존성·관련 환경이 바뀌면 재검증. 동일성 확인 불가도 재검증. 예전 결과를 무조건 캐시하지 않음. 맥락 반환은 현재 단계의 변경·실패·필요 근거 중심으로 측정 |
| 4. 지식 적용 | 실제 요구사항·영향 코드에서 위험과 기술을 추출해 검색. 영어 일반 단어 우연 일치를 줄이고 근거 약한 결과는 비움. 관련 참조를 결정/검사에 연결 | 현재 실패 질의뿐 아니라 미사용 한국어·영어 요청, 무관 요청, 다른 기술의 유사 요청으로 precision·recall·abstention 평가. 읽었다는 기록 자체는 효과로 점수화하지 않음 |
| 5. 행동 보장 | 비동기 변경에서 실제 호출 경로의 동등 입력·오래된 실패·동기 이중 제출·실패 복구를 선택적으로 검사. 중요 계약의 정상/결함 예제로 테스트 실효성 확인 | 정상 대안은 통과, 해당 결함은 지정한 assertion에서 실패. 자체 `passed` 리뷰만으로 이 보장을 충족했다고 표시하지 않음. 모든 설계 원칙의 자동 판정이나 결함 0건은 약속하지 않음 |

모든 기능을 새 프레임워크로 다시 만들 필요는 없다. 기존 도구 안에서 기계적 데이터 조립과 판단의 경계를 옮기고, 기존 원문·해시·기록의 저장은 유지하면서 모델이 처리하는 양을 줄이는 수정이다. 지식을 무조건 규칙으로 승격하거나, 승인·접근 제약을 완화하거나, 매 단계 추가 모델을 붙이는 접근은 이 근거에서 도출되지 않는다.

**효과 확인은 각 변경을 분리해서 해야 한다.**

1. 이번 독립 재현을 회귀 검사로 바꾸고 일반적인 다른 ID·script·plan에서도 검증한다. 개선 전의 실패와 개선 후의 올바른 거부/연결을 둘 다 남긴다.
2. 규칙·지식·모델·과제는 고정하고 인터페이스/반환량 수정만 넣은 소규모 짝 비교로 도구 실패, 중복 검사, 적격 완료, 사용량을 확인한다. 소규모 결과는 진단이며 우월성의 최종 근거가 아니다.
3. 절차가 안정된 동일 FS에서 관련 지식 제공 여부만 바꿔 품질 효과를 분리한다. 검색 변경과 지식 내용 변경을 동시에 섞지 않는다. 기존 checkout은 회귀용이고 추가 과제는 채점 전에 고정한 별도 검증용으로 둔다.
4. 효과가 확인된 버전만 일반 AI와 전체 비교한다. 토큰 절감 주장은 같은 완료 기준·품질을 유지하며 실제 사용량이 줄어야 인정한다. 품질 향상 주장은 설계 총점보다 필수 결함·변경 성공·적격 완료와 추가 비용을 함께 보고 판단한다.

따라서 지금 약속할 수 있는 것은 “수정하면 좋아진다”가 아니라 **현재 재현되는 인터페이스 결함과 검증 공백을 줄이고, 그 결과가 모델 성능으로 이어지는지 분리해 확인한다**는 절차다. 효과가 없으면 해당 절차·지식 주입 범위를 줄이거나 제거해야 한다. 본 추가 분석에서 제품 코드는 수정하지 않았다.
