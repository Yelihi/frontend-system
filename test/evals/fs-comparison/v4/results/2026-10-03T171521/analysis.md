# v4 실제 구현 비교 분석

모델 `gpt-6-sol`, 동일 계획, 세 사례 각 1회. 사전 격리 검사와 판정기 교정을 통과했다. 실제 모델 호출은 9회다. 일반 AI는 준비·구현 각 1회, FS는 준비 단계에서 중단되어 각 1회만 호출됐다. `summary.status=completed`는 실행기가 모든 조건을 처리했다는 뜻이며 모든 조건의 성공을 뜻하지 않는다.

| 사례 | 일반 AI 구현 | 일반 AI 준비+구현 시간 | 일반 AI 총 토큰 | FS |
| --- | --- | ---: | ---: | --- |
| duplicated | 첫 구현 통과 | 187.455초 | 292,447 | 준비 300.025초 시간 초과 |
| existing-good | 첫 구현 통과, client 보존 | 123.905초 | 187,881 | 준비 300.009초 시간 초과 |
| different-policies | 첫 구현 통과 | 245.482초 | 395,202 | 준비 300.029초 시간 초과 |

일반 AI 합계는 875,530토큰이며 입력 857,749(캐시 입력 777,984 포함), 출력 17,781이다. 입력은 호출별 누적 처리량이다. 이를 전부 새 입력이나 동일 단가의 비용으로 해석하면 안 된다. FS는 완료 usage 이벤트가 없으므로 사용량을 알 수 없다. 0으로 대체하거나 일반 AI 대비 비용 비율을 계산하지 않는다.

## 확인된 실패 지점

이번에는 FS 세 조건 모두 `get_work_context` 라우팅이 실행되었다. 과거처럼 라우팅 자체를 생략한 결과는 아니다. 그러나 구현 단계에 들어가지 못했다. 질문 응답 대기가 아니라 준비 턴을 실행하다 시간 제한으로 종료됐다.

| 사례 | 완료된 MCP 호출(실패 포함) | 실패 응답 | 종료 전 상태 |
| --- | ---: | ---: | --- |
| duplicated | 29 | 8 | 프로젝트 설명 저장, 라우팅 재실행, 검증 도구 조사; 계획 저장 없음 |
| existing-good | 24 | 4 | 계획 저장 4회 실패 후 라우팅 재실행 |
| different-policies | 32 | 11 | 계획 저장·승인 성공, 준비 턴 종료 및 구현 진입 없음 |

1. **도구 입력을 맞추는 비용이 크다.** `read_project_source.limit` 초과 5회, 필수 필드 누락, 정책 enum 오류, 근거 타입 오류 등이 반복됐다. 특히 `policy.rules[].evidence`는 문자열 배열이고 `evidence.decisions[].evidence`는 코드 인용 객체 배열이어서, 한쪽을 고친 후 다른 쪽에서 다시 실패했다. 일부 호출은 빈 객체로 스키마를 탐색했다. 테스트에서 유효한 객체를 넣었을 때 통과한 것과 모델이 이 인터페이스를 안정적으로 사용할 수 있는지는 다른 문제다.
2. **맥락 응답과 판단 대상이 넓다.** 성공한 `get_work_context` 응답 하나가 대략 4.8만~6.8만 문자였고, 초기 후보는 사례별 8~15개였다. 요청 경계 외 접근성·렌더링 등 후보도 포함됐다. 일부는 관련될 수 있으나 모두 판단해야 하는 현재 방식은 준비 작업을 늘린다. `get_work_context` 외에 별도 discovery·inspection도 호출되어 중복 처리가 관찰됐다. 문자 수는 토큰 수가 아니다.
3. **근거 연결 오류의 안내가 충분하지 않다.** existing-good은 좁힌 라우팅 범위에서 빠진 `CONTRACT.md`를 결정 근거로 계속 인용했다. 서버는 `Decision must cite routed source`만 반환했고, 모델은 어떤 경로가 빠졌는지 해결하지 못한 채 재시도했다. 검증 원칙을 없애기보다 누락 경로·허용 범위와 재사용 가능한 인용을 명확히 반환할 필요가 있다.
4. **경로가 연결됐어도 전달 결과는 실패했다.** different-policies는 `request-policy-boundaries`를 apply로 기록하고 결정·계획 승인까지 마쳤다. 하지만 완료된 준비 턴이 없어 구현 호출은 시작되지 않았다. 현재 실험의 300초 예산에서 FS의 작업 전달 성공률은 0/3이다.

이 관찰들은 시간 소모를 설명하는 구체적 마찰이다. 로그만으로 각 오류·응답이 몇 초를 차지했는지, 시간 초과의 유일한 원인인지까지 단정하지 않는다.

## 판단과 다음 순서

현재 버전은 이 파일럿에서 실용적 이득을 보여주지 못했고, 작업 완료 측면에서는 일반 AI보다 불리했다. FS 구현물이 없으므로 코드 품질이 같거나 더 나쁘다는 직접 비교는 할 수 없다. 일반 AI도 같은 지식과 확정 계획을 제공받았으므로 지식이 없는 AI와의 비교가 아니다.

다음 계획 실험을 바로 실행하기 전에 입력 계약의 혼동·응답 중복·경로 없는 오류를 줄이는 것이 우선이다. 코드 인용·승인·검증 조건은 유지하되 모델이 복사해야 하는 해시와 반복 구조를 줄이고, 작은 유효 입력 예시와 수정 가능한 오류 정보를 제공한다. 시간 제한만 늘려 성공을 만들면 추가 비용이 가려진다. 동일한 300초 조건으로 다시 측정하고, 제한을 바꾼 진단 실험은 별도로 기록한다.

이 분석에서는 제품 코드나 실행기, 기존 원시 결과를 변경하지 않았다. [집계 자료](analysis.json), [원본 요약](summary.json), 각 조건의 `prepare/0/model/events.jsonl`에 근거가 있다. 질문 품질과 장기 유지보수 효과는 이번 실험에서 측정하지 않았다.
