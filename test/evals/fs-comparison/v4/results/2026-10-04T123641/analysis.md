`compliance`, `duplicated` 한 사례를 `gpt-6-sol`로 조건별 1회 실행했다. 일반 AI와 FS는 각각 새 세션에서 시작하고 준비→작업만 같은 세션을 사용했다. 전체 모델 호출은 4회이며 시간 초과와 추가 수정 호출은 없다. 배포 파일의 매니페스트 해시가 분석 시점의 파일과 일치한다.

**두 조건 모두 최초 구현에서 계획 준수 검사 11/11을 통과했다. 이번 사례에서는 FS의 규정 위반 감소나 재작업 감소가 관찰되지 않았으며 시간·토큰은 더 많았다.** 이는 검사한 명시적 계약에 대한 결과이며 전체 설계 품질의 동등성 증명은 아니다.

## 실제로 확인한 준수

기존 요청 동작 검사 6개에 입력의 얕은 복사/참조 보존, 허용 의존성, 공개 API 범위, 사용자 선택 오류 정책, 변경 파일 범위 검사 5개를 추가했다. 두 조건 모두 첫 구현에서 모두 통과했다. 질문 절차는 이 11개와 별도로 관찰됐다.

양쪽 모두 준비 단계에서 “401의 onUnauthorized 콜백이 throw하면 원래 오류를 전달할지 unauthorized로 대체할지”를 질문했다. 같은 모의 사용자 답변을 받은 뒤 같은 오류 객체를 전달하도록 구현했다. 코드의 실제 인용·질문 내용도 이번 분석에서 읽어 확인했지만, 이것을 독립적 블라인드 의미 평가 점수로 추가하지 않았다.

FS는 `request-policy-boundaries`를 결정에 연결하고, USER_DECISIONS.md 인용으로 Q1을 resolved 처리한 뒤 계획 저장·승인, 작업 시도, 검사·의미 검토·완료 기록을 남겼다. FS 절차가 생략된 결과는 아니다. `semanticReview: unverified`는 독립 의미 평가가 없다는 뜻이며 그대로 유지한다.

## 남은 준비 비용과 오류

FS는 준비 MCP 17회, 구현 MCP 13회로 총 30회를 수행했다. shell 호출은 일반 AI 19회, FS 15회였다. FS의 추가 시간 약 290초 중 약 202초는 준비 단계 차이다. 이는 시간 차이가 어디에 집중되는지 보여주며 특정 도구에 비용을 인과적으로 배분한 측정은 아니다.

준비 단계의 save_revision이 두 번 실패했다. 미결정 선택의 `selected`를 처음에는 생략하고 다음에는 빈 문자열로 제출했다. 현재 입력 스키마는 미결정에 `null`을 요구한다. 준비 단계에는 초안 저장이 성공하지 않았고, 질문·답변 이후 작업 단계에서 resolved 결정을 포함해 저장에 성공했다. 다음 개선 대상으로 미결정 입력의 표현과 오류 안내를 검토할 근거가 있다. 이미 결정된 선택을 서버가 임의로 채우는 방식으로 해결하면 안 된다.

요약 응답 개선은 실제 사용됐다. 성공한 save_revision과 approve_revision 응답은 각각 636/635자였으며 전체 원본 근거를 반복 반환하지 않았다. 그러나 이것만으로 전체 비용 문제가 해결되지는 않았다. 입력·출력 모두 준비와 구현 대화 전반에서 누적된다.

## 이전 실행과의 관계

이전 implementation의 duplicated FS는 1,958,267토큰·407.317초였고 이번은 1,433,357토큰·446.466초다. 관측값은 토큰 약 26.8% 감소, 시간 약 9.6% 증가다. **계획·질문·검사 조건과 모델의 진행 경로가 달라졌으므로 최적화의 순수 효과로 계산하지 않는다.** 같은 조건에서 수정 전후를 반복 비교한 성능 실험이 아니다.

이전 전체 세 사례 합계와 이번 한 사례를 직접 비교하지 않는다. 과거 코드를 새 금지 규칙으로 다시 채점하지 않았다.

## 해석 범위

- 이번은 duplicated 한 쌍이다. existing-good과 different-policies는 이 실행에 없다.
- 질문할 주제를 두 조건에 명시했다. 확인이 필요한 지점을 스스로 발견하는 능력은 측정하지 않았다.
- 규정도 명시적으로 제공했다. 이 정도 범위의 구체적인 계획은 일반 AI도 추가 FS 절차 없이 준수했다는 관찰이다.
- 단계별 최종 파일 검사이므로 호출 중 위반 후 되돌린 수정은 검출하지 못한다. 모든 JavaScript 우회와 전체 아키텍처 준수까지 보장하지 않는다.
- 일반 AI는 HTTP 성공을 2xx로 제한했고 FS는 400 미만을 성공으로 취급했다. 이번 계획은 3xx의 처리 정책을 명시하지 않았고 검사하지 않았다. 이를 사후 규정 위반으로 점수에 넣지 않는다.

이 결과를 유지한 채 나머지 두 사례에서 같은 계약의 재현성을 확인할 수 있다. 더 큰 작업은 사용자가 실제로 겪는 승인 경계 위반 사례를 고정한 뒤 평가해야 한다. 일반 AI가 실패할 때까지 정답이나 금지 사항을 바꾸는 실험은 피한다.
