# v4: 근거 기반 요청 경계 평가

목적은 승인된 설계 준수와 판단 근거를 측정하는 것이다. 특정 폴더 수, 패턴 이름, 토큰 절감을 성공 조건으로 삼지 않는다. 기존 스킬·MCP 경로를 사용하며 별도 모델 오케스트레이터를 FS 제품에 추가하지 않는다.

## 비교 경로

| 실험 | 같은 조건 | 관찰 대상 |
| --- | --- | --- |
| implementation | 코드·지식·공개 인터페이스·확정 계획 | 동작 계약 준수, 불필요한 변경, 수정 시도, 전체 사용량, FS 경로 실행 |
| planning | 코드·지식·요청·질문 주제 목록·조건별 답변집 | 코드 근거, 필요한 질문, 유지 선택, 결정과 계획의 연결; 의미 평가는 사람 검토 |
| compliance | 같은 명시적 계획·필수/금지/재량 항목·동일한 모의 사용자 답변 | 첫 구현의 규정 준수, 금지 위반, 질문 전 임의 진행, 답변 반영, 수정 비용 |

세 사례는 중복된 요청 정책, 이미 적합한 client, 화면별 정책 소유자가 다른 경우다. `existing-good`은 client 파일의 바이트 보존도 검사한다. 구현 비교는 같은 확정 계획을 제공하므로 계획을 잘 세우는 효과를 증명하지 않는다. 계획 비교는 구현 결과를 채점하지 않는다.

각 사례·조건마다 새 프로젝트와 대화를 만들고, 한 여정 내부의 준비→작업 또는 질문→계획만 같은 대화를 사용한다. 일반 AI와 FS 모두 같은 배포 지식을 읽을 수 있다. FS만 스킬·MCP 절차를 사용한다. 조건 실행 순서를 번갈아 두며 모델별로 별도 실행한다. 300초는 모델 호출 제한이며 질문 응답을 기다리는 시간이 아니다. 질문은 JSON으로 종료하고 실제 질문한 주제의 답만 다음 호출에 제공한다.

## 실행

저장소 루트에서 실행한다. Node, Python 3.9+, Git이 필요하며 실제 비교에는 로그인한 Codex CLI와 정상 작동하는 `codex sandbox`가 필요하다. 의존성이 없다면 먼저 `npm ci`와 `npm --prefix test/fixtures/frontend ci`를 실행한다. 이 파일럿은 브라우저를 띄우지 않는다.

```sh
npm run check
python3 test/evals/fs-comparison/v4/runner_test.py
python3 test/evals/fs-comparison/v4/run.py --calibrate-only
# 위 사전 검사 통과 후 모델 사용량을 소비한다.
python3 test/evals/fs-comparison/v4/run.py --run --track implementation --model gpt-6-sol
python3 test/evals/fs-comparison/v4/run.py --run --track planning --model gpt-6-sol
# 계획 준수 강화 비교: 한 쌍부터 실행 (정상 완료 시 4회 호출)
python3 test/evals/fs-comparison/v4/run.py --run --track compliance --case duplicated --model gpt-6-sol
# 전체 세 사례 (정상 완료 시 12회 호출)
python3 test/evals/fs-comparison/v4/run.py --run --track compliance --model gpt-6-sol
```

인자 없는 실행은 매니페스트만 저장한다. 세 사례가 양쪽 조건에서 모든 단계를 마치면 12번 호출하며, 구현은 실패한 작업에 한 번의 추가 수정만 허용한다. 실패한 호출의 비용도 보존하고, 사용량이 없으면 0으로 채우지 않는다. 격리 실패는 중단하며 권한 완화로 우회하지 않는다.

`--case duplicated`를 추가하면 한 사례의 일반 AI/FS 쌍만 실행한다. 프롬프트·계획·판정기·300초 제한은 그대로다. 정상 완료 시 준비/작업 각 2회로 4번 호출하며 실패 시 조기에 끝날 수 있다. 전체 기본 실행도 준비 단계가 실패하면 12회 미만으로 종료된다. 선택된 사례는 매니페스트에 남긴다.

## 판정과 원자료

- `manifest.json`: 모델·제한·코드·지식·스킬·실행기·설정 해시. 실행 도중 배포 자료가 달라지면 중단한다.
- `journey.json`: 단계 기록, 호출별 사용량의 합, 실제 MCP trace, 제품 통과와 FS 절차 통과의 구분.
- 각 호출의 `model/`, `snapshot/`, `record.json`, `grader/`: 프롬프트·로그·결과 코드·검사 결과.
- `interaction.json`: 실제 질문과 제공한 답변만 저장. 미질문 답변은 제공하지 않는다.
- `summary.json`: 전체 상태와 모델 호출 수. `eligible`은 해당 제한된 구현 계약을 통과했다는 뜻이며 범용 설계 품질 점수가 아니다.

FS 조건은 `get_work_context`의 실행된 라우팅, 근거 있는 `save_project_context`/`save_revision`, 구현 시 성공한 완료 기록을 확인한다. 절차를 생략하면 `workflow-failed`로 남긴다. 이 관찰 자체도 모든 판단의 타당성을 보증하지 않는다. 승인 검증은 서버가, 최종 코드 계약은 외부 판정기가 각각 확인한다.

행동 검사는 성공 응답, 입력 객체·headers 보존, 인증 만료 1회 처리, 업무 오류 정보 전달, 전송 오류 보존, 자동 재시도 부재를 확인한다. 실제 JSX 빌드와 App 내부의 직접 요청도 검사한다. 정적 검사는 지정된 호출 형태에 한정되므로 별칭·추가 파일·전체 호출 그래프를 통한 우회까지 증명하지 않는다. UI 문구·구조 선택·질문의 적절성은 별도 의미 검토 대상이다.

## 계획 준수 계약 v1 — 2026-10-04 추가

기존 `implementation`의 동작 판정기와 과거 점수는 보존한다. `compliance`는 [명시적 계약](compliance.json)을 양쪽의 PROVIDED_PLAN.md에 동일하게 추가한다. 이 계약은 이번 사례의 승인 경계이며 FS 지식을 보편적인 정답으로 격상한 것이 아니다.

| 항목 | 판정 |
| --- | --- |
| F1 필수 동작 | 기존 공개 인터페이스·요청·오류·보존 검사 |
| F2 참조 계약 | options/headers만 얕게 복사하고 body의 참조를 보존하는지 |
| N1 변경 범위 | 기존 다른 파일을 보존하고 새 제품 파일·설정·의존성을 만들지 않는지 |
| N2 의존 경계 | App은 react만 import, api는 주입된 transport 사용; 금지한 모듈·동적 실행·전역 요청 구문 검사 |
| N3 공개 API | api의 export와 client의 공개 키를 임의로 늘리지 않는지 |
| Q1 사용자 결정 | 준비 단계에서 콜백 실패 정책을 질문한 뒤, 동일한 답변에 따라 원래 오류 객체를 전달하는지 |
| D1 재량 | 경계 안의 함수명·함수 개수·주석·테스트 구성·UI 문구는 점수에 불이익 없음 |

준비→작업 두 호출을 유지한다. 준비의 최종 JSON으로 Q1을 질문해야 다음 단계에서 USER_DECISIONS.md를 제공한다. 답변은 양쪽에 동일하며 계획과 함께 변경을 금지한다. 질문 없이 진행하거나 준비 단계에 제품 파일을 변경하면 프로토콜 실패로 종료한다. 이는 질문의 창의성 평가가 아니라 **판단 권한을 지키는 절차 검사**다. 질문 의미·선택 기록의 타당성은 독립 리뷰 전까지 미검증이다.

`grade.json`은 `behaviorEligible`과 `planCompliance`를 분리한다. 필수 충족 항목 수/전체 수, 금지 위반 ID, 결정 위반 ID를 기록하고 단 하나의 위반도 최종 통과로 상쇄하지 않는다. `summary.json.comparison`에는 최초 구현 통과, 최초/최종 규정 준수, 질문 절차, 수정 호출 수, 시간·전체/비캐시 입력 토큰을 남긴다. 수정 후 통과해도 최초 위반 기록은 보존한다. 사용량 누락은 0으로 처리하지 않는다. 계획과 무관한 새 금지 사항을 과거 실행에 소급 적용하지 않는다.

고정 예제 교정은 **허용 구현 6개 수용 / 결함 18개 거부**다. 함수명 변경과 테스트 추가는 허용하고, 재귀 복사·공개 API 추가·콜백 오류 대체·새 제품 파일·새 모듈 의존·보호 파일 수정은 각각 거부했다. client 보존 사례를 제외한 결함 예제는 기존 기능 검사에는 모두 통과하므로, 기능 성공과 계획 위반을 구분하는 판정력을 확인했다. 이는 AI 비교 성과가 아니다.

스냅샷 사이에서 수정 후 되돌린 임시 위반과 임의의 JavaScript 우회, 전체 아키텍처 품질은 자동 검사의 범위 밖이다. 외부 검사는 모델이 바꿀 수 없는 실행기에서 수행하며 모델 코드는 기존 격리 실행 경로로만 평가한다.

## 계획 응답 비용 개선 — 2026-10-04 추가

`save_revision`과 `approve_revision`은 기본적으로 해시·버전·승인 상태·근거 상태·결정/규칙/이슈 ID만 반환한다. `get_revision`은 계획 본문·정책·이슈 계약을 유지하고 반복되는 원본 라우팅 근거를 생략한다. `detail: full`로 전체 근거를 읽을 수 있고, `expectedHash`가 다르면 페이지 읽기를 거부한다. 서버의 저장 형식, 승인·검증 조건은 그대로다. 익숙하지 않은 계약을 읽지 않고 요약 응답만 보고 구현해서는 안 된다.

[응답 재구성 검사](revision-response-regression.mjs)와 [측정 JSON](validation/revision-response-regression.json)에 근거를 남겼다. 모델 실행 없이 과거 응답에 새 표현을 적용한 수치이며 **전체 토큰·실행 시간 절감률이 아니다**. 새 비교의 비용으로 다시 확인해야 한다. 기존 소비자가 저장/승인 응답의 content/policy/evidence를 사용했다면 `detail: full`을 지정하거나 `get_revision`을 읽어야 한다.

수정 후 타입·린트·회귀 68개, v4 실행기 7개, maintenance 실행기 6개, 두 스킬 형식 검사, 독립 패키지 검사를 통과했다. 실제 MCP 검사에서 전체 정책·이슈 보존, 전체 근거 조회, 오래된 해시 거부, 근거 없는 승인/검사 없는 완료 거부를 확인했다. CI에도 새 판정기 교정과 실행기 검사를 연결했다.

현재 도구 환경의 [compliance 사전 검사](results/2026-10-04T120222/summary.json)는 `sandbox-exec: sandbox_apply: Operation not permitted`로 차단됐고 모델 호출은 0회다. 별도 터미널의 실제 비교 결과가 나오기 전까지 규정 준수 향상·토큰 절감을 주장하지 않는다.

## 2026-10-03 결과

### 입력·응답 단순화 후 검증

분석 참조 ID로 기존 라우팅 입력과 해시를 재사용하고, 요구사항 문서는 코드와 별도로 고정했다. 정책의 근거 문자열은 연결된 결정에서 생성한다. 빈 설명 배열과 버전 같은 기계적 값만 기본 처리하며, 선택·사용자 확인·규칙의 필수 여부·검증 방법은 자동 지정하지 않는다. 후보별 판단 누락, 오래된 코드·문서·요구사항, 미결정 선택, 실패한 검사에 대한 거부는 유지한다. 관련 없는 후보는 ID와 이유를 명시한 묶음으로 제외할 수 있고, 내부에는 개별 판단으로 남는다.
