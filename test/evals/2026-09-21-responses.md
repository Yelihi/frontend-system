## A — board_review

**Zustand는 유지하고 구독 범위를 좁히는 것이 우선입니다.** 문제는 store를 사용한다는 사실보다, 카드 하나가 전체 상태를 구독한다는 점입니다.

1. **확인된 구조적 위험: 무관한 변경에도 구독이 반응합니다.**  
   `useBoardStore()`는 전체 상태를 구독합니다. clock이 매초 새 상태를 만들면 카드 제목이 그대로여도 마운트된 각 `Card`가 렌더링 대상이 됩니다. 500개가 모두 마운트돼 있다면 영향 범위도 커집니다. 이는 “무관한 렌더링 제한”이라는 도입 목적과 맞지 않습니다. 다만 실제 지연이나 프레임 저하는 측정되지 않았습니다.

   팀 계약 안에서 가능한 최소 대안은 개별 selector입니다. 다음은 수정이 아닌 제안입니다.

   ```tsx
   const card = useBoardStore((state) => state.cards[id]);
   const openCard = useBoardStore((state) => state.openCard);
   ```

   클릭에서는 `openCard(id)`를 호출합니다. 무관한 업데이트가 기존 `card`와 액션 참조를 유지해야 효과가 있습니다. 표시할 데이터가 제목뿐이라면 `state.cards[id].title`을 선택해 같은 카드의 다른 필드 변경까지 구독에서 제외할 수 있습니다.

2. **store 의존은 있지만, 컴포넌트 분리가 반드시 필요한 것은 아닙니다.**  
   현재 `Card`는 저장 구조와 열기 액션을 직접 압니다. 보드 전용이라면 허용할 만한 결합입니다. 다른 화면이나 독립적인 테스트에서 재사용할 필요가 생기면 `title`, `onOpen`을 받는 표시 컴포넌트와 store 연결부를 나눌 수 있습니다. 파일과 props 전달이 늘어나는 비용이 있고, 연결부가 전체 상태를 구독하면 렌더링 문제도 남습니다. 지금은 selector 변경이 더 작고 직접적인 대안입니다.

3. **카드 누락은 조건부 위험입니다.**  
   `cards[id]`가 없는 상태에서도 렌더될 수 있다면 `card.title`에서 오류가 납니다. 삭제·로딩 시점에 부모가 어떤 ID를 전달하는지 제공되지 않아 결함으로 확정할 수 없습니다. 그런 상태가 허용된다면 숨김 또는 로딩 표시 등 의도한 동작을 정해야 합니다.

검증은 실제 store를 연결한 상태에서 clock 변경, 다른 카드 변경, 해당 카드 제목 변경, 카드 열기를 확인하면 됩니다. 무관한 업데이트로 카드 렌더가 발생하는지와 실제 commit 시간을 전후 비교하고, 제목 갱신과 열기 동작이 유지되는지도 확인해야 합니다. 부모가 유발하는 렌더는 별도로 구분해야 합니다.

현 상태 유지도 실제 비용이 작다면 가능하지만 넓은 구독은 남습니다. 라이브러리 교체를 정당화할 근거는 없으며, 교체는 팀 논의 대상입니다. 제공된 자료만 검토했으며 파일 변경이나 실행 검증은 하지 않았습니다.

## B — derived_review

현재 요구사항에는 `watch`로 결과를 별도 저장하기보다 **`computed`로 파생하는 방식이 적합합니다.** 아래는 수정 제안이며, 파일은 변경하지 않았습니다.

```vue
<script setup>
import { computed, ref } from 'vue';

const props = defineProps(['items']);
const query = ref('');
const visible = computed(() =>
  props.items.filter(item => item.name.includes(query.value))
);
</script>
```

- **조건부 정확성 문제:** 현재 watcher는 배열 참조 교체와 검색어 변경을 감지합니다. 부모가 같은 반응형 배열에 `push`·`splice`하거나 항목의 `name`만 바꾸면 필터가 다시 실행되지 않아 표시 대상이 오래된 상태로 남을 수 있습니다. 콜백 안에서 읽은 `item.name`은 watcher의 감시 대상에 자동으로 추가되지 않습니다. 실제 부모의 갱신 방식은 제공되지 않아 발생 여부는 확인하지 못했습니다.
- **불필요한 상태 동기화:** `visible`은 `items`와 `query`만으로 결정되므로 독립적인 쓰기 가능한 상태일 필요가 없습니다. `computed`는 계산 중 읽은 반응형 의존성을 추적하고 결과를 캐시합니다. `deep: true` watcher도 변경 누락을 보완할 수 있지만, 별도 상태를 동기화하는 구조는 남습니다. 항상 새 배열로 교체한다는 계약이 있다면 현재 코드도 해당 경로에서는 작동합니다.

최초 표시, 검색어 변경, 배열 교체, 동일 배열의 추가·삭제, 이름 변경으로 검색 조건에 들어오거나 빠지는 경우를 실제 표시 목록 기준으로 검증하면 됩니다. 대상 프로젝트와 실행 환경이 없어 테스트는 실행하지 않았으며, 성능 개선도 측정하지 않았습니다.

## C — profile_review

`useState` 3개는 현재 구조에서 문제가 아닙니다. 이름·이메일은 독립적인 입력이고 이 폼만 사용하므로 로컬 상태가 적절합니다. 오류도 별도 UI 상태로 두면 충분합니다. 지금은 객체로 합치거나 `useReducer`, 전역 저장소, 폼 라이브러리로 바꿀 근거가 없습니다.

- **확인된 결함 — 성공 후에도 이전 오류가 남습니다.** `catch`에서만 `setError`를 호출하므로, 저장 실패 → 재시도 성공 후에도 `Save failed`가 표시됩니다. 성공 시 오류를 비우는 최소 수정이 필요합니다. 재시도 중부터 지울지는 UX 선택이지만, 성공 이후에는 남지 않아야 합니다.
- **조건부 위험 — 저장 요청이 겹칠 수 있습니다.** 처리 중 제출을 막는 코드가 없어 연속 제출이 가능합니다. 두 요청의 완료 순서가 바뀌면 이전 요청의 실패가 나중 성공 뒤에 표시될 수 있습니다. 서버가 요청을 처리하는 방식에 따라 이전 값이 최종 저장될 가능성도 있으나, 제공된 코드만으로 서버 결과까지 확정할 수는 없습니다. 동시 저장이 필요 없다면 처리 중 중복 제출을 막는 것이 작은 대응입니다.
- **유지할 동작 — 성공·실패 모두 입력을 보존합니다.** `submit`은 `name`과 `email`을 초기화하지 않으므로, 제시된 컴포넌트 안에서는 요구사항을 충족합니다. 저장 대기 중 추가로 편집한 값도 유지됩니다. 오류를 고치면서 성공 시 폼을 비우거나 외부 프로필 값으로 덮어쓰면 안 됩니다.
- **확인 필요 — 입력 검증 계약이 없습니다.** 이메일 입력에 `type="email"`이나 별도 검증이 없어 이 폼 자체는 이메일 형식을 검사하지 않습니다. 형식 제한이 요구된다면 네이티브 검증을 활용할 수 있습니다. 필수값 여부와 서버 검증은 자료가 없어 결함으로 단정하지 않습니다.

기존의 “제출 핸들러가 호출됐다”는 테스트는 저장 결과에 따른 화면 동작을 보호하지 못합니다. 기존 테스트 환경에서 실제 폼을 렌더링하고 `save` 경계의 성공·실패만 제어해 다음을 확인하는 것이 좋습니다.

1. 입력 후 저장 성공: 제출 값이 맞고 두 입력이 유지된다.
2. 저장 실패: 오류가 표시되고 편집 값이 유지된다.
3. 실패 후 재시도 성공: 입력은 유지되고 이전 오류는 사라진다.
4. 저장 대기 중 추가 편집: 요청 완료 후에도 최신 편집 값이 유지된다.
5. 중복 제출 방지를 적용한다면: 대기 중 재제출로 추가 저장 요청이 발생하지 않는다.

제공된 코드와 사실만 검토했습니다. 파일은 변경하지 않았으며, 대상 프로젝트와 실행 환경이 없어 테스트는 실행하지 않았습니다.

## D — checkout_review

현재 테스트는 **주문 계약을 검증하지 못합니다.** 검증 대상인 `order` 자체를 mock으로 바꾸고 호출 여부만 확인하므로, 수량 검증이나 인증 처리를 삭제해도 통과할 수 있습니다. 외부 의존성을 mock으로 대체한 개수보다 **실제 구현을 실행하고 결과를 확인하는지**가 핵심입니다.

제공된 코드에서 확인되는 문제는 다음과 같습니다.

| 판단 | 근거와 실패 조건 | 영향 |
|---|---|---|
| 확정: 수량 검증 누락 | `quantity`를 검사하지 않고 요청 본문에 넣습니다. `0`, 음수, 소수, 문자열도 전송됩니다. | 양의 정수라는 계약을 함수 경계에서 보장하지 못합니다. 서버의 실제 수락 여부는 미확인입니다. |
| 확정: 인증 정보가 오래될 수 있음 | `token`을 모듈 로딩 시 한 번 읽습니다. 이후 로그인·로그아웃·토큰 교체가 반영되지 않습니다. | 정상 사용자의 주문 실패, 로그아웃 뒤 이전 토큰을 사용한 요청이 가능합니다. |
| 확정: 인증 정보가 없어도 요청 | `order`에 인증 확인 분기가 없습니다. | 클라이언트가 비인증 상태의 주문 요청을 차단하지 못합니다. 실제 무권한 주문 생성 가능 여부는 서버 확인이 필요합니다. |
| 확정: HTTP 실패와 성공을 구분하지 않음 | `response.ok` 확인 없이 `ordered`를 기록하고 JSON을 반환합니다. | 401·403·500 응답도 JSON이면 정상 반환 경로로 처리됩니다. 잘못된 JSON에서도 성공 로그가 먼저 남습니다. 호출자가 이를 어떻게 처리하는지는 미확인입니다. |

**작은 수정은 필요하지만, 새 계층이나 의존성은 필요하지 않습니다.** 단순한 구조 정리보다는 계약 위반을 바로잡는 작업입니다. `order(quantity)`와 기존 요청 형식을 유지하면서 함수 내부에서 양의 정수를 검증하고, 호출 시점의 인증 정보를 읽고, HTTP 성공 여부를 확인하는 방향을 권합니다. 성공 로그가 필요하다면 성공 응답 처리 뒤에 기록해야 합니다.

토큰의 존재만으로 권한을 보장할 수는 없습니다. 클라이언트는 명백한 비인증 요청을 막고, 서버는 만료·위조·권한 부족을 검증해야 합니다. 서버 구현은 제공되지 않았으므로 서버 결함까지 단정할 수 없습니다. 오류 반환·예외 방식은 호출자 계약을 확인한 뒤 정해야 하며, 임의로 공개 API를 바꾸거나 자동 재시도를 추가할 근거는 없습니다.

테스트에서는 **실제 `order`를 호출하고 `fetch` 같은 외부 경계만 대체**해야 합니다. 저장소 mock을 쓴다면 값 변경을 반영하도록 하고, 시간 고정과 로그 감시는 관련 결과를 확인할 때만 사용하면 됩니다.

| 필요한 케이스 | 기대 결과 및 금지 결과 |
|---|---|
| 인증된 상태에서 `order(1)` 및 다른 양의 정수 호출 | `/orders`에 POST 1회, 현재 토큰과 정확한 수량 전송, 성공 JSON 반환 |
| `0`, `-1`, `1.5`, `"1"`, `null`, `undefined`, `NaN`, `Infinity` | 입력 거부, **요청 0회**, 성공 로그 없음 |
| 인증 정보 없음 | 주문 요청 차단, 성공 결과·로그 없음 |
| 모듈 로딩 후 로그인·토큰 교체 | 호출 시점의 토큰 사용. 모듈을 다시 로딩해서 결함을 숨기지 않음 |
| 로그인 상태에서 모듈 로딩 후 로그아웃 | 과거 토큰으로 요청하지 않음 |
| 서버가 401·403 또는 500 반환 | JSON 본문이 있어도 실패로 전달, 성공 로그 없음 |
| 네트워크 실패 또는 성공 응답의 JSON 파싱 실패 | 오류가 호출자에게 전달되고 성공 처리하지 않음. 의도하지 않은 추가 요청 없음 |

무권한 사용자가 실제 주문을 생성할 수 없다는 보장은 별도의 서버 연동 검증이 필요합니다. 거부 응답뿐 아니라 **주문이 생성되지 않았는지**도 확인해야 합니다.

현재 테스트가 보호하는 동작은 호출 여부뿐입니다. 먼저 위 계약을 검증하는 테스트를 마련하고, 잘못된 수량 허용·이전 토큰 사용·HTTP 오류 무시를 실제로 잡는지 확인한 뒤 최소 수정을 진행하는 것이 적절합니다. 제공된 사실만 검토했으며, 파일 수정이나 테스트 실행은 하지 않았습니다.

## E — price_review

**현재 구조를 유지해도 됩니다. 제공된 사실에서 확인된 구조적 결함은 없으며, 확장성을 위해 지금 바꿀 근거도 없습니다.**

- 두 화면이 같은 순수 함수를 사용하므로 표시 규칙을 한곳에서 관리할 수 있습니다. KRW만 사용한다는 요구와 팀의 단순한 헬퍼 방침에도 맞습니다.
- 호출자가 비유한 숫자를 차단하므로, 해당 검증이 두 화면에 적용된다는 전제에서는 헬퍼에 검증을 중복할 필요가 없습니다.
- 호출마다 `Intl.NumberFormat`을 생성하지만, 성능 문제가 확인된 것은 아닙니다. 대량 호출에서 실제 비용이 드러나면 포매터 인스턴스 하나를 재사용하는 정도로 충분합니다.

기존 테스트는 0과 양수를 다루지만, 코드가 없어 실제 기대 문자열을 검증하는지는 확인하지 못했습니다. 원화 기호와 천 단위 구분이 잘못되면 실패하는지 확인하면 됩니다. 음수·소수 처리는 실제 허용 입력일 때만 요구사항과 테스트를 보완하세요.

다른 통화나 로케일이 실제 요구사항이 되면 매개변수 확장을 검토하세요. 지금은 클래스·전략·팩토리 같은 추상화를 추가할 이유가 없습니다. 제공된 사실만 검토했으며 파일 수정이나 테스트 실행은 하지 않았습니다.

## F — record_review

아직 **현재 r2의 프로필 저장을 검증 완료로 볼 수 없습니다.** `profile-r1`은 r1의 과거 성공 결과이며, 현재 통과한 입력 검증 단위 테스트는 저장 실패·재시도·영속 저장을 확인하지 않습니다. 이는 검증 부족이지, 기능 결함이 확인됐다는 뜻은 아닙니다.

필요한 확인 절차는 다음과 같습니다.

1. **실행 준비:** r2를 실행할 실제 명령, 환경, 테스트 계정과 기존 테스트 전송 계층의 실패 유발 방법을 확인합니다. 제공된 사실에는 구체적인 실행 방법이 없습니다.
2. **현재 화면 진입:** `/settings/profile`에서 Name을 기존 값과 구분되는 값으로 바꾸고 `Save changes`를 누릅니다.
3. **저장 실패 확인:** 기존 테스트 전송 계층으로 요청을 한 번 실패시킵니다. 오류가 표시되고 **수정한 값이 유지되는지** 확인합니다.
4. **재시도 확인:** 같은 값을 다시 저장해 성공시킵니다. **오류가 사라지고 수정한 값이 유지되는지** 확인합니다.
5. **영속 저장 확인:** 새로고침하거나 화면을 재진입해 저장된 값을 다시 읽고, 수정한 값이 반환되는지 확인합니다. 성공 응답이나 화면에 남은 입력값만으로는 부족합니다.
6. **결과 구분:** 실행 시점·소스 r2·환경·각 단계의 실제 결과와 로그/추적 자료를 확인합니다. 기존 절차의 경로와 버튼명은 현재 값으로 읽어야 하며, `profile-r1`을 이번 실행 결과로 재사용하면 안 됩니다.

코드와 기록은 수정하지 않았고, 실제 실행도 하지 않았습니다. 위 항목은 모두 현재 미검증 상태입니다.

## G — requests_review

**현재 자료만으로 StrictMode가 원인이라는 결론은 믿기 어렵습니다. 확인되지 않은 가설입니다.**

확인된 사실은 개발 빌드에서 Save를 한 번 클릭한 뒤 **본문이 같은 POST 요청 두 건이 기록됐다**는 것입니다. 두 요청의 발생 경로, 서버 처리 결과, 실제 중복 레코드 생성 여부는 확인되지 않았습니다. 같은 본문만으로 원인이 같다고 판단할 수도 없습니다.

원인을 확인하려면 다음 자료를 순서대로 봐야 합니다.

| 확인할 자료 | 구분하려는 원인 |
|---|---|
| 두 요청의 Network **Initiator·호출 스택**, 발생 시각, 응답 상태 | 서로 다른 코드 경로에서 호출됐는지, 첫 요청 이후 재시도됐는지 |
| Save의 이벤트 처리부터 API 호출까지의 코드와 모든 호출자 | `onClick`과 폼 `onSubmit`의 중복 처리, 이벤트와 Effect 양쪽의 저장 호출 여부 |
| 관련 Effect, 의존성, 상태 변경 및 마운트 경로 | Effect 실행 경로가 요청을 발생시키는지, StrictMode 가설이 실제 호출 경로와 연결되는지 |
| API 클라이언트·인터셉터·저장 라이브러리의 재시도 설정 | 한 번의 저장 호출이 전송 단계에서 재시도로 이어지는지 |
| 서버 처리 로그와 생성된 레코드 ID | 두 요청이 실제로 중복 레코드를 생성했는지 |

개발·프로덕션 빌드 비교도 보조 증거가 됩니다. 다만 프로덕션에서 재현되지 않는다는 사실만으로 StrictMode를 원인으로 확정할 수는 없습니다. **현재 설정을 유지하고 호출 경로부터 확인하는 것이 우선**입니다.

원인이 확인되면 중복 호출은 해당 공통 경로에서 바로잡고, 재시도가 원인이라면 재시도 정책과 서버의 중복 생성 방지 계약을 함께 검토해야 합니다. 지금 특정 수정안을 선택할 근거는 없습니다.

검증 기준은 단순한 요청 횟수가 아니라 합의된 계약인 **“한 저장 동작이 중복 레코드를 만들지 않는다”**입니다. 정상 저장과, 서버 저장 후 응답 유실로 재시도되는 경우에도 생성 결과를 확인해야 합니다. 제공된 자료에는 코드·실행 환경이 없어 재현이나 테스트는 수행하지 않았으며, 설정이나 파일도 변경하지 않았습니다.
