# FS 판단 회귀 평가

최신 비용 측정은 [v14 반복 토큰 추세](fs-comparison/v14/README.md)입니다.
두 프로젝트·3회 반복·일반/FS·분석/계획의 24개 실행, 380개 응답을 계측했습니다.
FS 총 처리 토큰은 일반의 9.72배, 비캐시 입력+출력은 3.10배였습니다. 요청 수와
큰 입력의 반복 처리가 함께 나타났으며, [작업별 그래프·실행 선택 보고서](fs-comparison/v14/results/2026-10-07-trajectories/report.html)에
원자료와 실패를 포함합니다. 최초 측정은 FS를 고정하고 수정 우선순위를 제시했습니다.

후속 30회 재시험에서 기록 호출 통합 지침만으로는 FS 총 토큰이 2.2% 증가했습니다.
기존 분석서의 불필요한 재작성을 제한한 추가 계획 시험은 6/6 전달을 마쳤고,
재작성은 5/6→0/6건이었습니다. 계획 비용은 첫 수정본보다 13.6% 줄었지만 최초
기준보다 총 토큰 2.1%·비캐시 입력+출력 7.6% 감소에 그쳐 큰 절감은 미입증입니다.
[수정 내용·세 시점의 결과·한계](fs-comparison/v14/README.md#후속-수정과-재시험--2026-10-07)에 기록했습니다.

최신 흐름 분석/시각화 검증은 [v13 실제 코드·새 세션 평가](fs-comparison/v13/README.md)입니다.
기존 파일이 새 호출부가 되는 경우의 변경 감지, HTML 해시, 최초 기준 문서와 계획 저장을
검사합니다. 실패와 수정 후 재실행 비용을 함께 보존하며, 산출물 존재만으로 FS 계약
전달 성공으로 판정하지 않습니다.

이전 지식별 조사 결과는 [v11 지식별 조사 기준 비교](fs-comparison/v11/README.md)입니다. 같은 편집 코드의 호출부·계약을 바꾼 네 상황에서 일반 AI·동일 원문 AI·FS 리뷰 12회를 모두 완료했습니다. FS 네 사례의 트리거 연결·본문 전달·근거 저장을 확인했지만 핵심 설계 판단은 다른 조건에서도 나왔습니다. 총 토큰은 일반 415,215 / 원문 394,582 / FS 1,690,863이며, FS는 일반 대비 총 토큰 4.07배·비캐시 입력+출력 2.73배였습니다. FS의 추가 기록 의무와 복구된 MCP 입력 오류 3건을 포함합니다. [전체 수치·실제 리뷰·범위와 한계](fs-comparison/v11/results/2026-10-06-investigation-1/analysis.md)에 보존했습니다.

이전 [v10 다중 프로젝트 계획 비교](fs-comparison/v10/README.md)는 여섯 상황에서 실제 질문→답변→계획을 비교하고 라우팅·응답 오류 네 가지를 수정했습니다. 추가 회귀와 짧은 요청 비교까지 37개 여정 중 36개를 완료했습니다. FS 지식 연결·저장 일치는 확인했지만 설계 품질·비용 우위는 미입증입니다. 실제 생성·리뷰 76회, 알려진 총 토큰 16,130,437 이상이며 제공자 용량 부족 두 건과 모든 실패 비용을 보존합니다.

이전 비교는 [v9 지식·질문·설계 판단](fs-comparison/v9/README.md)입니다. 최초 8개 여정 이후 네 번 보완·재시험하고, 명시적 사용자 결정의 후속 반영도 비교했습니다. FS의 기록 일관성과 입력 전달은 보완됐지만 고유한 품질·비용 우위는 입증하지 못했습니다. 후속 여섯 의무는 원문 AI/FS 모두 반영했고, 추가 총 토큰은 121,970 / 556,475였습니다. [네 회차 전체·실패 포함 비용](fs-comparison/v9/results/2026-10-05-iteration-4/analysis.md)에 계획/후속/리뷰 48회 호출과 알려진 토큰 19,470,343 이상을 보존합니다. 미보고 사용량은 0으로 처리하지 않습니다.

이전 확장 실험은 [v8 문서 발견·후속 변경](fs-comparison/v8/README.md)입니다. 일반 지시/문서 위치 안내/FS 절차의 세 조건에서 같은 프로젝트를 세 번 변경하며 단계마다 대화를 초기화합니다. 결과와 비용은 실행별 원자료로 기록합니다. [v7 작성 규칙 비교](fs-comparison/v7/README.md)의 5회 실측도 보존합니다.

이전 확대 비교는 [v6 운영 콘솔](fs-comparison/v6/README.md)입니다. 32개 변경 대상·69개 외부 계약·8개 사용자 결정으로 확장한 뒤 6쌍을 실측했습니다. 최종 고정 버전 2회에서 FS 처리량은 첫 v6보다 감소했지만 일반 AI 대비 구현 준수/비용 우위는 입증하지 못했습니다. 중간 절차 실패와 비용 회귀도 모두 보존합니다. 아래 v4 이하 기록은 과거 결과입니다.

**이전 v4 compliance 결과:** [12:36:41 한 쌍](fs-comparison/v4/results/2026-10-04T123641/analysis.md)에서 일반 AI/FS 모두 첫 구현 11/11, 금지·결정 위반 0건, 수정 0회였다. FS는 총 처리 토큰 5.55배·비캐시 입력 1.93배·시간 2.85배를 사용했다. 명시적 계약의 준수 우위는 관찰되지 않았고, 다른 두 사례와 독립 의미 평가는 이 실행의 범위 밖이다.

**새 비교 경로:** [v4 compliance](fs-comparison/v4/README.md)는 같은 계획의 필수·금지·재량·질문 항목을 명시하고 최초 위반, 사용자 답변 반영, 수정 비용을 측정한다. 고정 예제 6개 수용/18개 거부를 확인했으며 실제 AI 비교와 분리해서 해석한다. 아래 3/3 결과는 이전의 제한된 동작 계약 결과이며 새 규정 준수 점수로 바꾸지 않는다.

**2026-10-04 이전 implementation 결과:** v4 동일 계획 구현에서 일반 AI/FS 모두 3/3 첫 구현 통과, FS 절차도 관찰됐다. 다만 FS 총 처리 토큰은 5.75배, 시간은 2.09배였으며 추가 구현 성과는 입증되지 않았다. [최신 수치·한계·코드 관찰](fs-comparison/v4/results/2026-10-04T074740/analysis.md)을 참고한다. 질문·계획 수립 효과는 별도 평가 대상이다.

이전 구현의 비교는 [v4 근거 기반 요청 경계 평가](fs-comparison/v4/README.md)를 사용한다. 같은 계획의 구현 준수와 질문·계획 수립을 분리하고 FS 경로 생략을 별도 실패로 기록한다. 2026-10-03 로컬 기능 검사 후 외부 터미널에서 실제 비교를 실행했다. 모델 9회 호출, 일반 AI 3/3 첫 구현 통과, FS 3/3 준비 단계 시간 초과다. [수치와 원인 분석](fs-comparison/v4/results/2026-10-03T171521/analysis.md)을 참고한다. 아래 기록은 이전 실험의 이력이다.

[v2 실제 비교](fs-comparison/v2/README.md)는 36회 실행을 완료했고 토큰 절감·일관된 품질 우위가 입증되지 않았다. 원자료와 실패 분석을 보존한다. 후속 [v3 평가 설계](fs-comparison/v3/README.md)는 합의한 코드 기준 충족도, 지식 sync/적용 적합성, 사용자 상호작용과 후속 수정까지의 누적 비용을 분리한다. 현재 설계·집계기 준비 단계이며 모델 재실험은 사용자의 코드 검토 이후 진행한다. 결정적 회귀 검사 통과를 모델 성능 개선으로 보고하지 않는다.

동일한 구현 요청을 일반 Codex와 FS에 전달해 모델별 토큰·결과물을 비교하는 실험은 [FS 사용 여부별 통제 실험](fs-comparison/README.md)을 참고한다. 새 세션·초기 코드 사본·고정 외부 채점기를 사용하며, 아래의 리뷰 시나리오 평가와 별도로 기록한다. 실제 모델 사용량을 소비하므로 일반 CI에서 자동 실행하지 않는다.

실행 도구의 보장 검증은 `npm run test:eval`로 별도 재현할 수 있다(개발/CI Node 24).
`test/reliability-eval.test.ts`는 Next.js 예제의 실제 주문 모듈과 테스트를 임시
프로젝트에 복사하고 세 계약을 세 번씩 평가한다. 잘못된 코드·오래된 검사·약화한
테스트의 완료 거부, 복구 후 완료 승인, 기존 정책의 읽기와 복구를 확인한다.
검사 하나는 10초로 제한하고, assertion 진단 없는 시간 초과/설정 실패를 계약
오류 탐지로 인정하지 않는다. 기록 파일은 임시 프로젝트와 함께 정리하며 결과에는
규칙·소스/정책 해시·거부한 조건을 출력한다. `npm run check`에도 자동 포함된다.
이는 결정적 도구 평가이며 아래의 호스트 모델 판단 평가나 실제 소비 프로젝트의
성과를 대체하지 않는다. 세 번 성공을 신뢰도 백분율로 바꾸지 않는다.

스킬·공통 판단 지침·지식 적용 방식 또는 호스트 모델을 변경할 때 관련 사례를
다시 실행한다. 일반 제품 작업에 평가를 추가하거나 기존 승인·완료 조건을
바꾸는 절차가 아니다. `npm test`는 모델의 판단 품질을 채점하지 않는다.

## 실행과 비교

1. [입력 사례](review-scenarios.md)와 [판정 기준](review-rubric.md)을 변경 전에
   고정한다. 공유 리뷰 지침 변경에는 A~G를 사용하고, 좁은 변경에는 관련 사례를
   고른 뒤 선택 이유와 제외 범위를 적는다. 기존 결과 문서는 과거 관찰이다.
2. 변경 전후 스킬과 필요한 참조를 각각 임시 디렉터리에 복사한다. 같은 입력,
   모델·설정, 도구·쓰기 권한으로 실행하고 파일 해시와 변경 diff를 보관한다.
   모델 비교라면 스킬을 고정한다. 여러 변수를 바꿨으면 효과를 분리할 수 없다고 적는다.
3. 사례마다 새 세션이나 허용된 네이티브 에이전트를 사용한다. 입력 파일의 해당
   사례 본문과 스킬만 전달하고, 이전 대화·결과·판정 기준·다른 사례는 전달하지
   않는다. 임시 경로와 요청에는 평가 여부나 기대 답을 드러내지 않는다.
   스킬의 상대 참조 구조를 보존한다. 외부 모델 실행기나 유료 API는 추가하지 않는다.
4. 답변 원문과 관찰 가능한 도구 호출·쓰기 결과를 보관한다. 평가자는 원문과
   실제 행동을 기준으로 판정한다. "검증했다"는 자기 보고만으로 실행을 인정하지
   않는다. 도구 기록이 없으면 행동은 미확인으로 남긴다. 평가용 임시 자료와 결과
   저장은 평가 담당자의 작업이며, 리뷰 대상에게 쓰기를 허용하는 뜻이 아니다.
5. 같은 기준으로 변경 전후를 `통과 / 실패 / 미확인`으로 비교한다. 결함 탐지,
   불필요한 변경, 근거 없는 단정, 미실행 검증의 성공 보고를 따로 본다.
   하나의 점수나 평균으로 중대한 실패를 숨기지 않는다. 판정이 애매하면 근거를
   기록하고 해당 사례를 새 세션에서 양쪽 모두 재실행한다. 실패 기록도 보존한다.
6. 새 회귀가 있으면 해당 변경을 수정하거나 보류하고 관련 사례를 다시 실행한다.
   실행할 수 없으면 평가 미실행으로 보고한다. 과거 요약과 현재 한 번의 실행만으로
   개선을 입증하지 않는다. 동일 조건의 변경 전 실행이 없으면 현재 기준선으로 기록한다.

이 절차는 작성자가 스스로 답을 예상해 확인하는 것과 독립 실행을 구분한다.
새 세션도 완전한 블라인드나 모델 독립성을 보장하지 않는다. 실제 모델·설정을
알 수 없으면 미확인으로 적고, 단일 실행을 신뢰도 백분율로 환산하지 않는다.

## 결과 기록

새 결과 파일에 날짜, 평가 대상과 파일 해시, 입력·판정 기준 버전, 모델·설정,
도구·환경 제약, 사례별 원문·관찰 행동·판정 이유·한계, 변경 전후 차이를 남긴다.
기존 [초기 결과](review-results.md)와 [통합 결과](consolidated-results.md)는
덮어쓰지 않는다. 전체 성공 대신 실행한 사례와 미확인 범위를 명시한다.
현재 기준선과 기록 예시는 [2026-09-21 결과](2026-09-21-results.md)를 참고한다.
보고 지침의 좁은 변경 비교는 [보고 사례](reporting-scenarios.md)와
[전후 결과](2026-09-21-reporting-results.md)에 별도로 기록했다.

실제 오판이 발견되면 민감 정보를 제거하고 당시 요청·최소 코드·제품 계약·관찰된
실패를 재현 가능한 사례로 추가한다. 실제 사례와 합성 사례를 구분하고, 정답을
현재 구현이나 모델의 취향에서 만들지 않는다. 사례 추가가 공통 규칙 승격이나
제품 정책 변경을 승인하는 것은 아니다. 실패에 맞춰 조정한 사례만 통과했다면
별도의 미사용 사례에서도 확인하기 전까지 일반적인 개선이라고 주장하지 않는다.
